## Project Overview

Vaultaire is a universal storage orchestration engine providing a unified S3-compatible API across multiple storage backends (local, iDrive e2 (primary, per-region), Seagate Lyve Cloud, Geyser (tape), Cloudflare R2 (public buckets only), OneDrive fleet (permafrost, internal), Sync.com via its encrypted WebDAV bridge (`sync`, target-only, flag-gated; generic WebDAV driver), Blomp over OpenStack Swift (`blomp`, target-only, flag-gated; generic Swift driver), Quotaless/S3-compat (dormant)). It is the core of FairForge's commercial product stored.ge — prices live in `internal/api/landing/prices.json`.

**Language**: Go 1.26 | **Database**: PostgreSQL 18 (prod 18.6; local dev may run older) | **Router**: chi/v5 | **Logging**: Uber Zap

## Architecture

### Three-Layer Design

```
API Layer (internal/api)      S3 protocol translation, auth middleware, HTTP handlers
Engine Layer (internal/engine) Backend orchestration, breaker-based failover, storage-class placement, smart demotion (flag-gated); the tiering/caching/ML/cost paths are inert (WP-R6-4)
Driver Layer (internal/drivers) Storage provider implementations (local, s3, lyve, quotaless, onedrive, geyser, idrive, r2, wasabi, webdav)
```

### Key Database Tables

Registration persists to **four tables in order**: `users` -> `tenants` -> `api_keys` -> `tenant_quotas`, in one transaction (R10). Missing any causes failures. **The `api_keys` row is the credential (WP-R5-14, migration 076):** the primary pair is an `is_primary` row with its `tenant_id` on it, every lookup (S3 SigV4, presigned URLs, STS minting — one function, `auth.Auth.LookupCredential`) resolves `api_keys` by `key_id` with `revoked_at` honoured, then `sts_tokens` for ASIA-prefixed temporary credentials joined to the parent key (a token dies with its parent). `tenants.access_key/secret_key` are a mirror of the live primary pair, rewritten by a rotation in the same transaction and read by no lookup. The primary is rotated, never revoked (`auth.ErrPrimaryKeyRevoke`, 409). A JWT issued before `users.password_changed_at` is refused.

Other critical tables (100 migration files numbered 003–102 (004 twice, 053 never existed) through `102_bucket_mode.sql`; `100_contract_drops.sql` was the first DROP — the deploy re-applies every file, so a dropped object's CREATE is emptied in the same change; the next number is in `docs/STATUS.md`):
- `object_head_cache` — HEAD/GET metadata cache (~1ms), content-type, ETag, metadata JSONB. **What the row knows about its bytes (094, Stage 1a Prompt 14):** `body_md5` = the whole body's MD5 when the ETag is not it (a multipart upload completed whole: its ETag is the parts' `-N`), written by Complete's whole branch and verified against by every whole GET and `/cdn` (`COALESCE(body_md5, single-part ETag)`; NULL = a row written before, a single-part object, a chunked one, an R2 direct multipart — served size-checked as before); `ssec_key_md5` = the base64 MD5 of the customer's SSE-C key (never the key), so HEAD and GET with a key of another MD5 are 403 from the row before any read (NULL = written before: HEAD 200, GET 403 at the blob). Both copied onto `object_versions` with the version's attributes
- `buckets` — bucket registry with visibility, cache TTL, metadata JSONB, slug, **`mode`** (102, keystone K3: `GENERATED ALWAYS … STORED` from the two columns below — `public-read` → `public`, `ssec_required` → `private`, else `standard`; NAME TRAP: `visibility = 'private'` is **Standard** mode; it can never drift and the previous build never writes it. A bucket's mode changes ONLY through `modes.SetBucket` (`internal/modes`), the one writer of `visibility` / `ssec_required` after a create, which enforces the 096 rule in its statement — `TestBucketModeWritersOnlyThroughTheDoor`; the names and sentences are `internal/api/landing/modes.json`'s, never typed — `TestModeNamesOnlyFromModesJSON`), `ssec_required` (096, WP-SSEC-1 B.5: every write must carry a customer key — an unkeyed PUT/Create/copy is 400 `InvalidRequest`, a generated object is refused, a public bucket cannot set it), and two CORS columns: `cors_origins` (the `/cdn` allow-list) and `cors_rules` (078: the S3 API's `?cors` configuration in the AWS shape, NULL = none — the OPTIONS preflight is answered before SigV4 from the rules of every bucket of that name, a signed response carries only the caller's own bucket's rule, `internal/api/s3_cors.go`; partial index `idx_buckets_name_with_cors` on `name`, 079)
- `multipart_uploads`, `multipart_parts` — in-progress multipart state; the upload row also keeps the attributes sent on CreateMultipartUpload (content type, `x-amz-meta-*`, cache/disposition/encoding headers, `x-amz-storage-class` — 068, R3) because CompleteMultipartUpload carries only the part list. **Parts are billed (WP-R10-8 Part C, 091):** each UploadPart reserves its bytes on the upload's floor before staging (`reserved_bytes` / `reserved_floor` on the row, under its lock; 403 past the quota, nothing staged); Complete settles the holding into the object inside its commit, Abort / the reaper / the erasure release exactly it (`endUploadReleasing`), the reconcile counts active holdings (`usage/billed.go`); `sse_requested` (089, WP-R8-5) keeps `x-amz-server-side-encryption: AES256` from Create, placed at Complete as on a PUT
- `object_versions` — versioning support (version_id, is_latest, delete markers). Every write of a key's rows (a version write, a delete marker, a version delete, a Complete retry's re-assert) runs in one transaction under `pg_advisory_xact_lock` on the key (`lockVersionKey`, Prompt 2b 0.5), and 083's unique partial index allows one `is_latest` row per key. **A retained version is billed** (WP-R2-1 C2, 088 `object_versions.floor`): a row with `storage_key` set, not a delete marker, whose address is not the head row's blob (`usage.RetainedVersionsFrom`) counts in `tenant_quotas` and on its floor (`usage.RetainedVersionFloor`: its own, else the head row's, else vault on geyser, else standard) — the head row's charge passes to the version when a write or delete leaves the blob to it (`displacedRow.KeptByVersion`, nothing released), and is released by `DELETE ?versionId` and by a Suspended null-version rewrite (`ReplacedVersion`); the reconciles, `SetHouse`, the dashboard and the quota check of every write include it. GET/HEAD `?versionId` serve a retained version from its own row; 501 only for a non-current version written before C1 (no address). **A version can be chunked (WP-VM-1, 092):** a chunked version row has `backend_name = 'chunked'` and its `storage_key` names its MANIFEST's address; it is read, copied, billed (C2, matched by address and kind — `usage.VersionRetained`) and retired like a whole one. Since 092 every version write copies the head row's attributes onto the version (`metadata`, disposition, encoding, language, cache-control, expires, redirect — R61-8) and GET/HEAD/copy of the version send them. A Suspended plain DELETE replaces the null version with a null delete marker (R61-5). HEAD names the current version (R85-2)
- `object_head_cache.storage_key`, `object_versions.storage_key` / `encryption_algorithm` / `encryption_key_version` (087), `smart_demotions.storage_key`, `multipart_uploads.storage_key` (087), `retired_blobs` — WP-R2-1: where a whole object's bytes are, NULL = `<key>` (rows written before Part C, for ever); every reader resolves it through `objectBlobAddress` (`internal/api/blob_address.go`, 086). **Since Part C (087) every whole-object write** (PUT, CompleteMultipartUpload, CopyObject, generated objects, direct-upload complete) puts its bytes at a NEW address `<key>@<26 base32>` (`newBlobAddress`) and ONE transaction (`commitBlobWrite`, `blob_flip.go`, head lock then version lock) flips the head row and the version row to it; the displaced blob is kept while a version row names it (Enabled: retained versions keep real bytes; a pre-C version's `<key>` blob is anchored to its row) and otherwise retired (`overwritten`), never overwritten — a failure after the write leaves the old object intact and queues the new blob as `orphan_write`. A complete records its address on the upload row before writing (a retry reuses it). Keys over 857 bytes (or a Sync-tier leaf over 219 mapped characters) are `400 KeyTooLongError` before the body. `retired_blobs` = displaced blobs; the **`retired_blobs` job** (every 10 min) deletes a due row's blob on its RECORDED backend only after re-checking under the key's lock that no head/version/open-ledger row or active upload names it (`blobNamedBy`); an open breaker or unregistered backend is skipped (a note). Erased with the account, excluded from the export
- `object_locks` — Object Lock / WORM retention and legal holds
- `account_exports` — the GDPR export (WP-R10-3b, 075): `pending` → the `account_export` job streams one JSON document (`internal/api/account_export_sections.go`, keyset-paged, never a secret column — `TestExportSectionsCoverSchema`) through `generatedObjectWriter` into the tenant's **system bucket `_exports`** (a `buckets` row whose name no S3 bucket name can take; to the S3 API it does not exist except GetObject/HeadObject of its keys; hidden from every listing, count and dashboard page; never versioned or lock-enabled; written even over quota, audited) → `completed` with `file_path`/`etag`/`expires_at = +7 d`; `GET /api/v1/manage/account/export/{id}` and the dashboard mint a 1 h presigned GET on the tenant's primary pair; 410 after expiry; three failed attempts = `failed`; one pending per user (partial unique index). Erased with the account (rows by user, the object by the runner's walk)
- `idempotency_cache` — management API idempotency keys (24h TTL)
- `webhook_outbox` — the webhook outbox (095, WP-R11-3): one row per (event, endpoint), written where the delivery pool job is enqueued (the job is attempt 1; `next_attempt_at` = a 15 min lease while an attempt is queued or running). Each finished attempt moves the row in the statement that writes its `webhook_deliveries` row (`retry_count` = the attempt's place, `next_retry_at`): 2xx → `delivered`, else due again after 1/5/25/125 s (±20 %), the fifth failure → `failed`; an attempt the pool dropped is due 30 s later with no attempt spent; a disabled/deleted endpoint → `skipped`. The `webhook_retry` job (30 s, `FOR UPDATE SKIP LOCKED`) hands due rows back to the same pool. Signature `X-Webhook-Signature: t=<unix>,v1=<hmac(t.body)>,sha256=<legacy hmac(body)>`; `POST /api/v1/webhooks/{id}/rotate-secret`. Terminal rows kept 30 d (retention), erased with the account, excluded from the export. `vaultaire_webhook_retries_total{outcome}`
- `sts_tokens` — STS temporary credentials (ASIA-prefixed, scope-intersected, hourly cleanup)
- `stripe_events` — webhook event dedup
- `dashboard_sessions` — PostgreSQL-backed sessions with IP/user-agent tracking
- `oauth_accounts` — OAuth provider links (Google, GitHub)
- `smart_demotions` — Smart-tier demotion ledger (5.15.8): one row per hot→cold move, hot copy reclaimed after a grace period under an etag guard; read-time promotion state (063)
- `vault_parity` — the Vault parity second copy (077, WP-VAULT-1, flag `vault_parity` default OFF in code; on prod a global row turns it ON for every tenant, Sync first): one row per vault-floor object, bound to the etag its shards were computed from. RS 4+4 over the object (`internal/api/vault_parity_codec.go`, 1 MiB per shard per stripe): the four data shards are NOT stored (tape holds them), the four parity shards go to the first registered leg in the order `sync` → `permafrost` → `lyve` (`VAULT_PARITY_LEGS` overrides; Sync since 2026-10-07, #629) as `<tenant>__parity/<digest>/<etag>/p<j>` by the `vault_parity` job (every 2 min, registered only with a leg). Any four of the eight shards rebuild the object, so the parity alone is a complete copy: a GET of a vault object whose backend fails (error, not found through the failover chain, open breaker — never `ErrArchived`, which keeps the restore semantics) is rebuilt from the parity (`x-vaultaire-served-from: parity`), and from the data ranges Geyser can still serve when a parity shard is gone too. `state` = `complete` | `partial` (which shards landed, `last_error`, retried up to 20 attempts); the `legs` of a partial row are the INTENDED leg of every shard, recorded before the first byte; an overwrite or delete makes the row stale and the job erases the shards; DeleteObject and every key of DeleteObjects erase them at once (best effort, one shared aftermath — `internal/api/object_delete_shared.go`); the job never rewrites a row whose shards it could not erase first (skipped that run) and erases what it wrote when the row went meanwhile; **shards no row names** (a row gone during the write, a failed shard delete, a failed clear of a prior etag) are found by the job's **reconcile pass** (081, `vault_parity_orphans`, Prompt 2a PR 5): it runs at most every `VAULT_PARITY_RECONCILE_EVERY` (30 min, Prompt 2a.2 G3) in its own slice of the run (10 min) — FIRST, before the stale and protect passes (Prompt 2b 0.1: run last, it was starved by a protect that overran into its slice); a protect is started only when its size estimate (`VAULT_PARITY_PROTECT_RATE`, 20 MB/s, + 30 s) fits before the run's deadline, so nothing started is cut, and one estimated longer than a whole run is never started (`too_large`, a note), walks `<tenant>__parity/` folder by folder on every registered leg whose breaker is closed (permafrost through `ListDir`; legs skipped are named in `skipped_legs`) within a listing budget (1,000 per leg per run), resumes from a `{tenant, digest}` cursor persisted in `job_runs.result` (a deploy no longer restarts it), and a walk cut by the budget, the slice or `MaxRunTime` is a note (`reconcile_stopped`), never a failed run, a `<digest>/<etag>/` folder no row names **on that leg** (`shard_prefix` + the leg in its `legs`; Prompt 2a.3 H1) is a candidate, and one holding files is erased — files, then the empty folders — only once it has been one on two passes at least `VAULT_PARITY_ORPHAN_GRACE` (1 h) apart (a row is inserted before the first shard byte, so a real write always has its row; one Sync bridge's stale listing cannot cost a shard); a candidate that gains its row is forgotten; an empty `<etag>` folder no row names goes at its first sighting; **folders are removed only by the reconcile, under the job lock** — the stale pass, DeleteObject/DeleteObjects, overwrites and the account erasure delete shards, then the row (on its own 5 s deadline once the shards are provably gone), never a folder (Prompt 2a.3 H1: up to 11 Sync calls inside a DELETE's post-commit budget left `complete` rows naming no shard); a `complete` row is made `partial` (attempts reset) BEFORE its first shard delete, so a delete stopped mid-shards (a leg 5xx, the budget) is re-protected by a same-content re-upload instead of staying `complete` with shards missing (Prompt 2b 0.2); on the multi-bridge Sync driver a folder is removed only when EVERY bridge lists it empty, then by ONE collection DELETE (a collection DELETE is recursive and one lagging bridge's empty view used to wipe the folder) — what makes that safe is that only the job writes shards and only the job removes folders, under one lock; the permafrost fleet removes a folder empty on every account the same way (`OneDriveDriver.RemoveEmptyDir`); `orphans_found` (new sightings only) / `orphans_erased` (counted once) / `orphans_failed`, `orphan_folders_removed`, `reconcile_listings` in the job result, `vaultaire_vault_parity_orphans_total{outcome}`; an unregistered leg or an open breaker is skipped, never a failed run; an account erasure erases every row's shards before the sweep and defers the tenant when the leg is not registered or its breaker is open. A chunked object is never vault-floor (asserted, not handled)
- `packs`, `pack_members` — the pack store (080, `internal/packstore`, Phase 37): small immutable objects batched into content-addressed `<aa>/<sha256>.pack` files on a slow per-file backend (`sync`); `pack_members` is tenant data (erased by `account.EraseRows`; `pack_gc` rewrites a pack whose rows were erased), `packs` is infrastructure. Excluded from the export and the sweep's bucket sources
- `tenant_key_versions` — the tenant keys (084, WP-R8-1): per (tenant, version) a RANDOM chunk key and the ML-KEM-768 seed, wrapped under `ENCRYPTION_MASTER_KEY` (AES-256-GCM, AAD tenant‖version‖purpose); the newest version encrypts, every blob records its own (`global_content_index.encryption_key_version`, `object_head_cache.encryption_key_version`, the SSE-S3 header — format 0x03 since WP-R8-5: sealed and opened as it streams, 1 MiB segments, no size limit, `internal/crypto/stream.go`; 0x01/0x02 blobs still open) and is opened under it. Rotate = `POST /api/v1/admin/tenants/{id}/encryption-key/rotate`; the `key_reencrypt` job moves chunks to the new version (old addresses kept 1 h in `retired_chunk_blobs`; a chunked GET whose resolved address is gone re-reads the row once — WP-R8-1 A2); then whole SSE-S3 objects — head rows AND retained versions — within the same per-run budget (WP-R2-1 C2, `key_reencrypt_whole.go`): re-sealed at a NEW address on the same backend, every row naming the old address at the old version re-pointed in one transaction (ETag unchanged), the old address retired as `reencrypted` in `retired_blobs`; tape-backend, open-demotion, `vault_parity` and `_exports` objects are skipped and stay pending (`kind="whole"` of `vaultaire_key_rotation_pending` counts blobs, so it never reaches 0 while they exist). ## Architecture Decisions (Non-Negotiable)

1. **Authenticated health probes, TCP dial as fallback** — unauthenticated HTTP checks against S3 backends are unreliable (EOF, 403 vary by vendor), so never probe with a bare GET. Backends with a driver are probed with a *signed* HeadBucket (iDrive, Geyser) or the Lyve console action (root key); anything else gets a backend-agnostic TCP dial. Signed probes are what catch a dead key (`internal/api/backend_probes.go`). Every S3-class probe (idrive, idrive-<region>, wasabi, lyve, r2, s3compat) also HEADs the canary object `t-_probe/_probe/<hostname>` (reserved tenant `_probe`, written when absent; never on Geyser or permafrost — `internal/api/backend_canary.go`): a key that sees the bucket but not its objects passed HeadBucket for 9+ h on 2026-10-11. `/health` is `degraded` with a `reason` while the primary's breaker is open (`vaultaire_primary_backend`; Prompt 2b.5 F2).
2. **HEAD serves from `object_head_cache`** — never fetches from backend. Size/ETag/content-type stored on PUT, queried on HEAD (~1ms). One exception: an object that REPORTS an archive class (a `vault`-floor object on Geyser) gets its live `x-amz-restore` state from the backend; a Smart-demoted `standard`-floor object reports STANDARD and makes no call (WP-R13-1).
3. **ETags computed via MD5 stream on upload** — never return MD5 of empty string.
4. **Always stream, never buffer** — use `io.Reader`, never `[]byte` in memory for large data.
5. **Always propagate context** — every service method takes `ctx context.Context` as first parameter.
6. **Always wrap errors with context** — `return fmt.Errorf("create bucket %s: %w", name, err)`
7. **Client IP comes from `internal/clientip` only** — HAProxy appends the real peer as the *last* `X-Forwarded-For` entry; `CF-Connecting-IP` is trusted only behind a Cloudflare edge. Reading those headers anywhere else reopened an API-key IP-allowlist bypass (review R1-01). Shutdown order is fixed too: HTTP drain, the wait for detached long S3 operations (≤ 15 min from each one's start, `internal/api/s3_long_op.go`), tracker flush, then engine (which closes the DB) — `cmd/vaultaire/main.go`; `vaultaire-switch` polls `long_ops_in_flight` on the old slot's `/health` before it stops it.

## Development Methodology

- **TDD is mandatory**: Red -> Green -> Refactor. Write failing test first.
- Tests follow Arrange/Act/Assert pattern with testify (`require` for fatal, `assert` for non-fatal).
- Pre-commit hooks run `go fmt` and `make lint` (CI's pinned golangci-lint through `go run` — first run ~40 s to build it on a cold cache, then ~3 s; RP20-3) on commit; `go test ./... -short` runs on **push** (`pre-commit install && pre-commit install --hook-type pre-push`).

## Git Workflow

```bash
git checkout -b phase-X.Y-feature-name  # Branch from main
# ... TDD cycle ...
git commit -m "feat(scope): description [Phase X]"
git push origin phase-X.Y-feature-name
gh pr create --base main
# Wait for CI (build-and-test) to pass, then:
gh pr merge --squash --delete-branch
```

Commit format: `type(scope): description [Phase NNN]` where type is feat/fix/refactor/test/docs.

Never include `Co-Authored-By` lines mentioning Claude or AI in commit messages.

Branch protection: direct pushes to main are blocked; CI must pass before merge.

**Never use `--admin` to bypass CI.** Wait for `build-and-test` to pass. If CI fails, fix the issue on the branch and push again.
