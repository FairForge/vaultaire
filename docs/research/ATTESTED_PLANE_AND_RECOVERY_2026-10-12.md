## 1. What the reference systems actually do

| System | Hardware | Recovery policy | Operator lock-out | Verifiability | Takeaway for us |
|---|---|---|---|---|---|
| **Apple Private Cloud Compute** | Apple silicon servers, Secure Enclave, measured boot | — | "No privileged runtime access": a small audited command set, no shell; stateless — the data-volume key is generated in the enclave at every boot and never stored | Every production image in a public append-only log; the phone refuses a node whose measurement is not listed; images and a Virtual Research Environment published; OHTTP relay for non-targetability | Published measurement the client enforces; boot-fresh data key so a copied disk is worthless. Non-targetability is a fleet property — not ours to claim |
| **Apple iCloud Keychain escrow** | HSM clusters | Passcode checked with SRP (never leaves the device), each HSM counts attempts independently, release on majority, **10 attempts then the record is destroyed**; the HSM admin cards were physically destroyed | Policy in HSM firmware the operator can no longer change | — | The mainstream recovery precedent: passcode, not paper; destroy-after-N |
| **Signal SVR3** (OSDI '24) | SGX + AWS Nitro + AMD SEV-SNP, different clouds | PIN behind a Ristretto OPRF; secret shared across three enclave types; attempt counter in an in-memory Raft (no disk to roll back) | An attacker must break every hardware model | Enclave code open (AGPL, C++ enclave + Go host); SEV-SNP build ships as a whole measured VM image | **One operator's enclave is not enough** — a snapshot restore resets the counter |
| **WhatsApp Backup Key Vault** | HSM fleet, multi-datacenter, majority-consensus replication | OPAQUE; limited attempts, then the key is permanently inaccessible | Keys inaccessible to Meta and cloud providers | 2026: fleet public keys ship in a bundle **signed by Cloudflare and counter-signed by Meta; Cloudflare keeps an audit log**; deployment evidence published per fleet | The external-witness pattern for our transparency log |
| **Juicebox** (ePrint 2025/348) | "commodity hardware or secure hardware" realms | OPRF + secret sharing + self-destructing record; PIN-sized secret; realms across organisations | No single operator trusted | Open source: MIT SDK (Swift / Android / JS bindings, active 2026), AGPL Go software realm + Rust HSM realm (quiet since 2024) | The protocol and client for F-19; we run the realm inside the measured VM |

## 2. The EPYC box: the stack

- **Hardware.** EPYC Milan or newer. BIOS must allow SMEE, SEV control, the RMP table, an SEV-ES ASID limit above 1 and SEV-SNP (all off by default) — so the vendor must expose the BIOS. Verify on the live image before paying: `/sys/module/kvm_amd/parameters/sev_snp` = `Y`, `cpuid -1 -l 0x8000001f` shows SNP. The prod Ryzen 9 9950X has no SEV-SNP (consumer parts never do; only an fTPM).
- **Host.** Stock Ubuntu: host-side SEV-SNP (QEMU + the AMD OVMF build) since 25.04; the SLC box runs 26.04. No custom kernel.
- **Guest.** QEMU `-object sev-snp-guest,...,kernel-hashes=on` with `-kernel`/`-initrd`/`-append`, `-cpu EPYC-v4`, vCPU count pinned — kernel, initramfs and command line are in the launch measurement, and any change to those inputs moves it. Reproducible image (Phase 15.5), dm-verity root, **no ssh, no shell in the initramfs** (the hypervisor can inject terminal input). The data disk's LUKS key is released only against an attestation report whose report-data field carries a fresh guest-generated public key, so a copied disk never decrypts outside the measured image.
- **Attestation and key release.** `snpguest report` inside the guest; verification against AMD's ARK → ASK → VCEK chain (`snpguest verify`, or Google's go-sev-guest). **Trustee** (Confidential Containers: KBS + Attestation Service + Reference Value Provider; Apache-2; docker-compose, Kubernetes optional) runs on the *other* box; its release policy is the published measurement; measurement and policy go into the transparency log and are served at `/.well-known/attestation`.
- **What runs inside.** Vaultaire + Postgres + keys; TLS for `s3.stored.cloud` terminated inside the guest; our half of the recovery realm (Juicebox).
- **The second realm.** A small rented confidential VM or Nitro enclave under another operator, threshold 2-of-2 (a third later). Without it the attempt counter is only as strong as our willingness not to restore a snapshot.

## 3. The master key install (facts verified 2026-10-12)

- `systemd-creds encrypt --with-key=host+tpm2` is the default when a TPM exists and `/var` is persistent: decryption needs the TPM **and** the OS install, so a copied credential is useless off the box. Default = no PCR binding; the signed-PCR-policy path assumes unified kernel images on PCR 11 (not Ubuntu Server's boot); v262 additionally pins to the SRK. The credential directory is "restricted to the service's user" — hence the dedicated service user, since `user1` is the deploy identity.
- The code side shipped in #685: `$CREDENTIALS_DIRECTORY/encryption_master_key`, `ENCRYPTION_MASTER_KEY_FILE` for labs, the env var last.
- Escrow tooling: **age-plugin-sss** v0.4.0 (Shamir over age recipients, nested policies, hybrid-PQ labels; "experimental until 1.0"), **age-plugin-yubikey**, **age-plugin-tpm** 1.0.1 (packaged in Debian/Arch 2026). Test the decrypt path during the ceremony.
- faulTPM extracts AMD fTPM secrets with hours of physical access (shown on Zen 2/3; nothing published for Zen 5); `host+tpm2` still needs the OS secret.
- Follow-up: a TPM-resident KEK (tink-go-tpm pattern) so no exportable master exists; TPM ops run at single digits per second, fine behind the one-hour tenant-key cache.

## 4. SSE-C: what we may say

With an "SSE-C required" bucket: *"We never store your key and cannot decrypt your stored data."* True for everything at rest. Caveats the copy carries: the key passes through our servers on every request (a modified server could capture it from that point on — a visible measurement change once 41.4 exists); the key is plaintext inside the edge provider while TLS terminates there (hence a direct `s3` host, F-17b); names, sizes, timestamps and access logs stay plaintext. Ranking for an S3 customer, strongest first: client-side tools (restic, rclone crypt — no key ever reaches us, names encrypted) → SSE-C on a direct attested host → SSE-C through the edge → Standard. Guard-rails in WP-SSEC-1: the key in no log and no stored key-MD5; never a bucket default; TLS at the origin.

## 5. Züs / 0chain — reviewed, not adopted

- **Network state (2026-10-12):** the registry lists 14 miners and 6 sharders across 10 domains; the foundation's `0chain.net` miners/sharders do not resolve; the one responsive third-party sharder reports its latest finalized block at 2026-08-07; ZCN ≈ $0.0013, market cap ≈ $200k, 24 h volume ≈ $5 on one DEX pair. GitHub still commits (SDK Sep 2026, a new "AI data acceleration" repo 2026-10-11). No third-party audit found. The S3 gateway is a MinIO-gateway fork with no releases.
- **The shipped proxy re-encryption (`gosdk/zboxcore/encryption/pre.go`):** custom tag-based PRE over edwards25519 (kyber), AES-GCM with key and nonce both sliced from one SHA-512 of a random point, private key straight from the mnemonic with no salt or KDF, an unkeyed SHA-512 of the plaintext stored in the clear (a confirmation oracle), the proxy given the value that verifies the integrity tag, no domain separation, a probable in-place-encryption bug, an unchecked slice. No paper cited in code, no audit. Ente's sealed-box sharing needs no PRE at all.
- **Worth taking:** the Broken-Ecosystem test matrix (§6); the warning that a challenge proving a block can be *produced* proves nothing about where it is held; the warning that token-paid storage loses its providers with the token; the lesson that breadth without a trusted core is how a network stops while its repos keep moving.

## 6. The Broken-Ecosystem matrix (CCS 2024) as our 10.7 test set

Hofmann & Truong (ETH Zurich) under a malicious-server model: (1) unauthenticated key material, (2) unauthenticated public keys, (3) protocol downgrade, (4) link-sharing leakage, (5) unauthenticated encryption modes, (6) unauthenticated chunking, (7) filename/location tampering, (8) metadata tampering, (9) folder/file injection. Sync, pCloud, Seafile and Icedrive broke; Tresorit only partially analysed; Ente not studied. Each becomes a test against our own server acting maliciously before the privacy page may cite the paper.
