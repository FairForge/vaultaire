# WP-R13-3 — one scheduler, persisted, observable

**Built 2026-10-01 on `wp/R13-3-job-scheduler` (PR #543), from `main` @ #542.**
**Findings closed:** R13-07 (the daily tickers never fire on a box that is redeployed daily),
R13-11 (no background job emits a metric), R13-23 (inventory's hour-0 gate and shared
deadline), the rule the WP-R10-3 note owed (`AccountDeletionDeferred`), the async half of
WP-R11-8, SYNTHESIS table A row WP-R13-3. With WP-R13-1 (#542) this closes both gates in front
of the `smart_demotion` flag; the flag itself is still OFF for every tenant.
**No migration** (`job_runs` is 071; next is still 074).

**One deviation from the brief, at the top because a reviewer will look for the series:**
the label is **`job_name`**, not `job` — `vaultaire_job_last_success_timestamp_seconds{job_name}`
and `vaultaire_job_runs_total{job_name,outcome}`. `job` is the label Prometheus itself puts on
every scraped series (prod's scrape config: `job_name: vaultaire`, `honor_labels` unset), and a
scraped series that brings its own `job` is stored as `exported_job`. `JobStale` written on
`{job="retention"}` would have matched nothing: a staleness rule that can never fire, and that
a test against the app's own `/metrics` cannot catch. The rule test now refuses any `vaultaire_*`
series carrying a `job` label and any rule selecting on one.

## What was built

### A. The scheduler — `internal/api/jobs.go`

| Piece | Where |
|---|---|
| `jobSpec`: a job is **daily** (`Hour`/`Minute` UTC) or an **interval** job (`Every`); `BootDelay`, `MaxRunTime`, `Run(ctx) (jobReport, error)` | `jobs.go` `jobSpec` |
| Daily: a catch-up check `BootDelay` after start, then one check per hour (`jobRecheck`); a run happens when `job_runs.last_success_at` is NULL or older than the most recent HH:MM | `loop`, `tick`, `due`, `lastScheduled` |
| Interval: one run `BootDelay` after start, then one per `Every` (the hourly cleanups used to wait a full hour after every start) | `loop` |
| ONE advisory lock per job: `pg_try_advisory_lock(jobLockKey(name))`, session-level on a dedicated connection, released on close. The scheduler's check, an admin trigger, a dry run and a second process all meet it; the loser gets `errJobAlreadyRunning`, never a queue | `acquire`, `jobLockKey` |
| `job_runs`: `running` + `last_started_at` at the start; outcome, rows, text and — on `ok` — `last_success_at` at the end, written on its own short context (the run's may be cancelled) as an **upsert** | `recordJobStart`, `recordJobFinish` |
| Outcomes: `ok` (per-item failures are a **note** in `last_error`), `error` (the run itself failed; `last_success_at` stays put; a daily job is retried at the next hourly check), `interrupted` (the scheduler's context was cancelled: a deploy) | `execute` |
| A panic in a job is an `error`, not a crash of the server | `execute` |
| A row a dead process left `running` is closed as `interrupted` at the next start, under the job's lock (a row that is `running` while its lock is held belongs to a live run and is left alone) | `markInterrupted` |
| `RunNow` (wait for it), `StartDetached` (take the lock now, run on the server's context), `WithLock` (hold the lock, record nothing — the dry run) | same file |
| `vaultaire_job_runs_total{job_name,outcome}` — every outcome starts at 0 when the job is registered, so the first failure after a restart is an increase | `jobRuns`, `Register` |
| `vaultaire_job_last_success_timestamp_seconds{job_name}` — a collector that **reads `job_runs`** (15 s cache; a failed read keeps the previous values and is itself cached, so a database outage cannot stack scrapes; nothing exported until the first good read; 0 = registered and never succeeded) | `jobsCollector`, `lastSuccesses` |

### B. The job table — `internal/api/jobs_wiring.go`

Every loop of R13's job table, rebuilt. "Fails" = what makes a run `error` (a daily job is then
retried every hour until it succeeds). Everything from `inventory` to `access_log_delivery`
runs under the scheduler: lock, `job_runs`, `vaultaire_job_runs_total`, last success.

| Job | Schedule (UTC) | Boot | Ceiling | A run fails when | Does not fail it (a note; next run's work) | Before this WP |
|---|---|---|---|---|---|---|
| `inventory` | daily 00:30 | +4 m | 6 h, **30 min per report** | the configuration list cannot be read | a report that could not be written (target gone, over quota, its deadline) | hourly tick acting only when `now.Hour()==0`; one 5-min deadline for every tenant; no metric |
| `dedup_gc` | daily 02:30 | +3 m | 2 h | the reconcile statement or the candidate scan fails; the ceiling | a chunk that could not be swept (`failed` in the result) | 24 h ticker, no boot run: **never ran unattended**; no metric |
| `retention` | daily 03:30 | +1 m | 10 m | any table could not be pruned | — | same schedule; lock, `job_runs` and schedule code its own copy; a gauge that read 0 after a restart |
| `account_deletion` | daily 04:30 | +2 m | 6 h (2 h per tenant) | a tenant was **deferred** (Stripe, a backend) — on purpose: the erasure is owed | a cancelled tenant | same; second copy of the schedule code; same gauge |
| `smart_demotion` | daily 06:30 | +5 m | 6 h | the tenant list or the day's ledger cannot be read; a backend is no longer registered | an object that could not be demoted, reclaimed or promoted; a tenant whose plan failed; reaching the ceiling | 24 h ticker, no boot run: **never ran unattended**; no metric. Registered only when the hot AND the cold backend are |
| `multipart_reaper` | every 1 h | +10 s | 30 m | a pass cannot list its rows | one upload that could not be aborted/purged | boot + hourly, no metric |
| `cdn_rollup` | every 1 h | +20 s | 5 m | the upsert fails | — | boot + hourly, error logged, no metric |
| `idempotency_cleanup` | every 1 h | +30 s | 5 m | the DELETE fails | — | first run an hour after start; **error discarded** |
| `sts_cleanup` | every 1 h | +30 s | 5 m | the DELETE fails | — | first run an hour after start |
| `session_cleanup` | every 1 h | +30 s | 5 m | the DELETE fails | — | first run an hour after start; **error discarded** |
| `bandwidth_alerts` | every 1 h | +40 s | 30 m | the candidate list cannot be read | a tenant whose check or e-mail failed (retried next pass, R13-09) | boot + hourly, no metric |
| `access_log_delivery` | every 5 m | +1 m | 2 m (60 s per pass) | the bucket list cannot be read | a bucket whose rows could not be delivered (kept) | 5-min ticker, no metric |

Not jobs of the scheduler (unchanged; each has its own series or none is needed):

| Loop | Trigger | Metrics | Note |
|---|---|---|---|
| Flag cache refresh | 15 s | none | keeps the last snapshot on failure |
| Bandwidth / CDN-analytics / access-log flushers, site stats | 5 s / 100 events; 30 s | none | flushed synchronously at `Shutdown` |
| Backend health loops, cert monitor | 30 s / hourly | `vaultaire_backend_*`, `vaultaire_tls_cert_*` | |
| Synthetic customer check | `SYNTHETIC_CHECK_INTERVAL` | `vaultaire_synthetic_check_*` | |
| Read-time promotion (copy-back) | per GET of a demoted object | `vaultaire_smart_restore_waits_total` (WP-R13-1) | the daily job's `PromotePending` retries leftovers |
| House price verification | boot + hourly | none | keeps checkout closed on mismatch |
| **Metered reporter** | boot + hourly, **daily report at hour 0** | none | **the one hour-0 gate left.** Dormant on prod (both `STRIPE_METER_*` unset). It must move onto the scheduler before the meters are switched on (WP-R10-4): a restart during hour 0 would skip or repeat a day's usage report. Comment added in `billing/metered.go` |
| Webhook dispatch, engine `RecordLocation` | goroutine per event / per PUT | none | WP-R11-3, WP-R6-1 |

**Run times.** An hour apart, so the short jobs never start together; `inventory` first (the
report is dated the new day), `retention` right after the 03:00 database backup,
`smart_demotion` last and at night in the Americas because it moves bytes across the box. A
long run (account deletion and demotion have 6 h ceilings) can still be in progress when the
next job starts; that is safe — they hold different locks and touch different rows (R13
invariant 6; a deletion walk and a demotion of the same object are both etag/row-guarded). At
boot the catch-ups are staggered by their `BootDelay` (1–5 min).

### C. The runners

- **Retention, account deletion** — moved onto the runner with no behaviour change: same
  times, same boot delays, same ceilings, same names in `job_runs`, a failed table / a deferred
  tenant still fails the run (`TestRetention_KeepsItsScheduleOnTheSharedRunner`,
  `TestAccountDeletionRunner_KeepsItsScheduleOnTheSharedRunner`). Their own lock, `job_runs`,
  `due`, `Start` and last-run-gauge code is deleted. The lock key is now
  `jobLockKey(name)` for every job (the two hard-coded keys are gone; no two binaries ever
  overlap on prod).
- **Dedup GC** — `sweepOne` reports `sweepDeleted` / `sweepKept` / `sweepBlobLeaked`; a chunk
  that could not be swept is counted in `DedupGCResult.Failed` instead of being only a log line.
- **Smart demotion** — `MaxBytesPerRun` is now a budget **per 24 hours**: the run reads what
  the ledger shows as demoted in the last day and only gets the rest (finding 1 below). A run
  that reaches its ceiling is `ok` with a note.
- **Inventory** — `RunOnce(ctx, day)`: the day comes from the schedule, not the wall clock; the
  report key carries that date; weekly reports belong to the run scheduled on a Sunday; each
  report has its own deadline (`ReportDeadline`, 30 min) and returns its error.
- **The hourly loops** — each became a function that returns its error (`cleanupExpired`,
  `auth.CleanupExpiredSTSTokens`, `DBStore.CleanupExpired`, `rollup`, `deliverLogs`,
  `checkBandwidthAlerts`), registered as an interval job.
- All loops start in `Server.Start` on the context `Shutdown` cancels (`NewServer` only
  registers). Six of them used to start in `NewServer` on `context.Background()`.

### D. Admin

- `GET /api/v1/admin/jobs` — every registered job joined with its `job_runs` row: schedule,
  running, last start / finish / success, outcome, error or note, rows, next run; a row no job
  of this process claims is listed with `registered: false`.
- `POST /api/v1/admin/jobs/{job}/run` — the generic trigger (it gives `inventory` and the
  interval jobs one). The four older routes (`dedup-gc`, `smart-demotion`, `retention`,
  `account-deletion`) are the same call. **202** `{"job":…,"status":"started","status_url":…}`
  as soon as the run holds the lock; it continues on the server's context — a closed tab or
  HAProxy's 50 s cannot cancel it (R13-08), a shutdown can. **409** `already_running`.
  `smart-demotion?dry_run=true` stays synchronous: under the job's lock (so it cannot describe
  a moving target), not recorded in `job_runs` (it must not count as the day's success).
  404 for an unknown job on the generic route, 503 on a named route whose job this process does
  not run, 400 for `dry_run` on any other job. One `admin.<job>` audit row per trigger.
- `quota-reconcile` is not a scheduled job: synchronous, its in-process gate kept.
- OpenAPI: both new operations, the four triggers re-documented (202/409), schemas `JobRun`,
  `JobStarted`, `JobAlreadyRunning`; the drift guard is green.
- **Dashboard buttons:** there are none — no admin page posts to a trigger (grep over
  `internal/dashboard`). The System page (`/admin/system`) gained a read-only **Background
  jobs** table from `job_runs`, so the state is visible without a JWT in hand.

| Rule | Expression | For |
|---|---|---|
| `JobStale` | `(time() - vaultaire_job_last_success_timestamp_seconds{job_name=~"inventory\|dedup_gc\|retention\|account_deletion\|smart_demotion"}) > 36 * 3600` | 30 m |
| `PeriodicJobStale` | the same on the seven interval jobs, `> 3 * 3600` | 30 m |
| `JobFailing` | `increase(vaultaire_job_runs_total{outcome="error"}[6h]) >= 3` | 0 m |
| `AccountDeletionDeferred` | `increase(vaultaire_account_deletion_tenants_total{result="deferred"}[2h]) > 0` | 0 m |

`RetentionJobStale` is gone from `vaultaire-synthetic.yml`: it is `JobStale{job_name="retention"}`.
`job_rules_test.go` builds the production job table and checks that every registered job is
named in exactly one staleness rule, that the rules name no job that does not exist, that every
series the file reads is on `/metrics` right after a start, and that no rule selects on `job`.
README updated.

## Tests

**Red first:** the trap test (above); `TestRetention_*` and `TestAccountDeletionRunner_*` were
adapted before the runner code compiled. **Not red first:** `jobs_test.go` was written right
after the first draft of `jobs.go`, and `jobs_runners_test.go` after the runners were moved.
For those, two were checked the other way round — the behaviour was removed from the code and
the test run: `TestSmartDemotionJob_AnObjectThatCannotMoveIsANoteNotAFailedRun` fails with
`expected "ok", actual "error"` when a per-object failure fails the run, and
`TestSmartDemotion_ByteBudgetIsPerDayNotPerRun` fails (`expected 0, actual 2`) without the
24-hour budget.

`jobs_test.go` (own job name per test): daily due / catch-up arithmetic; a run records start,
finish, success and counts; per-item failures are a note and the job is not re-run at the next
check; an error keeps `last_success_at` and is retried until it works; a panic is an error; one
run at a time in-process **and** against a second session holding the lock (the scheduler's
check, `StartDetached` and `WithLock` are all refused); `WithLock` records nothing;
**killed mid-run → the next boot says `interrupted` and runs it again**; a stale `running` row
of a job that is not due is closed too, and one whose lock is held is left alone; a shutdown
during a run is `interrupted`, not `error`; a deadline is an error; an interval job runs after
boot and on every tick and stops with its context; a daily job that already ran today is not
run at boot; a detached run survives the request; the finish row is written even when the
start row is missing; **the last-success series after a restart** (the trap, on the new
series: equals `job_runs`, 0 for a job that never succeeded, the old gauges absent, a run in
this process visible on the next scrape); a failed read keeps the previous values; lock keys
are distinct.

`jobs_runners_test.go`: demotion — an object that cannot move is a note, the run is `ok` and
not repeated; the byte budget is per day; a failed tenant list is an error. GC — a blob the
backend will not delete is a note. Inventory — scheduled by `job_runs` at 14:00 after a missed
00:30, one report dated the scheduled day, a second restart the same day writes nothing more,
the next day writes the next; weekly only on the Sunday run; one failing report does not fail
the run; per-report deadline. `TestRegisterJobs_EveryLoopIsAJobAndDailyTimesDoNotCollide` pins
the table (names, schedules, a ceiling and a boot delay for each, no two daily jobs at the same
time, no demotion job without the cold backend). Admin — the list; 202 / 409 / dry run
synchronous and unrecorded / 404 / 503 / 400.

`job_rules_test.go` (above); `retention_test.go` and `deletion_runner_test.go` now use their
own job names and the retention fixture prunes only its own tenant's rows (it used to delete
every package's old rows on the shared database, one row per statement);
`admin_system_test.go` — the jobs table.

`make test-db`, `go test -race ./...` against `vaultaire_test`: every package ok. `make lint`:
0 issues. `make gosec`: 0 issues.

## Adversarial pass — what it found in my own code

1. **The byte budget was per run, and this WP makes runs repeat — fixed.** A deploy in the
   middle of a demotion run leaves no success for the day; the next boot's catch-up runs the
   job again, with a fresh 500 GiB. Ten deploys a day made a daily transit budget an
   every-restart one. The budget is now read from the ledger over 24 hours
   (`TestSmartDemotion_ByteBudgetIsPerDayNotPerRun`). An undercount is possible (a row whose
   object was promoted since is gone from the ledger), never an overcount.
2. **The label `job` — fixed** (top of this note).
3. **A lost start row made a daily job hourly — fixed.** `recordJobFinish` was an `UPDATE`:
   when the start `INSERT` failed (a database blip), the finish updated nothing, the job had
   "never succeeded" and ran at every hourly check. It is an upsert now
   (`TestJob_FinishRecordsTheSuccessEvenWhenTheStartRowIsMissing`).
4. **A run killed by a deploy.** What `job_runs` says: `running`, forever, when the process
   dies before the finish write (it has about 30 s of drain to write `interrupted` itself — the
   scheduler's context is cancelled first). What the next boot does: closes the row as
   `interrupted` under the job's lock, **at once** (first draft: after the job's boot delay —
   up to five minutes of a "running" job that was not), then runs the job again if the day has
   no success. If the day already had one (a manual second run was the one killed) the row is
   still closed — the first draft only closed it when the job ran again, i.e. tomorrow.
5. **Per-job, what repeats.** A daily job that returned `error` for one bad object would re-run
   the whole job every hour until the object could move. Decided per job (the table above) and
   tested for demotion, GC and inventory.
6. **A scrape during a database outage** would wait out the 2 s query timeout behind the
   collector's mutex, one scrape after another. The failed read is cached for the TTL like a
   good one, and the previous values are kept (never a 0, which reads as "never succeeded").
7. **A counter that first appears at 1.** `increase()` cannot see a series born at 1 after a
   restart, and this box restarts ten times a day. Every outcome of every job, and every result
   of `vaultaire_account_deletion_tenants_total`, is created at 0 at registration.
8. **Ticker vs trigger vs a second process:** one lock; the tests take it from another session.
   The dry run takes it too. Not closed: if the lock's connection is reset mid-run the session
   lock is gone and an admin trigger could start a second run (the scheduler's own loop cannot:
   it is the goroutine that is running). The jobs' writes are individually guarded (etag-guarded
   flips, per-chunk locks, idempotent deletes), so it costs work, not data.
9. **A sentence that said "always":** "every run is recorded" — the dry run is not, on purpose.
   "Every job runs on every server" — smart demotion is not registered without both backends
   (it would fail hourly and read as stale forever on a dev or CI build); it then exports no
   series.
10. **What every gauge and rule reads right after a restart.** `…last_success…{job_name}`: the
    database's value at the first scrape (A1 in the live proof), 0 for a job that has never
    succeeded — `JobStale` has `for: 30m` and the boot catch-up runs within 5 minutes.
    `…runs_total`: 0 for every job and outcome. `…account_deletion_tenants_total`: 0 for the
    three results once the runner is built in `Start`. The two last-run gauges: gone.
11. **The attacker.** The admin routes are JWT + admin; `{job}` is a map lookup. `/metrics`
    carries job names and no tenant label; the collector's query is bounded by the 15 s cache
    whoever scrapes.
12. **The other entry point:** the trigger and the scheduler call the same `spec.Run`; the four
    named routes are the generic one.
13. **A name registered twice** would have started a second loop on the same lock and row;
    the second registration returns the first job (`TestJobScheduler_ANameIsRegisteredOnce`).
14. **Seen on the way, not changed:** the metered reporter's hour-0 gate (table B); the
    host-routed CDN has no logging middleware (WP-R13-1 note); the global reads inside a
    demotion run (`reclaimHotCopies`, `PromotePending`, the day's budget) are not scoped per
    tenant in tests — only this package writes `smart_demotions`, and its fixtures clean up.

## Decisions taken

- Label `job_name` (above).
- Run times and boot delays (table B).
- Per job, what fails a run (table B).
- `MaxBytesPerRun` (`SMART_DEMOTION_MAX_GB_PER_RUN`) is a 24-hour budget.
- The old last-run gauges and the two per-job `*_runs_total` counters are removed, not seeded:
  one source (`job_runs`), one name per fact. No installed rule reads them.
- Smart demotion is a job only where both backends exist.
- All triggers are asynchronous (retention too: its ceiling is 10 minutes, HAProxy's is 50 s);
  results live in `job_runs` and the log, not in the response.
- A read-only jobs table on the dashboard's System page instead of buttons.
- Interval jobs take the lock and write `job_runs` like the daily ones (two small writes per
  run; `access_log_delivery` makes that 24 an hour).

## What is deliberately not done

- **The metered reporter** keeps its hour-0 gate (dormant; WP-R10-4).
- **Flushers, health loops, flag refresh** are not scheduler jobs.
- **Weekly inventory after a full Sunday of downtime** is skipped until the next Sunday (the
  day is the schedule's, and Monday's run is Monday's).
- **No history table.** `job_runs` is one row per job (the last run); the history is the log
  and the counters.
- **R13-06 / R13-10** (WP-R13-2) are untouched.

## What I could not prove

- **`promtool check rules`** is not installed here; the rule file is parsed by a Go test.
  The `exported_job` behaviour is Prometheus's documented default and prod's config was read,
  not exercised: no rule file was installed on the box.
- **A real SIGKILL in the middle of a long run** with the built binary: the runs of the local
  proof finish in milliseconds. A7 sets the rows a dead process leaves behind and boots the
  binary over them; the mid-run cancel itself is a test.
- **Demotion at prod scale over a day of deploys** (the 24-hour budget with real transit).
