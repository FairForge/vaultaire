## The problem

A demoted object has bytes on two backends until its hot copy is reclaimed, and on the cold
one afterwards. Everything that replaces or removes the object has to deal with the copy it
is *not* writing to — and nothing did:

| What the customer did | Before | Cost |
|---|---|---|
| Plain PUT over a demoted object | new bytes hot, head row rewritten, **old cold copy stays on tape** — nothing points at it, the reclaim closes the ledger as `kept_changed` and walks away | tape bytes billed to us per overwritten object (R13-10) |
| CopyObject / CompleteMultipartUpload onto a demoted key | same | same |
| PUT with an archive class over a demoted object inside the grace | their bytes land on the cold backend at the key; the old **hot** copy stays forever (`kept_changed` kept it as "live data") | paid hot storage |
| DELETE of a demoted object inside the grace | cold copy and head row go; the hot copy waits for a reclaim a day later — which then deletes at a key the customer may be uploading again | R13-06: the new upload can be destroyed |
| DELETE of the object while the demotion copy runs | the flip finds no row and **leaves the cold copy it just wrote** | tape bytes |

Reproduced first with two local drivers behind the real handlers (`smart_ledger_test.go`):
16 tests written before the code, all seen failing on `main` @ #546.

## The rule

One sentence decides every case: **a copy is stale when the key does not route to its
backend.** "Route" is the head row; a chunked row routes no whole blob anywhere; with no head
row, the newest live version behind a delete marker (its bytes are what `GET ?versionId`
still serves); otherwise nothing. A live whole-object row with no backend on record
(62 legacy rows in prod) is "unknown": nothing is deleted on its account.

The copy on the backend the key **does** route to is the customer's object — a PUT with an
archive class puts their bytes on the cold backend at that very key — and is never touched.

## What was built (`internal/api/smart_ledger.go`)

- **`ledgerSettler.settle`** — the rule applied to the copies a ledger row knows (the hot
  copy until reclaimed, the cold copy). Head row `FOR UPDATE`, then the ledger row
  `FOR UPDATE` (the order demote, flip-back and copy-back already use), both held across the
  deletes:
  - object still as the demotion left it (routes cold, same etag): nothing inside the grace;
    after it the hot copy is reclaimed (`deleted`) — today's behaviour;
  - object overwritten, moved, chunked or deleted: every copy on a backend the key does not
    route to is removed, the row closed `kept_changed` / `object_gone`, its pending
    promote/restore requests cleared;
  - a delete that fails leaves an open row open (`delete_failed`).
- **The reclaim** (`reclaimHotCopies`) is `settle` over two listings: open rows past the
  grace, and — new — reclaimed rows whose object is no longer the demoted one (an anti-join
  on the head row). The second is the retry for a cleanup that failed at the time or that a
  restart cut between the commit and the delete; without it a failed cold delete on a
  reclaimed row was never looked at again.
- **`dropDisplacedBlob`** — the ledger-free half, after every whole-object write: plain PUT,
  CopyObject, CompleteMultipartUpload and the generated reports (`background_put.go`). When
  the row the write replaced was on **another** backend than the one just written, its blob
  there is deleted — through that backend's driver, never `engine.Delete`, which falls back
  to the primary, where the new bytes are. The route is re-read first: if the key routes to
  the displaced backend again, the blob is another writer's. Same backend = overwritten in
  place, nothing to do. This is R8-20 for the plain path; it also covers a class change, a
  bucket made public and a failover write.
- **`SmartPromoter.OnDelete`** — after the hard-delete branch of `HandleDelete` and for every
  key of `DeleteObjects`: `settle` at once. One index lookup for a key that was never demoted.
- **Detection (`checkLostWrite`)**, after every stale-copy delete — see the next section.
- **A cancelled run** returns `ctx.Err()`: the reclaim and the pending promotions stop
  between two rows and list nothing they did not reach (before: every remaining row was
  `begin: context canceled`, and the run then failed on "read the day's demoted bytes").
  The demotion loop does the same for a move the stop cut.

## R13-06 — what is detected, and exactly which window remains

A PUT (or copy, or multipart complete) writes its bytes to the backend **before** its
head-row transaction. Between those two steps it is invisible to every lock: a delete of a
"stale" copy at the same key on the same backend removes the bytes that are about to become
the object. Nothing in this WP can prevent that; WP-R2-1 (write-new-key-then-swap) does.

Where a stale-copy delete can meet such a writer:

| Delete | Writer that loses | How likely now |
|---|---|---|
| reclaim, `object_gone` (hot copy of a deleted object) | a re-upload of the key | **only for leftovers**: DeleteObject now removes the hot copy itself, so the reclaim meets this only when that delete failed or the process stopped between the row delete and it. Before, every demoted object deleted inside the grace waited a day for it. |
| reclaim, `deleted` (hot copy of an unchanged demoted object, past the grace) | a plain PUT over the demoted object at that moment | as before (the "residual race" 5.15.8 documented) |
| reclaim / overwrite, cold copy of an object that moved hot | a PUT **with an archive class** of the same key at that moment | new delete, same class |
| `OnDelete` | the customer's own PUT racing their own DELETE of the key | their race; exists for any object today |

**Detection.** After the deletes and the commit, `checkLostWrite` takes the advisory key lock
every head-row writer holds for its transaction (`atomicHeadUpsertReleasing`) — so it waits
for a writer that was already committing — re-reads the row, and when the key now routes to a
backend the delete ran on, asks that backend whether the bytes are there (`Exists`). Missing →
`Error` log `stale copy: the delete of a stale copy removed a write of the same key that was
in flight` with tenant, bucket, key, backend and etag, and
`vaultaire_stale_copy_lost_writes_total{source="reclaim"|"delete"|"overwrite"}` (server
registry; all three series exist at 0 from boot). Bytes present → the write landed after the
delete: nothing is logged. Rule `StaleCopyLostWrite` (critical) in `vaultaire-jobs.yml`.

**The window that remains undetected:** a writer whose bytes landed on the backend before the
delete and whose head-row transaction had **not begun** when the check ran. The check runs
after the backend delete call and one commit; the writer's gap between its backend write
returning and its `BeginTx` holds no I/O (the measured-size and digest comparisons). So the
delete, the commit and the check must all fit inside that gap. That write is lost and not
logged. Everything wider than that is logged and counted; none of it is prevented.

## The other paths that displace a blob

| Path | Before | Now |
|---|---|---|
| Plain PUT onto a demoted key | cold copy leaked | removed (`dropDisplacedBlob`); reclaim closes the ledger |
| CopyObject onto a demoted key | cold copy leaked | removed |
| CompleteMultipartUpload onto a demoted key | cold copy leaked | removed |
| Chunked PUT onto a demoted key | cold copy removed (existing code); hot copy inside the grace leaked — `kept_changed` saw "routes hot" | the reclaim removes both (a chunked row routes no whole blob) |
| PUT with an archive class onto a demoted key | hot copy inside the grace leaked | reclaim removes the hot copy, keeps the cold blob (theirs) |
| DeleteObject / DeleteObjects inside the grace | hot copy waited for the reclaim | both copies removed in the request; ledger closed `object_gone` |
| DeleteObject on a versioning-enabled bucket (delete marker) | — | untouched by `OnDelete`; the reclaim keeps the copy the newest live version routes to (before: it deleted it — see adversarial 3) |
| Account-deletion walk | deletes the unreclaimed hot copy, then the recorded copy | unchanged — still does (`TestAccountDeletionRunner_ErasesEverythingOnce`, "the unreclaimed hot copy is gone too") |
| Generated reports (access logs, inventory) | displaced blob leaked on a tier change | removed |

## Adversarial pass — what it found in my own code and next to it

1. **A stale ledger row copied old bytes over a new object — silent corruption, fixed.**
   `promote` (the copy-back) read the cold copy and wrote it to the hot backend at the key
   *before* looking at the head row; the guarded flip then found the row changed, reported
   `changed`, and left the blob. Sequence: demoted and reclaimed → a read asks for the
   copy-back, the object is on tape, the request stays pending → the customer overwrites the
   key (new bytes hot; the cold copy leaked, R13-10) → the next daily run's `PromotePending`
   copies the **old** bytes over the new object. The row says the new etag and size; the
   blob is the old one. Reproduced (`TestPromotePending_StaleLedgerNeverCopiesOldBytesOverANewObject`,
   red on `main`). `promote` now reads the route first and settles a stale row instead of
   copying; `PromotePending` selects `hot_outcome = 'deleted'` only. Fixing R13-10 alone
   would have hidden this (the cold read would miss) without removing it.
2. **An overwritten object went back to tape the next morning — fixed.** The write upsert
   keeps the row's `created_at` and `last_accessed`, so a key created a month ago and
   rewritten today was "old and idle": the next run demoted the fresh bytes. For a backup
   job that rewrites `latest.tar` daily that is a tape write and a tape delete every day.
   MinAge now also requires `updated_at` (set by the write upserts only) to be older than
   the cutoff. Found because the reclaim test's object was re-demoted in the same run.
3. **`object_gone` deleted the bytes of a live version — fixed.** A bucket versioned after a
   demotion, the key overwritten (version v1, hot) and then deleted with a marker: no head
   row, so the reclaim removed the hot blob — the bytes `GET ?versionId=v1` serves. The
   route now includes the newest live version behind a marker.
4. **The object deleted during the demotion copy** left the cold copy just written
   (`qerr == nil && cur != cold` is false for no row). Fixed.
5. **The same etag twice.** A settled row kept its etag: a later object with the same
   content, stored with an archive class at the key, matched it on read and was "promoted"
   to hot — an attic object moved downstairs. `lookup` no longer returns settled rows; a new
   demotion resets the row including its pending requests.
6. **Flaky backend.** A stale delete that fails: the customer's request still succeeds, the
   Warn names the key, an open row stays open (`delete_failed`), and the daily pass retries
   both open rows and — second listing — reclaimed rows whose object changed. A missing blob
   is a success in every driver's shape (`isObjectMissingErr`); before, a missing hot blob
   on the local driver was `delete_failed` forever.
7. **Crash or deploy between two writes.** Commit of the overwrite, then the process dies
   before the displaced delete: the second listing finds the row the next day (if the object
   was demoted; a displaced blob with no ledger row — a class change — is an orphan until
   WP-R10-3c's sweep). Commit of the row delete, then death before `OnDelete`: the row is
   open or reclaimed-and-changed; both listings cover it.
8. **Two names, one store.** `dropDisplacedBlob` deletes on a backend by name; if two
   registered names were the same bucket it would delete the new bytes. `main.go` registers
   each backend once and skips `idrive-<default region>`; a name with no registered driver
   is skipped. Written into the function's comment as the invariant it relies on.
9. **"Never deletes a copy the key routes to" against the code path that returns first.**
   True under the row lock; a writer that has written and not committed is not "the route"
   yet — that is R13-06, and the reason the sentence in the code says "does route to".
10. **Tests on the shared database.** The reclaim listing was global: a run in one fixture
    settled other fixtures' rows with its own drivers (every delete a miss, the row closed).
    `scopeTenant` on the runner and the promoter confines every ledger pass and the day's
    byte budget to the fixture's tenant.

## Decisions taken

- **DeleteObject settles the ledger at once** (beyond the brief, which asked for detection
  only): it is what takes the reclaim's `object_gone` — the R13-06 case — from "every demoted
  object deleted inside the grace" to "the deletes that failed".
- `object_gone` removes the cold copy too (nothing routes anywhere).
- Settled rows stay as history (`kept_changed` / `object_gone`), they are not deleted: the
  24-hour byte budget reads them. They are invisible to the read path.
- Overwrites do **not** call `settle`: the displaced delete removes the copy, the daily pass
  closes the row. One less transaction on the PUT path.
- The lost-write rule pages (critical): it is a customer object.
- MinAge counts from the last write. The idle rule still reads `last_accessed` alone — an
  overwrite is a write, not a read; with MinAge on `updated_at` a rewritten key gets three
  days before that matters.

## Not done

- A flip-back (a GET inside the grace) racing a DELETE of the same key can leave the hot
  copy: the DELETE deleted on the backend it read before the flip, the flip removed the
  ledger row. Money, not data; WP-R10-3c's sweep reaches it at erasure.
- A displaced blob with no ledger row whose delete failed is not retried (no record of it).
- The chunked PUT path keeps its own stale-blob delete (`engine.Delete` with a hint).
- `GET ?versionId`, the delete-marker branch and `DELETE ?versionId` are untouched (WP-R2-1).
