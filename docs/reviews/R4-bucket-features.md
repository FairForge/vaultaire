## Versioning ledger consistency (item 3, given WP-R2-1)

Live cycle on `r4v`: Enabled → PUT v1 (3 B) → PUT v2 (12 B): `list-object-versions` shows v2 `IsLatest`, v1 not; DELETE → marker `IsLatest`, GET → 404 `NoSuchKey` + `x-amz-delete-marker`, v2 listing shows both versions non-latest; batch DELETE of the marker-latest key → `Deleted` (hard delete of the blob the undelete path needs, ledger untouched — WP-R3-4); Suspended → PUT → `null` version row `is_latest`, older rows demoted. `is_latest` maintenance on PUT/marker/version-delete is correct in every branch read (`recordObjectVersion`, `HandleDelete:1996-2050`); version listing merges `object_versions` with head-cache "null" versions, pages by `(key, created_at)` with `key-marker`/`version-id-marker` (ties on `created_at` would be skipped — theoretical). `GET ?versionId` of a non-current version → 501 (R2-03 stop-gap) confirmed at `s3_engine_adapter.go:262-278`. **Prod has 205,604 `object_versions` rows** (3 versioned buckets, bench data) describing bytes that do not exist. **WP-R2-1 ranking for R15:** it unblocks real version retention (R2-03), removes the in-place-overwrite corruption class on all three writers (R2-05, R2-15, R3-15), lets the delete marker keep AWS semantics on locked keys (R2-01 deviation) and makes Object Lock on versioned buckets mean what AWS means; it is the single largest correctness item left on the object path and should precede any "versioning" marketing copy. Size L; depends on nothing but the head-row upsert helpers that R3 centralised.

## Object Lock model (item 4)

COMPLIANCE vs GOVERNANCE and legal hold are enforced on PUT overwrite, single DELETE (every flavour), batch DELETE, multipart complete and copy (R3-01) through one `checkObjectLock`; `#442`'s `ObjectLocked → AccessDenied` mapping confirmed at all call sites (403 + "Object is protected by Object Lock."). Bypass = header only (R4-09). `applyObjectLockOnPut` runs after PUT, copy and multipart complete with the request's `x-amz-object-lock-mode`/`retain-until-date` or the bucket default — on CopyObject AWS applies the request's lock headers to the destination exactly this way (the source's retention is not copied) ✓. Retention extension-only and mode immutability for COMPLIANCE: **not enforced** (R4-01, fixed).
