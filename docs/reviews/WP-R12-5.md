# WP-R12-5 — session-bound CSRF

**Worker session, 2026-10-02. Branch `wp/r12-5-session-bound-csrf`.** Closes R12-19. No migration.

## The problem

`middleware/csrf.go` was a double-submit: a random `csrf_token` cookie, and a POST was valid
when the submitted value (form field or `X-CSRF-Token`) equalled the cookie. The token was
unsigned and bound to nothing. Whoever can set a cookie for the registrable domain — any page
on a `*.stored.ge` host; `cdn.stored.ge` serves customer content — chooses both halves: plant
`csrf_token=X`, submit `X`. The one real protection was `SameSite=Lax` on the session cookie.
Reproduced: with the old middleware, "planted cookie + matching value" passed on every one of
the 30 mutations below.

## What was built (`internal/dashboard/middleware/csrf.go`)

- **The token is `hex(HMAC-SHA256(key, session id))`.** The session id is the
  `vaultaire_session` cookie value (the row key of `dashboard_sessions`), read after the
  session middleware accepted it. Bound to the session: a token minted for one session is
  refused for another, and it changes whenever the session does — sign-in, the second factor
  (the session is created after it), sign-out and in again. Compared with
  `subtle.ConstantTimeCompare`. No session cookie = no token (never the MAC of an empty
  string) and every mutation is refused.
- **There is no CSRF cookie any more.** The token lives in the page only — the hidden
  `csrf_token` field of every form and `<meta name="csrf-token">`, which htmx sends as
  `X-CSRF-Token` (both layouts) — so there is nothing to plant. A browser that still sends
  the old `csrf_token` cookie is told to delete it. The cookie policy page listed that
  cookie; it now says the protection uses none (and a test pins that).
- **The key** is `HMAC-SHA256(JWT_SECRET, "stored.ge dashboard csrf token key v1")`
  (`DeriveCSRFKey`). **The choice:** `JWT_SECRET` is the one secret every deployment must set
  (`VERIFY_SECRET` already falls back to it; `ENCRYPTION_MASTER_KEY` is absent on prod), it
  survives restarts, and the labelled derivation means a CSRF token is never a MAC under the
  key that signs JWTs. With no secret (tests, a dev server) the key is random per process and
  a Warn says so.
- **Fetch metadata, on POST / PUT / PATCH / DELETE, before the token:**
  - `Sec-Fetch-Site`, when the browser sends it, must be `same-origin` or `none`.
    `cross-site` is refused — and so is `same-site` (stricter than the brief): a sibling
    subdomain is exactly the attacker R12-19 describes.
  - `Origin`, when present, must be one of the dashboard's own: the origin of
    `VAULTAIRE_BASE_URL`, or `https://` + the request's `Host` (the dashboard answers on
    `stored.ge` and `stored.cloud`); `http://` + Host only when the host is loopback (local
    development). `null` is refused.
  - Neither header (curl, a browser from before 2020): **the token alone decides.** The two
    header checks never replace the token.
- **One instance for both chains** (`/dashboard` and `/admin`), mounted where the old one was.

### What is accepted — the whole list

A state-changing request on `/dashboard/*` or `/admin/*` is accepted when it carries a valid
session cookie **and** the token of that session **and** (`Sec-Fetch-Site` absent,
`same-origin` or `none`) **and** (`Origin` absent, or the dashboard's own). Nothing else.

### A deploy in the middle of a form

The token depends on the key and the session id only. The key is derived from `JWT_SECRET`
and sessions are rows in PostgreSQL, so a form opened before a restart posts after it — shown
live below. Two one-time exceptions: the deploy of *this* change (an open page still carries
the old random token: its next POST answers `403 CSRF token invalid — reload the page and
try again`), and a rotation of `JWT_SECRET`.

## Adversarial pass — what it found

1. **`same-site` is the attacker.** The brief said "reject cross-site". A request from
   `cdn.stored.ge` is `same-site`, not `cross-site`: accepting it would have left the sibling
   subdomain — the case the finding is about — to the token alone. Refused; no dashboard flow
   posts from another subdomain (OAuth and Stripe come back with GET).
2. **A legal page that had become false.** `/legal/cookies` listed `csrf_token`. Fixed with
   the code, pinned by a test.
3. **The HMAC of nothing.** A request with no session cookie must not get
   `HMAC(key, "")` as its token — that value would be the same for everyone and valid for
   anyone the chain let through without a session. No session = empty token = refused.
4. **Cookie tossing.** A sibling subdomain can still plant its *own* `vaultaire_session` for
   `.stored.ge`; the session middleware and the CSRF middleware both read the first cookie of
   that name, so they agree on the session — the attacker gets their own account with their
   own token, never a valid token for the victim's. (Making the victim act inside the
   attacker's account is the login-CSRF class R12 accepted; a `__Host-` cookie prefix would
   end it — not this WP.)
5. **A token that never changes within a session is in every page** (BREACH-style recovery
   over compression). Considered, not masked: the token alone is worth nothing — a
   cross-site POST carries no session cookie (`SameSite=Lax`) and is refused by the two
   header checks before the token is looked at.
6. **A deploy between two writes / concurrent requests / flaky backend:** the middleware is
   stateless; nothing is written.
7. **The same logic on another entry point:** every cookie-authenticated mutation is under
   `/dashboard` or `/admin` (the matrix walks the router and counts them); the JSON APIs use
   bearer tokens and no cookies.
8. **"Constant-time"**: `ConstantTimeCompare` returns early on a length mismatch; the length
   (64) is public.

## What I could not prove

- A browser older than Fetch Metadata (no `Sec-Fetch-Site`): the "token alone" path is
  tested with curl and in unit tests, not in such a browser.
- **A real browser against prod.** Read-only on the box: `VAULTAIRE_BASE_URL=https://stored.ge`
  (so `Origin: https://stored.ge` is accepted whatever `Host` the app sees), `JWT_SECRET` is
  set, and HAProxy has no rule that rewrites `Host` (so `https://stored.cloud` is its own
  origin there). A form post by a signed-in browser on prod is the owner's to do — workers
  do not sign in to prod.

## Decisions taken

- No cookie at all (the brief allowed the signed double-submit; with a session to bind to,
  a cookie adds only something to plant).
- `same-site` refused. `Sec-Fetch-Site: none` accepted.
- `http://` own-origin accepted on loopback hosts only.
- The 403 text keeps its first three words (`CSRF token invalid`) and adds what to do.
