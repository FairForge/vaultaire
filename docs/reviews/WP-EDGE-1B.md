## Decisions

- **D-EDGE-10 — the If-Match a read link signs is the row's digest ONLY where it is provably the backend's own ETag.** The prompt's rule (`COALESCE(body_md5, etag)` for every shape) is wrong above the uploader's single-part cutoff: the S3-class drivers write any body over `drivers.S3SinglePutMaxBytes` (16 MiB) as a backend MULTIPART whose ETag is the parts' `-N`, unknown to the row (a single PUT's MD5 ETag, a CopyObject's, an origin-assembled multipart's `body_md5` — none is what the backend answers). The lab: a 64 MiB origin-written object's link signed its `body_md5` and both backends answered **412** on every read. So `edgeGetIfMatch`: an edge-assembled multipart (a `-N` ETag with no `body_md5` — the backend's own answer, recorded at Complete) → that ETag; an object of at most the cutoff (one backend PutObject: the row's single MD5, or an origin-assembled multipart's `body_md5`) → the digest; anything larger → no If-Match. Since WP-R2-1 Part C no write overwrites a blob address in place, the If-Match is a belt; the address is the guard — and a digest that turns out wrong (a `-N` row written before 094 of an object over the cutoff) is a 412 → the origin serves, never other bytes. Recording the backend's ETag at write (every driver Put discards `PutObjectOutput.ETag`) would give every read its belt: a residual (RB-2).
- **D-EDGE-11 — every read link signs its exact byte span.** The admit always names a `Range` — the client's, or `bytes=0-<size-1>` for a whole read — so the backend answers 206 to every link (`expect_status`) and the link is bound to the bytes the row describes; the client's status is the origin's (`status`: 200 for a whole read, 206 for its own Range) under the origin's headers. A link signing neither a range nor an If-Match is never made (`presignGet` refuses it). The `-N` / `body_md5` shapes above then still get the size bound.
- **D-EDGE-12 — a client If-Match the row satisfies is admitted.** `aws s3 cp` sends `If-Match: "<etag>"` with `Range: bytes=0-` on every download past its multipart threshold (the lab: every 64 MiB download went through the origin until it was admitted) — the prompt's "pass through any conditional header; no S3 client on the API path sends them" was wrong for THE client. The admit evaluates If-Match against the row with the origin's own `checkIfMatch`; a mismatch is the origin's 412, If-None-Match / If-*-Since stay the origin's (a 304 is its answer; no S3 client sends them).
- **D-EDGE-13 — the throttle decision is a pass-through, never a 503 from admit.** A tenant past its allowance with `egress_throttle` on reads through the origin, which paces it as D-25 says (slow, refused only past MAX_STREAMS); the Worker never paces, and the bytes through SLC are then the throttle rate. 40.10's "503 SlowDown from admit" is rewritten in the plan: a 503 on every ≥ 4 MiB GET past the allowance would turn D-25's trickle into hard failures. With the flag off the decision is counted (`vaultaire_egress_would_throttle_total{surface="edge"}`).
- **D-EDGE-14 — the commit is at the backend's headers, and the two trades are accepted.** The Worker hands the backend's body to the client untouched and has no event when a stream it does not touch ends. `served` meters the backend's `Content-Length` (clamped to the admitted size): a client that aborts mid-body is metered for the whole response; a lost commit is metered for the ADMITTED size by the reaper (the upper bound; nothing released, nothing queued — the row's address is the live object's). Both err toward the tenant paying for what the backend sent, never less; the origin meters what it wrote.
- **D-EDGE-15 — a fallback carries the backend's status into the breaker with the engine's own rules.** `RecordReadOutcome(backend, err)`: a 5xx, a 403 (a dead key) or no answer charges (five open the breaker, and an open breaker passes the next GET through to the origin); a 404 (logged loud: the row names a blob the backend does not hold), a 412 and a 416 never — they are the object's state. RE-3 closes for reads; writes stay Prompt 47's.
