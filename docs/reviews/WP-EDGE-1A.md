# WP-EDGE-1 Part A — the mover (Stage 1a Prompt 44)

*Plan 40.10 slice 1, the WRITE half: PutObject and UploadPart of a tenant with the `edge_ingest` flag leave SLC. A Cloudflare Worker on `s3.stored.cloud` takes every S3 request; an admitted write is streamed by the Worker straight to the backend on a presigned URL that signs the size and the client's checksum, and committed by the control plane exactly as a PUT through SLC would be. Everything else passes through. Prompt: `docs/reviews/WP-EDGE-PROMPTS.md`. Session 2026-10-26, the owner away ("build everything now").*

**The baseline amendment (#979, the owner session, 14:05 UTC the same day — `bench-results/EDGE-RELAY-2026-10-26.md`), read mid-build and applied:** the Worker never touches bytes on the write path (the subrequest's body is the request's own: any JavaScript in the byte path halves a stream to ~25 MB/s; pass-through runs 42–54 MB/s per stream, ~150 MB/s at eight); so no MD5 / SHA-256 at the edge, the "backend ETag against the Worker's MD5" check is dropped, a hex `x-amz-content-sha256` claim is not verified on this path (the docs say so), aws-chunked bodies pass through to the origin (aws-cli v2 users set `request_checksum_calculation = when_required`), `EDGE_MIN_BYTES` (default 4 MiB). The first build of this session had a streaming decoder + digests in the Worker and verified them end to end in the lab (recorded below under "the first lab"); it was removed before the PRs merged.

Contract lines cited: 1 (the Worker moves Standard plaintext and Private ciphertext alike — it never decides a mode), 4 (no key at the edge in this part), 7 (the Worker's build is a `client_build` row of the transparency log), 11 (one domain: `s3.stored.cloud`). Line 8: the Worker is not a privacy feature and no customer copy says it is.

## Decisions

- **D-EDGE-1 — a part's placement question is "may a whole unsealed write land in this bucket", never the chunk threshold.** The admit evaluates `decidePlacement` with `Size = 1` for a part (every refusal and the sealing rules still apply); an edge upload is completed WHOLE by the backend whatever its total size, because its parts are the backend's. A Complete of an edge upload that would now have to seal (the bucket's SSE setting changed meanwhile) is refused 400 with the upload left active for Abort; a `chunked` placement at Complete is ignored (the object is whole). The prompt's "Size = decoded length" would have passed a > 64 MiB part through and then refused it as a staged part on an edge upload.
- **D-EDGE-2 — one upload is one path.** `multipart_uploads.edge` is set by the FIRST edge part's admit under the row's lock, only when no part row exists; from then a staged part is 400 `InvalidRequest` (checked before the body is read, re-checked under the lock in the reservation and the settle — `errUploadEdge`), and an edge part on an upload that already holds staged parts is `{edge:false}` (`errUploadStaged`: the origin stages it too). Complete assembles staged files or asks the backend to assemble its parts, never both.
- **D-EDGE-3 — the backend half of an edge upload is the control plane's to end.** Abort calls `AbortMultipart` after the row ends and stamps `backend_upload_ended_at`; a failed abort is a Warn and the `multipart_reaper`'s new pass retries it (`backend_aborted` / `backend_abort_failed` in its result); the purge never deletes an aborted edge upload whose backend abort has not been made. Complete stamps it too. An abandoned edge upload is aborted by the reaper's abandon pass and then its backend half by the same run.
- **D-EDGE-4 — the commit's integrity is the backend's (the amendment).** The Worker reports the backend's answer only. A backend 400 `BadDigest` / `XAmzContentChecksumMismatch` / `InvalidDigest` (the signed `Content-MD5` the backend enforced) is the client's 400 `BadDigest`; a backend `IncompleteBody` / 408 / 411 (the body ended short of the signed length) is 400 `IncompleteBody`; any other backend error, or a subrequest that failed before an answer (`edge_error`), is 503 + Retry-After 30 with the address queued `orphan_write` on THAT backend (placeObject's rule). On a 200 the backend's ETag must be an MD5 (it is, on every EdgeWriter backend — Step 0.2) and, when the link signed a `Content-MD5`, that digest — otherwise the blob is deleted and the write refused (500 / 400); the ETag is the row's and the client's. Every failure releases the reservation. A hex `x-amz-content-sha256` claim is NOT verified on this path (`docs/API.md` says so; the origin verifies it). The edge path with a signed `Content-MD5` never stores a bad body at all (both backends refuse it); the origin's path stores first and retires.
- **D-EDGE-5 — `EDGE_MIN_BYTES` (the owner's addendum, default 4 MiB, a size or `off`):** a write under it is `{edge:false, reason: small}`, counted `pass_through_small`. Two round trips fewer for a small body, and its bytes do not matter for SLC's bandwidth.
- **D-EDGE-6 — the Worker classifies by shape, the control plane decides.** A signed (SigV4 header) PUT of an object key with no query, or exactly `partNumber` + `uploadId`, with a plain body, is asked about; aws-sdk-go-v2 (rclone's library) names the operation in the query (`x-id=PutObject`) and that is not a sub-resource (found in the lab: every SDK PUT passed through before). A copy, a sub-resource, a presigned or unsigned request, a body with no `content-length`, an aws-chunked body (`x-amz-content-sha256: STREAMING-*` — the control plane says the same, `pass_through`) and every other method pass through without a call.
- **D-EDGE-7 — the lab topology:** `wrangler dev --local --local-upstream <origin>` with clients using the dev server as an HTTP proxy (`HTTP_PROXY`), so the Host they sign is the origin's, `fetch(request)` reaches it and the Worker sees the request exactly as the edge would (the dev server rewrites the URL host to the upstream — a client signing for the dev host would always mismatch). Go clients must set the proxy explicitly: `ProxyFromEnvironment` never proxies a loopback destination (two "pass-through" results in the lab were requests that had bypassed the Worker).
- **D-EDGE-8 — `ValidateDescribed` returns the tenant, not the access key** (the prompt said `accessKey`): the admit needs the tenant and the scope; the key id is in the descriptor's Authorization. The live entrance keeps `wrapPayloadVerification` after the shared verifier; the described one has no body.
- **D-EDGE-9 — the edge calls are JSON over the Worker's own request:** the client's `Authorization` travels INSIDE the body, so the S3 credential gate (Decision 8) never captures the call (`TestEdgeRoutes_NeverCapturedByTheS3Gate`); a wrong token or a non-Cloudflare peer is a plain 404 (the recovery route's rule).

## Residuals (Part 0 of Prompt 45)

- **RE-1 (P3) — the edge path does not verify a hex `x-amz-content-sha256` claim** (the amendment: no JavaScript in the byte path). The origin's path does; `docs/API.md` says so. A client that wants the claim verified sends `Content-MD5` (signed into the link, enforced by both backends) or uses `stored.ge`. A later part may let the backend verify it (`x-amz-checksum-sha256` as a signed header — Step 0.2 showed both backends enforce it — when the client sends the sha256 as a checksum header rather than the payload hash).
- **RE-2 (P3) — aws-cli v2's default upload shape (aws-chunked + CRC32 trailer over TLS) is the origin's.** `docs/API.md` tells aws-cli users to set `request_checksum_calculation = when_required`; `pass_through` counts them. A decoder in the Worker costs ~25 MB/s per stream (the baseline); measure a decoder later if aws-cli traffic matters.
- **RE-3 (P3) — the breaker never hears from the edge.** A backend that 5xxs the Worker's PUT is a 503 to the client and an `orphan_write` row, but no `engine` breaker charge: the origin's own probe and its own writes decide the breaker; an admit checks `CanAsk` (an OPEN breaker passes the write through to the origin). 40.10 names "breaker signals from the data-plane host's report" — Part B or the data node (Prompt 47) should carry a backend outcome into `CoreEngine.RecordReadOutcome`'s sibling for writes.
- **RE-4 (P3) — a Complete retry after the backend's Complete succeeded but before our commit** answers the backend's `NoSuchUpload` as a 500 (`writeCompleteStoreError`'s default) and leaves the upload active; the client's next retry fails the same way until the reaper abandons it (48 h) — the object is then unnamed (its blob queued by the abandon → `orphan_write` is NOT written for an edge Complete's blob; the `retired_blobs` collector never learns of it: the sweep removes it with the account only). Fix: `completeEdgeUpload` should treat a backend `NoSuchUpload` after a recorded `backend_upload_ended_at` as the replay of a landed Complete (`completedUploadResult`'s rule: the head row names the address with the expected ETag), and a failed commit after a successful backend Complete should queue `storage_key` as `orphan_write` (it does when `commitBlobWrite` fails; the gap is the retry path).
- **RE-5 (P3) — the flag flip on tenant zero went in as a `feature_flags` row (no admin JWT without the owner's TOTP since #956), so no `flag.set` audit row names it.** The owner re-asserts it once from `/admin/flags` (one click writes the audit row). The DEPLOY.md rule "never a psql row" is about the guarded flags; `edge_ingest` has no write guard.
- **RE-6 (P4, pre-existing) — the origin discards aws-chunked trailers:** a wrong `x-amz-checksum-crc32` trailer is a 200 at the origin (the first lab's decoder caught it; the origin never did). Not this WP's; noted for the CRC32 trailer verification a later part may add to the origin's `awsChunkedReader`.
- **RE-7 (P4) — duplicate header values:** the Worker joins repeated client headers with `", "` (the Headers API); SigV4's canonical form joins with `","` — a client that sends a signed header twice would fail at the admit and be refused as a signature mismatch (the origin passes it). No S3 client does; a pass-through on a refusal of that shape is a one-liner if one appears.
- **RE-8 (P4) — the first lab's `edge_ingest` flag row on the lab DB and the lab tenant's rows** live in `vaultaire_edge` on the Mac (a private lab DB); nothing on prod.
