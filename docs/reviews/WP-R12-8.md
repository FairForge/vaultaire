# WP-R12-8 — MFA enrolment: the pending secret stays on the server, the QR code is ours

**Worker session, 2026-10-02. Branch `wp/r12-8-mfa-enrolment`.** Closes R12-23 and the
remainder of WP-R5-8. No migration.

## The problem

`GET /dashboard/settings/mfa` generated a TOTP secret and ten backup codes and put both in
hidden form fields; `POST /dashboard/settings/mfa/enable` read them back:

```go
secret := r.FormValue("secret")
code := r.FormValue("totp_code")
backupCodesRaw := r.FormValue("backup_codes")
...
if mfaSvc == nil || !mfaSvc.ValidateCode(secret, code) {
```

So the secret enrolled was whatever the form said. A user — or a script in the page — could
enrol a secret of their choosing (`JBSWY3DPEHPK3PXP`), with backup codes of their choosing
(`CODE1`): admin-MFA enforcement was satisfiable with a secret known to the world. And the QR
code was drawn by `qrcode-generator@1.4.4` loaded from `cdn.jsdelivr.net` **without SRI**, on
the one page that shows a new secret, with the CSP allowing the whole CDN in `script-src`: a
CDN compromise read every new secret.

## What was built

### The pending secret (`handlers/mfa_enrol.go`, `MFAEnrolmentStore`)

- Generated by the server on the first GET of the setup page and **kept in the server's
  memory**, keyed by the session id (the session cookie's value) and bound to the user id.
- **One per session**: a reload or a second tab gets the *same* secret — opening the page
  again never invalidates the QR code already scanned.
- **10-minute TTL** from the first open (not sliding). **Single use**: `Confirm` verifies the
  code under the store's lock and takes the entry when it is right, so two tabs posting at
  once cannot both enrol. A wrong code keeps the entry (a typo does not cost a re-scan).
- **Bounded**: expired entries are swept when the store holds 256; at 5000 live entries a new
  enrolment is refused (`ErrMFAEnrolmentBusy`, "try again in a few minutes") rather than the
  map grown. One entry is a session id, a user id, a 32-character secret and a URL.
- The enable POST carries **the 6-digit code and the CSRF token, nothing else**. A `secret`
  or `backup_codes` field in the request is ignored.

**Where it lives, and what a deploy does.** Memory, not PostgreSQL — the choice. A table of
not-yet-confirmed TOTP secrets is one more place a secret is at rest (and one more table for
the erasure walk, the retention job and the schema tests) for state that lives ten minutes;
the 2FA *login* challenge already lives in memory the same way. The price: the box redeploys
several times a day, and **an enrolment that is open across a restart loses its pending
secret.** What the user sees: they enter the code, and the page comes back with

> That setup session has expired — it lasts 10 minutes, and a service restart ends it. Scan
> the new QR code below, and remove the earlier stored.ge entry from your authenticator.

and a fresh QR code. They are never enrolled with a secret the server no longer holds. At
five deploys a day and a minute or two per enrolment that is well under 1 % of enrolments.

### Backup codes

Generated by the server **after the code verified**, handed to `auth.EnableMFA` (which stores
bcrypt hashes), and shown **once**, in the response to that POST (`200`, `Cache-Control:
no-store`). A reload of that page re-sends the POST: the account is already enrolled, so it
redirects to Settings — nothing is replaced and no codes are shown. The setup page shows none.

### The QR code: rendered by the server

`GET /dashboard/settings/mfa/qr.png` returns the pending secret's `otpauth://` URL as a PNG
(`otp.NewKeyFromURL(url).Image(240, 240)` — `boombuler/barcode`, already compiled into the
binary through `pquerna/otp`; no new dependency), `no-store`,
`Cross-Origin-Resource-Policy: same-origin`, 404 when the session has no pending enrolment.

**Why not vendor the script:** rendering on the server removes the script instead of moving
it. No JavaScript is handed the secret, the page works with JavaScript off, there is no
third-party blob in the repository to keep current, and it needs nothing the binary did not
already link. (A `data:` URI in the page would have needed the dashboard's first
`template.URL`; an image route keeps "no typed-safe strings anywhere" true.)

### The CSP

`cdn.jsdelivr.net` is gone from `script-src`; the policy
(`middleware.ContentSecurityPolicy`) now names **no host in any directive**.
`TestNoServedTemplateOrCSPNamesAnExternalScriptHost` walks every embedded template (and the
static CSS) for a `<script src>`, `<link href>` or `@import` pointing at another host, and
checks every CSP source is a keyword or `data:` — it fails on the old template and the old
policy (seen).

### Still working

- **Admin-MFA enforcement** (`RequireAdminMFA`) redirects to the same setup page; the QR route
  is inside the session group.
- **OAuth → MFA** and the login challenge (`MFAPendingStore`) are untouched.
- **MFA disable** (password required, other sessions revoked) is untouched.
- **R12-38** (a TOTP code is single-use at sign-in) is untouched — and the code that enrolled
  is now recorded as spent, so it cannot also be the second factor of a sign-in in the same
  30 seconds.

## Adversarial pass — what it found

1. **`EnableMFA` wrote memory before the database — fixed.** A write the database refused
   left the account "enabled" in this process only: the dashboard said two-factor was on and
   sign-in asked for a code, until the next restart loaded `user_mfa` and found nothing. With
   the new flow that also meant "already enabled" on the retry, so the user could never
   finish. The row is written first now (`TestEnableMFA_ADatabaseFailureLeavesTheAccountNotEnrolled`,
   red on main), and the handler puts the pending secret back when enabling fails.
2. **The QR image is a GET that returns a secret.** A sibling subdomain is same-site, so the
   session cookie rides along on an `<img>` there. The pixels are not readable cross-origin,
   and `Cross-Origin-Resource-Policy: same-origin` now stops the image loading at all.
3. **Concurrent writer.** Two tabs posting the same code: `Confirm` is atomic, one enrols,
   the other is told the session expired and lands on Settings (already on). A second
   *session* of the same user has its own pending secret; once the account is enrolled its
   POST is a redirect — a second pending secret cannot overwrite the enrolled one (tested).
4. **A crash between two writes.** Between `Confirm` and `EnableMFA`: the pending secret is
   gone, nothing is enrolled, the user scans again. **Between `EnableMFA` and the response:
   the account is enrolled and the backup codes were never shown.** Not closed here: the
   user can sign in with the authenticator, and gets new codes only by disabling (password)
   and enrolling again. A "regenerate backup codes" action would close it.
5. **The same logic on another entry point.** The user API's MFA routes were mocks and were
   removed in R11; the management API has none. Enrolment exists only here.
6. **"Nothing secret is ever accepted from the client" against the code.** The handler reads
   one form value, `totp_code`. The test posts `secret=` and `backup_codes=` alongside a code
   that is valid *for the posted secret*: refused; and alongside the right code: enrolled with
   the server's secret, `CODE1` is not a backup code.
7. **Attacker with a stolen session.** Enabling two-factor still asks for no password: a
   session thief can enrol *their* authenticator and lock the owner out until an admin reset.
   Pre-existing and not changed by this WP (the same person could not change the password —
   that asks for the current one). Worth a small WP: ask for the password on enable.
8. **Flaky backend.** The store is memory; the only backend call is `EnableMFA` (item 1).

## What I could not prove

- **A phone.** The QR code was decoded by Chrome, not scanned with Ente Auth or Google
  Authenticator from a screen.
- **Prod.** Enrolment on prod needs a signed-in browser; workers do not sign in to prod. The
  admin account already has MFA on (so the setup page redirects for it).

## Decisions taken

- Pending state in memory, keyed by the session; a restart costs a re-scan and says so.
- The QR code is rendered by the server as a PNG route; nothing is vendored.
- A second tab shares the session's secret; the TTL does not slide.
- Wrong codes are not counted: whoever can post them already sees the secret.
- Backup codes are generated at verification and shown in the POST response (the reveal-once
  shape the API-key page uses), not after a redirect.
- `EnableMFA` writes the database before memory.
