## Step 0 answers

- **RP90 and RP91 on main?** Yes: #1123 (`fe6f02c7`) landed both notes and filled Part 0.
- **The Family line in `prices.json`?** None. A family has no price of its own yet (F-40: $6/mo or $60/yr, 3 TB, 6 people is a draft). The organizer's plan IS the pool: members draw on the organizer's `tenant_quotas` limit and floors. Nothing was added to `prices.json`, and the checkout does not sell a family (open question 3).
- **Who counts in "six"?** The organizer counts (42.1's "up to 6 people"). So a family is the organizer and at most five members, with pending invitations counted. One constant, `auth.MaxFamilyPeople`, until the owner decides (D-STRIPE-87).
- **A live entitlement** means an `entitlements` row with `lapsed_at IS NULL` (F-40: join after cancelling; no proration).
- **Adults only** (F-40) is a sentence in the docs, not a gate: no age is collected anywhere. The minors' path waits for counsel.

## Decisions as built (D-STRIPE-87…)

- **D-STRIPE-87** — six people include the organizer (above).
- **D-STRIPE-88** — a detached member gets the free tier (`storage_limit_bytes` = the free limit, `tier = 'free'`), whatever cap the organizer had set. A cap was the pool's, not the account's. The organizer's erasure (stage b5) takes the same path.
- **D-STRIPE-89** — migration 123 landed with Part 0, not PR A. The prompt's "123 in PR A" assumed PR A needed the column. RP90-5 (`buckets.created_by_agent_grant`) and RP90-6 (`approvals.resource_ref`) needed one each, and the family needed none. Still one file, written whole.
- **D-STRIPE-90** — `ScheduleApp` lives in `internal/account`, not `internal/auth`: `account`'s tests import `auth`, so `auth` importing `account` would be a cycle. It is still one function for both doors.
- **D-STRIPE-91** — Part 0 shipped as #1126 (RP90-1…9, deployed `204f3d11`) without waiting for RP91-1/2 (#1127). RP90-1/2/3 were live on prod and deploy first; RP91-1/2 follow in their own PR after #1125, whose `s3.go` block they share.
- **D-STRIPE-92** — every family write is the owner's: `ActionBilling` on both surfaces (`dashboardWrites`; `requireRole` on the API — `TestManagementRoutes_EveryWriteNamesItsAction` refuses a viewer before the handler). The pool is paid for, so inviting, capping, removing, joining and leaving are billing acts. An invitation also needs a fresh TOTP code, like an approval of a destructive act.
- **D-STRIPE-93** — only a plain personal account joins: a root, not a sandbox, not provisional, no platform or partner grant, and no children of its own. Otherwise one pool would have two roots, or depth would pass 2.
- **D-STRIPE-94** — a member's `label` is the account's own e-mail: the address the organizer invited, which tells them nothing new. Never a bucket, object or request.
- **D-STRIPE-95** — the TOTP counter (RP90-7) is in-process, like the replay guard beside it: each slot counts its own. A wrong backup code at a sign-in counts too. A replayed right code counts as a failure.

## Residuals (RB14-n)

- **RB14-1** — a member keeps `tier = 'free'` inside the pool. Free-tier rules keyed on the tier (one bucket, `freeTierBucketCapBlocksWrite`, the free egress ratio) still apply to members: a family member gets the pool's bytes but the free tier's bucket count. Fix with F-40's price: give a sponsored child the organizer's tier, or key those rules on the pool root's tier.
- **RB14-2** — an invitee with no account must register first, and `signups` is closed on prod. A family invitation does not open registration the way a member invitation does (`RegisterInvitedUser` makes no tenant). The join page needs a "make an account" path that creates a root and joins in one step.
- **Prod (Part 0)**: `204f3d11` deployed 2026-11-03, 22/22 backends, 0 errors in 1,395 journal lines; RP90-3 proven live (`/oauth/register` from one IP: 10 × 400, then 429).

- **RB14-4** — `TestManualPayment_GrantsWithoutRow_ThenExtends` (internal/payments) fails outside UTC across a DST change (`addPeriod` in the local zone). CI runs in UTC. Pre-existing, unrelated.
- **RB14-5** — `agentMayCap` passes a key or bucket that does not exist on to the handler, which answers its own 404. An agent learns nothing new from that 404 that the list routes don't already tell it.
- **RB14-6** — the shared family space (one more tenant in the pool with every member as a WP-TEAM-1 member) is not built. F-40 does not ask for it.

- **RB14-8** — RP90-1 closes the agent's deletes, not its overwrites. An agent key's PutObject or CopyObject onto an existing key in an UNVERSIONED bucket replaces the old bytes for good, the same loss F-41 names. The fix has the same shape: refuse an agent's write over an existing key unless the bucket is Enabled (one head-row read), or make it part of D-STRIPE-85.
