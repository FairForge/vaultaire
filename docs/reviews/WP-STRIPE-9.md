# WP-STRIPE-9 — browser uploads: S3 presigned POST policies (Stage 1a Prompt 57), after Part 0 = RP92's findings

*Plan § WP-STRIPE, the **WP-POST-1** row. A web page lets its visitors upload straight into a bucket: the owner's server signs an S3 POST policy (any SDK's `generate_presigned_post`), the browser POSTs a form with the file to `/{bucket}`, and the upload is checked and written exactly as a PUT of the same bytes — the same verifier, the same write path — and admitted at the edge by the policy's signed size.*

*Prompt: `docs/reviews/WP-STRIPE-PROMPTS.md` § Stage 1a Prompt 57 (both editions; this session ran the Opus edition). Session 2026-11-03. **Migration 124** (`124_oauth_client_ip.sql`, Part 0's RP92-5 — WP-POST-1 added no column). Next: **125**. The post-merge review is **RP94**.*

Contract lines cited (`docs/ARCHITECTURE_CONTRACT.md`):
- **4** (keys only through the one hierarchy): no key, wrap or derivation added. A POST policy is signed with the credential's existing SigV4 signing key; the verifier derives it with its own `deriveSigningKey` (never a copy — the presigned query verifier's `presignDeriveKey` is the one copy that predates this and stays).
- **5** (convergence within a space only): untouched. A form's file is a PUT's write; at the edge it is moved whole (never the codec).
- **6** (the chunker is frozen): untouched.
- **Architecture Decision 8** (S3 credentials are the S3 API's before any route): a POST policy form's credential is inside its body, so its SHAPE — POST, `multipart/form-data`, a one-segment path — is the gate's (`postPolicyShape` in `signedS3Request`).

- **What a browser sends:** every field, then `file`, then `\r\n--<boundary>--\r\n` — Chrome, Firefox, curl `-F`, Python requests and Go's `mime/multipart` all close the same way. S3 ignores fields after `file`; ~~so does Stored (never read)~~ **Stored refuses them** (corrected by Prompt 58 PR C: since #1142 a part after the file is 400 `MalformedPOSTRequest` at the origin and, since the Worker 0.7.1, at the edge — RP94-1, D-POST-10; until then it was stored inside the object).
- **The file's size:** never declared by a browser's part. It is the request's Content-Length less the bytes before the file and the closing delimiter (D-POST-2) — known before a byte of the file is read, the same number at the origin and the Worker.

## Decisions as built (D-POST-1…)

- **D-POST-1** — `success_action_redirect` (and the legacy `redirect`) is refused, 400. The signed alternative — honoured only when an exact `eq` condition binds it, https, a 303 with `bucket`, `key`, `etag` — is the owner's call (a key holder's own choice of page, not an open redirect).
- **D-POST-2** — the file's exact size = Content-Length − the fields − the closing delimiter, held to `content-length-range` before anything is read or reserved, reserved as a PUT's declared length, and proven as it streams: the bytes after the file must be exactly the delimiter, in the Read that yields the last file byte (a consumer that stops at the declared length still sees a bad tail as an error before it commits). The prompt said "the max reserved and the real size checked as it streams"; the exact size is stricter and bills nothing it will not write.
- **D-POST-3** — no cap on a policy's `expiration` (AWS sets none). A presigned URL's 7 days (R5-12) is not applied: a policy is bounded by its key (revocation kills it) and by its own conditions. The owner may want a cap (open question 2).
- **D-POST-4** — a form upload needs the key's `PutObject` permission (AWS's IAM action for a POST is `s3:PutObject`), at the origin and the edge; `PostObject` stays the access log's operation.
- **D-POST-5** — the gate takes POST + `multipart/form-data` to ANY one-segment path. No page of ours posts multipart (none in the templates, no handler reads one); `/login`, `/register`, `/abuse`, `/forgot-password`, `/reset-password` read forms through `FormValue`, which parses multipart too, so a `curl -F` to them is now the S3 API's (an XML error). Those names are reserved bucket names.
- **D-POST-6** — a policy must name its bucket (an eq or starts-with condition on `bucket`): a policy that names none would work against every bucket of the key. boto3 always adds it.
- **D-POST-7** — `acl` is accepted only as `private` (a bucket's mode decides who reads it), `tagging` is 501, a SigV2 policy (`AWSAccessKeyId` + `signature`) is refused as SigV2 headers are.
- **D-POST-8** — at the edge a form is admitted only for a whole, unsealed placement (no codec, no RS stripes — both need the host to cut the body, and a form's body is the file between two delimiters); a mirror leg is kept (the Worker tees the file stream as it tees a PUT's body).
- **D-POST-9** — the brief's "over the cap: the origin's error naming it" cannot be built: a request body over Cloudflare's 100 MB never reaches a Worker or the origin (Cloudflare's own 413 HTML). Built instead: the admit declines a policy whose signed max is past the cap (`post_over_edge_cap`), and `docs/API.md` § Browser uploads names the limit and the multipart alternative.
