## What is wrong, measured

On 2026-11-02 03:07:34 UTC a customer GET of a 96 MiB SSE-C Vault object whose Geyser blob had been deleted by hand was served from its parity copy, bit-identical, in **27.04 s**. The prod journal (`journalctl -u 'vaultaire@*'`, slot 8001) places the time:

| UTC | Line | Meaning |
|---|---|---|
| 03:07:34.049 | `authenticated request` GET `/vault-e2e-20261030/e2e/sealed-96m.bin` | start |
| 03:07:34 ×3, 03:07:35 ×1 | SDK `Response has no supported checksum` | Geyser answered 404 in under a second (the engine asks the recorded backend and no other — WP-R6-1); then the four Lyve shard GETs were opened, one after another |
| 03:07:41.523 | `vault object served from its parity copy` (`sse_stream.go:580`) | the first RS stripe (4 × 1 MiB) and the sealed header were read and verified: **6.5 s for the first 4 MiB** |
| 03:08:01.051 | `artifact retrieved` 100,663,296 bytes | the remaining 92 MiB streamed: **19.5 s ≈ 4.7 MB/s** |
| 03:08:01.085 | `request` 200 `latency 27.036682651` | end |

The scrub's rebuild of the same object (`vault_parity_scrub.go` `rebuild`, 02:40:58 → 02:41:17) took the same 19 s: the same opener, the same rebuilder. Lyve us-east-1 (prod `LYVE_REGION`) reads from SLC at 348–506 MB/s concurrent and hundreds of MB/s single-stream (`bench-results/COMPARISON-v2.md`, `COMPARISON-v3.md`); the 2026-10-07 lab rebuild from Lyve ran at 239–242 MB/s (`bench-results/SYNC-WORKLOADS-2026-10-07.md` line 52). So the 5 MB/s is in our process, not on the wire.

**The bench record's finding "7.5 s for the failover chain to fail … then every other backend" is wrong.** There is no chain: `engine.Get` asks the recorded backend alone (`internal/engine/engine.go:196`, `readCandidates` :697). The 7.5 s before the Warn line was ~1 s of Geyser plus ~6.5 s for the first stripe. Step 0 corrects the record.

What the code does today (`internal/api/vault_parity.go:1364` `Open`, `internal/api/vault_parity_codec.go:140` `newParityRebuilder` / `decodeNext`):

1. The four shard streams are opened **sequentially** with `drv.Get` (a whole GET per shard; a ranged GET only for a window that is not the whole object).
2. The rebuilder is pull-based: per stripe it does `io.ReadFull(stream, 1 MiB)` on shard 0, then 1, 2, 3 — **lockstep, nothing read ahead**, a fresh `make([]byte, 1 MiB)` per shard per stripe — then `Reconstruct`. The Lyve driver's client runs HTTP/2 (`TunedHTTPClient` without `WithHTTP1Only`, `internal/drivers/lyve.go:100`), so the four streams multiplex one connection and advance only as fast as the lockstep asks.
3. Nothing times it: no metric for shard open, first stripe or rebuild rate.
4. The read order is fixed: Geyser first, parity only after Geyser fails; an object on tape (`ErrArchived`) is never served from parity (`sse_stream.go:557`, `s3_engine_adapter.go:926`).

Hypotheses for the 5 MB/s, in the order to test: **H1** the lockstep 1 MiB reads over multiplexed HTTP/2 (flow-control window updates per 1 MiB read, four streams waiting on each other); **H2** sequential shard open and TLS setup (the 6.5 s first stripe); **H3** something in the Lyve driver's body path (`sdkCallOptions`, the op timeouts). The fix below is right whichever holds; Step 1 measures so the closeout can say which it was.

## Decisions (made — do not reopen)

- **D-V3-1** The rebuild reads every shard through `internal/parfetch` as **parallel ranged reads** when the leg's driver is an `engine.VersionedRangeGetter` (lyve, idrive, idrive-<region>, wasabi, blomp): a part = `R` whole stripes of the shard (`R` = `LARGE_GET_PART_BYTES` / stripe bytes, 16 stripes at the defaults), parts in flight per shard = `LARGE_GET_PARALLEL_PARTS` / m (2 per shard at the defaults, never below 1), the GET budget `LARGE_GET_PARALLEL_BUDGET_BYTES` (`a.largeGet.budget`), hedging as `startParallel` does (`s3_large_get.go:467`). Every range of a shard must report the same ETag and total size (`engine.RangeInfo`), or the read fails — never a splice (`errRangeIdentity`, as the parallel GET).
- **D-V3-2** A leg whose driver has no `VersionedRangeGetter` (permafrost, sync) keeps one whole stream per shard, but the m streams are **opened concurrently** and each is read ahead by its own goroutine into a bounded ring of `vaultParityReadAhead` = 4 stripes (m × 4 × 1 MiB = 16 MiB per rebuild), taken from the same GET budget. No `make` per stripe: stripe buffers are pooled per rebuilder.
- **D-V3-3** `Open` and the scrub's `rebuild` share ONE opener (`openParityShards`) and ONE reader (`newParityRebuilder` over `[]parityShardSource`): a structural test pins that `vault_parity_scrub.go` calls no `drv.Get` of its own.
- **D-V3-4** The first stripe is still decoded before `Open` returns (a wrong SSE-C key, a shard that does not match, must be decided before the status line — `openSealed`'s rule holds). Target on prod: ≤ 1.5 s from `Open` to the first stripe.
- **D-V3-5** One rebuild settles the leg's breaker once, at Close: `CoreEngine.RecordReadOutcome(leg, err)` (as `parallelGetReader.Close` does). Today a failing leg is never charged by a parity read.
- **D-V3-6** A new per-tenant flag **`vault_parity_serve`** (default OFF). ON: a GET of a vault-floor object with a `complete` parity row whose shards' leg has a closed breaker is read **from the parity FIRST**; its backend (Geyser) is asked only when the parity cannot serve (row not complete, leg open, a shard unreadable, the rebuild fails before the status line). So with the flag on an object on tape is served 200 from parity, never 403 `InvalidObjectState`, and Geyser's recall is never started by a GET. OFF: today's order exactly — Geyser, then parity on a failure, `ErrArchived` keeps the restore semantics. The flag gates GET only: HEAD's `x-amz-restore` lookup, RestoreObject, the dashboard Restore and the parity job are unchanged. Register it in `flags_wiring.go` beside `flagVaultParity` (`:63`), a root CLAUDE.md `feature_flags` sentence, the dashboard's flag page needs nothing (it lists registered flags).
- **D-V3-7** HEAD of an archive-class object keeps its one live backend call (Architecture Decision 2's exception), **bounded to 3 s** (`vaultHeadRestoreTimeout`, a constant): past it the header is omitted as on any failure, counted in `vaultaire_vault_head_restore_lookups_total{outcome=ok|error|timeout}`. On 2026-11-02 the lookup of a blob Geyser no longer had took 2.76 s.
- **D-V3-8** Metrics (registered in `prom_metrics.go` — the lesson of `be9d044d`: declared is not registered; a test asserts presence on `/metrics`): `vaultaire_vault_parity_rebuild_seconds{phase="open"|"first_stripe"|"stream"}` (histogram, buckets 0.1 s … 60 s), `vaultaire_vault_parity_rebuild_bytes_per_second` (gauge: the last whole rebuild's rate), `vaultaire_vault_parity_shard_reads_total{leg,kind="range"|"whole"}`, `vaultaire_vault_parity_fallback_reads_total` gains the outcome `served_first` (the flag path) beside `served` / `unavailable`. Rule `VaultParityRebuildSlow` in `deploy/monitoring/vaultaire-jobs.yml`: warn when the last rebuild rate is under 20 MB/s for 1 h with at least 3 rebuilds in the window; promtool test beside the others.
- **D-V3-9** The codec (`parityLayout`, RS 4+4, 1 MiB stripes, shard names, the row) does not change; a shard written before this WP is read by it unchanged.

## When a step does not go as written

- The rebuild stays slow after D-V3-1 on prod but PR 0's case (d) was fast: the difference is in our path — bisect with `rebuild_seconds{phase}`; the likeliest residual is the sealed opener's read pattern (`crypto` stream open in `sse_stream.go`): measure a PLAIN (unsealed-in-lab, `GEYSER_ALLOW_UNSEALED` only in a lab) vault object against the SSE-C one in the fixture with injected latency. Write what you find; do not redesign the codec.
- `data_path_allocations_test` fails on a new `make`: add the row with its budget, never widen the test.
- A flag read needs the tenant on the context and `a.flags` is nil in a test: `S3ToEngine.flags` nil means OFF (as `chunkingEnabled` treats nil as ON — do not copy that; nil = OFF for this flag, say so in a comment).
- The owner is not present for the admin JWT (step 14d): record the flag path as unproven on prod with the lab tests as the evidence, and list it first in the residuals.
- Geyser answers the by-hand delete with an error, or the landing zone has already flushed (`spectra-storage` header, a GET refused `InvalidObjectState`): stop; the object is on tape and cannot be deleted; the proof then uses only step 14d's path (the blob present, the flag on) and says so.
