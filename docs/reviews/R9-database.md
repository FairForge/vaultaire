## The nine areas

**1. Migration runner.** Deploy: `deploy.yml:151-158` scp's the directory and runs `for f in $(ls /tmp/vaultaire-migrations/*.sql | sort); do psql -w -v ON_ERROR_STOP=1 … -f "$f" < /dev/null; done` **before** the binary swap, as the `vaultaire` role against `vaultaire`. CI: `ci.yml:49-51`, same loop with `ON_ERROR_STOP=1`. `make test-db`: same loop against `vaultaire_test`. `scripts/deploy.sh` has no migration step. Ordering is lexical filename sort: `004_backend_health.sql` runs before `004_mfa.sql`; gaps are irrelevant. There is **no `schema_migrations` table** — "already applied" is decided purely by idempotency, and every deploy re-runs all 62 files. The idempotency claim is proven: the full set applied to an empty `vaultaire_review` then applied again — second pass **0 errors**, output is 131×`CREATE INDEX` (all `NOTICE: already exists, skipping`), 90×`CREATE TABLE`, 61×`ALTER TABLE`, 9×`CREATE FUNCTION` (OR REPLACE), 6×`DO`, 9×`DROP INDEX` (IF EXISTS), 3×`DROP FUNCTION` (IF EXISTS), 2×`INSERT 0 0` (seeds with `ON CONFLICT DO NOTHING`). Grep found no `ADD COLUMN`/`CREATE INDEX`/`CREATE TABLE` without a guard, no `CREATE TYPE`/`TRIGGER`, no `RENAME`, no `ALTER TYPE`. Live-safety: the DO-blocks in 034/043 (`to_regclass` guard), 054 (PK still single-column), 056 (`confdeltype <> 'c'`) and 058 (`data_type = 'uuid'`, `lock_timeout 5s`) are all no-ops once applied; no `NOT NULL` without `DEFAULT` on a live table. Gap: R9-11 (no timeouts on the runner).

**2. Schema + query audit.** `pg_dump -s vaultaire_review` = 87 tables, 827 columns, 36 FKs. **Prod's live schema equals the migrated schema** (`diff` of normalised dumps: only the position of `tenant_quotas.spending_cap_cents`, added by 043 on prod vs baked into 056 on a fresh DB). Query audit results are in the Query audit section: 482 static sites prepare cleanly, **10 sites reference columns/tables that do not exist** (R9-01/02/03/08/09/15), 16 dynamic sites reviewed by hand (all parameterised; `GetUsageHistory` is the one that is broken).

**3. Single schema owner.** Done here: `InitializeSchema` removed, the three tests use the migrated schema with per-tenant cleanup, 056 header fixed. Orphan tables listed for Isaac (D-12). `postgres.go:CreateTables` (the third owner) is dead and goes with WP-R0-4.

**4. Indexes / hot queries.** See Query audit table. Every hot lookup is served by its PK or a covering index; the two structural weaknesses are prefix `LIKE` under `en_US.UTF-8` (R9-19) and the three unbounded log tables (R9-04). 057's nine drops were all true duplicates; nothing current needs them (`idx_ohc_lookup` was the PK, `idx_tcr_*` the UNIQUE, `idx_bandwidth_tenant_date` the UNIQUE, `idx_gci_marked_for_deletion` replaced by the partial `idx_gci_marked`). No leading-wildcard `LIKE`; no function on an indexed column except `DATE(timestamp)` in `GROUP BY` after an indexed range (fine).

**5. Referential integrity and deletion.** 36 FKs, 33 `ON DELETE CASCADE`, 2 `NO ACTION` (`admin_notes.admin_user_id → users`, `user_roles.granted_by → users`), 1 `SET NULL` (`retention_jobs.policy_id`), 1 composite `NO ACTION` (`tenant_chunk_refs(dedup_scope, plaintext_hash) → global_content_index` — correct: a chunk row must not vanish under a ref). **The object tables have no FKs at all**: `object_head_cache`, `object_versions`, `object_locks`, `object_locations`, `multipart_uploads`, `buckets`, `smart_demotions` are keyed by `tenant_id` text with no reference to `tenants`, so a tenant delete cascades nothing there — deletion is entirely the explicit list in `ExecuteDeletion`. Cascading a tenant delete therefore **cannot leak chunk references through FKs** (nothing cascades into `tenant_chunk_refs`); the set-based GCI release in `ExecuteDeletion:129-146` is the only path and it is correct. What survives `ExecuteDeletion` today (tenant-scoped, not audit/financial): `multipart_uploads`+`multipart_parts` (in-flight uploads → backend part leak), `smart_demotions`, `idempotency_cache`, `bucket_notifications`, `cdn_access_log`, `cdn_stats_daily`, `s3_access_log` (PII), `access_patterns`, `bandwidth_alerts`, `bandwidth_rollover`, `tenant_cost_daily`, `tiering_policies`, `feature_flags` (per-tenant rows), `metered_usage_reports` (keep — billing), `abuse_reports`/`admin_notifications`/`stripe_events`/`billing_charges`/`audit_logs` (keep — records). Tenant suspension (`tenants.suspended_at`) touches no other table. `ExecuteDeletion` is unreachable (R0) — not rewired here (R10).

**6. Types.** See R9-14. `bigint` for every live byte count; the `integer` columns are counts (`requests_count`, `ref_count`, `chunk_count`, `retry_count`). 20 JSONB columns, none constrained (`api_keys.permissions` is validated at read time to fail closed — R5-14). `object_locations.bucket` holds the container `<tenant>_<bucket>` (R6-14) — confirmed: `engine.go:445` passes `container`; the PK `(tenant_id, bucket, object_key)` therefore duplicates the tenant inside `bucket`, and `overview.go:242`/`admin_costs.go:390` group on it unaware. Fix belongs to WP-R6-1 (make head-cache the only truth); if the table stays, a one-off `UPDATE … SET bucket = substr(bucket, length(tenant_id)+2)` migration is needed first.

**7. Connection handling.** Pool: `MaxOpenConns 50 / MaxIdleConns 25 / ConnMaxLifetime 5m / ConnMaxIdleTime 1m` (`postgres.go:59-62`) against prod `max_connections = 200`, no pgbouncer (`which pgbouncer` empty), 1 app connection idle at review time. Headroom is fine for one binary; a second instance or the Grafana/backup connections still fit. `statement_timeout`/`lock_timeout`/`idle_in_transaction_session_timeout` are all 0 on prod and nothing sets them per session — recommend `SET statement_timeout = '30s'` for the app role (`ALTER ROLE vaultaire SET statement_timeout …`) so a runaway `COUNT(*)` on `events` cannot pin a connection. All 13 `BeginTx` sites `defer tx.Rollback()` immediately after `BeginTx` (verified); no early-return leak. `sslmode=disable` hard-coded (`main.go:158`) — acceptable for `127.0.0.1`. Nil-DB: `main.go` never pings (R9-06); `api/*` has 200+ `s.db == nil` checks but the HEAD path R1 flagged (`s3_engine_adapter.go:279`) is guarded — the concern is moot in prod because `db` is never nil there.

**8. Backups.** Cron `0 3 * * *  /opt/vaultaire/bin/pg-backup.sh` (user1's crontab). Newest `vaultaire_20260926_030001.sql.gz`: 03:00 UTC today (13.5 h old at review), 37,264,892 bytes, 87 `CREATE TABLE`, 87 `COPY` blocks, produced by pg_dump 16.13 (with the `\restrict` header — needs psql ≥ 16.10/15.14 to replay). Script has size and DDL asserts and fails loudly; `backup.log` shows daily "Backup completed" lines. Also backs up `configs/` (incl. `.env`) and Prometheus rules; 7-day `find -mtime +7 -delete`. Gaps: plain format, 0664 perms, no off-box copy, no in-repo restore runbook (R9-12). **What a restore loses:** everything written only to local disk — `DATA_PATH=/opt/vaultaire/data` (120 KB; the `local` driver's containers, e.g. the letshow demo buckets) and `/tmp/vaultaire-data` (704 KB), multipart staging dirs, and up to 24 h of DB writes (head cache rows, quota counters, versions, sessions, STS tokens, chunk refs — the last means objects chunked after the dump are unreadable after a restore even though the chunks exist on the backend).

**9. Test infrastructure.** `testutil.DSN()` precedence: `DATABASE_URL` > `TEST_DB_*` > `vaultaire_test`. Only 6 test files used it; 27 read `DATABASE_URL` directly (3 of them with a dev-DB fallback), and `database/postgres_test.go` duplicates the parser because of the import cycle. Destructive statements: `usage/manager_test.go` (12× `DROP TABLE`), `api/{usage,quota_management}_test.go` (2× `DROP TABLE`), `crypto/gci_test.go` (3× unscoped `DELETE`, never runs), `api/dedup_gc_coherence_test.go:167` (scoped by hash — fine).
