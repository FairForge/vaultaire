**Convergent construction, exactly:** `storeData = zstd(chunk)` if `ShouldCompress(chunk, Content-Type)` and it got
smaller, else `chunk` (`s3_chunked_put_pool.go:193-202`); then `EncryptChunkData(tenant, plaintextHash, storeData)`
→ `AES-256-GCM(key=SHA256(tenantKey‖H), nonce=HKDF(key, H), aad=nil, msg=storeData)` where `H = SHA256(chunk)` is the
**pre-compression** hash. The GCI row identity is `(dedup_scope=tenant, H)`; the row records `ciphertext_hash =
SHA256(blob)` once at first store; dedup hits copy it (`s3_engine_adapter.go:1300-1311`).

**Three attackers**

| Attacker | Learns | Can forge |
|---|---|---|

Can rewrite manifests (`tenant_chunk_refs`) to point one tenant's object at another tenant's `_global` chunk rows — plaintext dedup chunks are readable by anyone who can reference them (the manifest IS the access control for `_global`). |
| **Backend read only** (`_global/_chunks/*`, tenant containers) | Unencrypted chunked and whole objects in full (prod today: everything). For encrypted tenants: ciphertext, sizes, which blobs are shared within a tenant (same storage key), compressibility (CRIME-class length leak, inherent to compress-then-encrypt). With **two ciphertexts under one (key, nonce)** (R8-01) also the XOR of the two messages and, via the GCM forbidden-attack, the authentication key `H` for that chunk key. | Without the master key: nothing under an encrypted tenant. Can swap/overwrite `_global` blobs: caught on read by the plaintext SHA-256 check (chunked) — **not caught on the non-chunked path** (R8-10 / WP-4). |
| **Both + master key** (a box compromise: the env holds the key) | Everything. | Everything. |

**Concurrent PUT re-referencing a chunk the GC is deleting (the interleaving asked for):**

```
GC: candidate scan sees (S,H) ref 0 marked 8d ago
GC: acquire AL(S,H) [session]; invalidate cache
PUT: LookupChunk(S,H) → stale cache or DB row → hit; IncrementRef → UPDATE ... WHERE ref_count row exists
   a) IncrementRef commits BEFORE GC's DELETE: DELETE ... AND ref_count = 0 affects 0 rows → GC "re-referenced" → returns; blob kept ✓
   b) IncrementRef runs AFTER GC's DELETE committed: 0 rows → PUT logs "vanished", mustStore=true → storeChunkLocked
      waits on AL(S,H) (GC still holds it while deleting the blob) → GC deletes blob, unlocks → PUT stores fresh blob + row ✓
   c) GET between (b)'s DELETE and the PUT's re-store: no manifest references (S,H) (ref was 0), so no object can address it;
      a GET that resolved (S,H) from a stale cache before the DELETE fetches a blob the GC is about to delete → fetch error →
      500 (first chunk) / aborted body (later) — a customer never receives wrong bytes, only a failed read to retry.
```

**Chunks are always on the primary:** every chunk `Put` goes through `engine.Put(_global, …)` → `[target,
primary, general failover]`; `_global` has no storage class so the target is the primary; `backend_id` records where
it actually landed (a failover to `lyve` is recorded), and GC hints it back. Smart demotion/promotion exclude
chunked objects entirely (`NOT is_chunked`), so nothing ever moves a chunk; `floor='standard'` for chunked rows is
therefore consistent with reality (R8-18).

## Invariants confirmed

1. **Convergent dedup is per tenant when encrypted, global when not** — `dedupScope = t.ID` (`:1217`) with storage key `_chunks/<tenant>/<hash>`; unencrypted `_global`/`_chunks/<hash>`; `LookupChunk`/`IncrementRef`/`DecrementRef`/cache key all `(scope, hash)` (`gci.go:113-115`). Live: 36 + 36 rows for identical bytes under two tenants; both decrypt with their own key; `TestCrossTenantEncryptedDedup_Isolation` covers it.
2. **A GET never serves bad bytes on the chunked path** — `ciphertext_hash` (row value authoritative, `:1666-1671`) → GCM tag → SHA-256 of the plaintext (`:1578-1581`); first-chunk failure = clean 500, later = aborted body. Live-proven twice (R2 corrupt chunk; R8 missing key → 500).
3. **ETag = MD5 of the plaintext** on every path: the hasher sits before compression/encryption (`hashingBody` tee); chunked (`:1330`), SSE-S3 (`hasher.Sum` after `ReadAll`, `:876-880`), SSE-C (`:829-831`). Live: all head rows' ETag == upload MD5.
4. **Manifest install is atomic with the head row** (`atomicHeadUpsert`, `:1355`), overwrite release is atomic with the new install (`ReplaceObjectManifestTx` `FOR UPDATE`), plain-over-chunked release is atomic (`atomicHeadUpsertReleasing`). Aborted PUTs release every taken ref (`TestChunkedPut_AbortedInstallReleasesRefs`); prod refcount drift = 0.
5. **IncrementRef reports rows affected and callers re-store on 0** (`gci.go:356-377`, `:1283-1293`); the pool's within-upload waiters treat 0 as corruption (`pool:286-290`), which is right because the upload holds a reference.
6. **GC sweep is safe against re-reference** — conditional `DELETE … ref_count = 0`, session advisory lock across row delete → blob delete, cache invalidated before and after (`sweepOne`); the PUT side takes the same lock (`storeChunkLocked`). Live: 36 rows swept, 36 blobs gone, survivor intact; `TestDedupGC_SweepInvalidatesGCICache`, `TestChunkedPut_ReStoresVanishedChunk`.
7. **SSE-S3 construction** is sound per FIPS 203 / RFC 5116: fresh ML-KEM-768 encapsulation per object, HKDF to a one-use AES-256-GCM key, random nonce, versioned blob; the tenant seed is wrapped under the master key with AES-GCM and a random nonce; wrong tenant / corrupted / bad version / short input all rejected (`sse_s3_test.go`). Encryption is skipped, never faked, when the service is absent — but reads then serve ciphertext (R8-04).
8. **SSE-C key hygiene** — parsed per request, MD5-validated, zeroed after use, never in a `zap` field, never persisted; the algorithm marker alone is stored. SSE-C bodies never chunk (#340 gate, `TestSSEC_AboveChunkThreshold_NotChunked`).
9. **Compress-then-encrypt only**; decryption order fetch → hash → decrypt → decompress → hash.
10. **Chunking gate** — `size > 64 MiB ∧ ¬versioned ∧ ¬(GLACIER|DEEP_ARCHIVE|RESILIENT|PUBLIC) ∧ body unencrypted ∧ flag on` (`:924-925`); a flag flip never affects reads (manifests self-describe; `TestHandlePut_ChunkingFlagOff`). The R8-03 gap is that SSE-S3's skip did not use the same predicate.
11. **Prod state is consistent**: 127 rows, 127 refs, 1 manifest, 1 chunked head row, drift 0, nothing marked, no encryption keys, all chunks on `idrive`.
