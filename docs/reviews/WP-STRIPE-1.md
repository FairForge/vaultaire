## Decisions

- **D-EDGE-59** (RP76-1): every bucket has a jurisdiction: its region's first segment (`us`, `eu`, `ap`), or the default region's for an unpinned bucket.
  - A mirror leg must store in that jurisdiction (`legRegion`: `idrive` → `IDRIVE_REGION`, `idrive-<r>` → r, `lyve` → `LYVE_REGION`, us-west-1 by default).
  - A leg of unknown region may hold an unpinned bucket's copy, never a pinned one's.
  - The prompt named only pinned buckets. The red test found that an unpinned US bucket would otherwise be mirrored to an EU leg listed first in `MIRROR_LEGS`, so the rule covers both.
- **D-EDGE-60** (RP76-4): the copy pass's month spend per source is carried in the job's own `job_runs.result` (`egress: {month, spent}`), not a new table.
  - Part 0 has no migration (115 is PR B's), and job state is never in process (the R13 lesson).
  - The cost: a run whose result is not written undercounts by at most that run's bytes (≤ 50 GiB, the run's cap).
  - The budget: `egress_free_multiple × the last backend_capacity stored total − max(vendor month-to-date, this job's month spend)`.
  - A source with no plan row, or a NULL multiple, is unmetered. A metered source with no capacity run yet gets nothing.
- **D-EDGE-61** (RP76-2): the Worker checks the lag on every counted read of the primary's branch (the only place the lag can grow), not on a 500 ms timer. The 5 s after-primary cut is its own timer; the 30 s + 2 MiB/s deadline stays the outer bound.
- **D-EDGE-62** (RP76-2): the Go mirror queue holds copies of the tee's 1 MiB buffers, at most `mirrorMaxLag` (16 MiB) per mirrored write. Cut = request cancelled + pipe closed. A failure that is not a cut (the mirror answered, its pipe broke) is not counted as one.
- **D-STRIPE-1**: `request_suggestions` holds the GENERIC suggestion of each S3 error code, from a static catalogue (`requestSuggestions`, all 49 codes, held to `errorStatusCodes` both ways).
  - It never holds the response's own `WithSuggestion` text, which the prompt said to capture.
  - That text can be "Did you mean `<bucket>`?" (`bucketSuggestion`, `keySuggestion`) or name a key's bucket scope, and the table is shared by every tenant: the first tenant's text would be shown to all.
- **D-STRIPE-2**: the S3 dispatcher records a request ONCE, deferred from the moment the credential resolves a tenant.
  - So a refusal after authentication (an operation the key lacks, a bucket outside its scope, an expired key, the IP allow-list, a suspended account) is in both logs.
  - Before this, the access-log write ran only after the operation switch, and `errorCode` was never set. `s3_access_log` rows now carry their error code too.
  - A refusal before authentication has no tenant and is in neither (it is `vaultaire_auth_failures_total`'s).
- **D-STRIPE-3**: the request id stored is the one the client was answered: the error body's `RequestId` (kept by `noteS3Error`), else the response's `x-amz-request-id`, else the request's `X-Request-Id`.
- **D-STRIPE-4**: `host` is `origin` for the S3 dispatcher (host=slc requests included: the origin's own dispatch writes them). An edge row carries its data-plane host's name (`s3.stored.cloud` for the Worker, `edge` when unknown). No IP address, no user agent.
- **D-STRIPE-5**: the read side is `internal/requestlog` (one reader for the API and the dashboard; the dashboard cannot import `internal/api`). The writer stays the tracker's.
- **D-STRIPE-6**: the free tier on `/pricing` comes from `usage.FreeTierLimits` (a limit, not a price) and its egress from the price file's ratio. `/pricing/` 301s to `/pricing`. The Deep tier is absent until F-38.

## The 0.5.1 regression (found on prod, rolled back in two minutes)

**What happened:**
- The Worker 0.5.1 was deployed at 23:57:58 UTC (version `3c18d368`, every module equal to its row).
- The first measurement PUTs found every mirrored whole PUT failing: `edge_admits` state `failed`, backend status **411**, iDrive's `IncompleteBody`.
- **Cause:** 0.5.1's `putTwo` hands each `fetch` a JS-built `ReadableStream` (the byte counters). Such a stream has no known length, so workerd sent both PUTs `Transfer-Encoding: chunked` with no `Content-Length`. The 0.5.0 tee branches of the request body kept its length.
- **Rolled back** to 0.5.0 (`ebb3decb`) at 23:59:49 UTC.
- **Impact:** only tenant zero's three 64 MiB test PUTs, which failed and were retryable. In the same window 128 multipart parts committed normally (parts are never mirrored at the edge), and no other tenant made an edge write.

**Why the tests passed:** Node's `fetch` sends an explicit `content-length` header for a stream body, and every fake server accepted chunked bodies.

**The fix (#1042):**
- Each body goes through `new FixedLengthStream(n)` where the runtime has it, as the codec's chunk PUTs already did.
- A unit test records that `putTwo` asks for the length.
- **Reproduced and fixed in workerd itself**: `wrangler dev --local` with a Node sink that answers 411 to a body with no length.

| `putTwo` in workerd (4 MiB body) | primary | mirror |
|---|---|---|
| 0.5.1 | chunked, no length → 411 | chunked, no length |
| 0.5.2 | `content-length: 4194304` → 200 | `content-length: 4194304` → 200 |

RP76-2's bound in workerd's own backpressured tee (Step 0.1's shape), with a 64 MiB body and a mirror reading at 2 MB/s:

| | client time | the mirror |
|---|---|---|
| 0.5.0's `putTwo` | **34.75 s** (held at the mirror's pace) | got all 64 MiB |
| 0.5.2's `putTwo` | **0.74 s** | cut after 1.5 MB (16 MiB of lag), `mirror_cut: true`; the primary got all 67,108,864 bytes |

**Lesson for the next Worker change:** a body handed to `fetch` must keep its length in workerd. The workerd lab (a sink that refuses a length-less body) is the test to run before a deploy. A Node fake is not enough.

*Setup:*

- A smoke test first: one 64 MiB mirrored PUT, committed 200, its `lyve` copy `ready`.

| | `edge_mirror` ON | OFF | what took the bytes |
|---|---|---|---|
| `aws s3 cp` 256 MiB (aws-cli defaults: 8 MiB parts) | 126.6 MB/s | 57.6 MB/s | edge UploadParts: **never mirrored at the edge** (D-EDGE-49), so the difference is run-to-run noise |
| `aws s3 cp` 1 GiB | 195.6 MB/s | 174.4 MB/s | the same |
| `put-object` 64 MiB whole (×3) | 12.9 / 12.1 / 9.8 MB/s (5.2–6.8 s) | 28.7 / 26.8 / 25.2 MB/s (2.3–2.7 s) | edge-admitted PutObject on `idrive`, **mirrored to `lyve`**: all three copies `ready`, `vaultaire_blob_copies_total{outcome="cut"} 0` |
| `put-object` 96 MiB whole (×3) | 26.8 / 22.6 / 30.4 MB/s | 28.8 / 34.0 / 20.9 MB/s | a chunked placement (over 64 MiB): the origin's, never the edge's |

*What it says:*
- **The edge mirror only applies to a whole PutObject of 4–64 MiB.** That is under Cloudflare's 100 MB request limit (a 256 MiB single PUT is Cloudflare's 413) and at or under the chunk threshold. aws-cli's default `cp` never takes it.
- **On that path, a healthy but slower mirror leg still costs the write about 2.3×:**
  - 0.5.2 lets the primary run 16 MiB ahead, then the tee paces it to the mirror.
  - `putTwo` then waits up to 5 s for the mirror's answer before it commits.
  - A 64 MiB body therefore finishes at about the mirror's pace for 48 MiB, plus its answer.
  - What RP76-2 asked for holds: the cost is bounded. A stalled leg (the 2026-10-17 shape) is cut at 16 MiB of lag or 5 s past the primary, never a 60 s stall. The workerd lab shows the cut: 0.74 s against 0.5.0's 34.75 s with a 2 MB/s mirror.
  - Not stalling is not the same as costing nothing: RB7-13.
- The measurement objects were deleted (DELETE removed the leg copies; their five rows are the `blob_copies` orphan pass's, as designed).

## Open questions

1. **RB7-13: should a mirrored PUT wait for its mirror at all?** On prod a healthy Lyve mirror makes a 64 MiB whole PUT 2.3× slower (2.5 s → 5.8 s). Two options, both cheap:
   - (a) lower the lag bound to 4 MiB: the mirror is cut sooner, and the job writes more copies;
   - (b) commit when the primary answers and settle the mirror in the background (`ctx.waitUntil` + a second commit call `mirror_etag`): the client never waits for the leg.

   **Recommend (b)**: the copy row is `pending` until the mirror's ETag arrives, which the job already handles. RP78 decides.
