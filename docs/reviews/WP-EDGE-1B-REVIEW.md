## Findings

| # | Sev | Finding | Fix |
|---|---|---|---|
| RP66-1 | **P2** | **A stored `Content-Encoding` is re-encoded by the Workers runtime.** `readResponse` builds a NEW `Response` from the backend's body under the ORIGIN's headers, and a row with `content_encoding` set (`s3_content_encoding.go`: a client's pre-compressed upload — static-site deploys, `gzip` assets — stores and echoes it) puts `Content-Encoding: gzip` on that Response. A Workers `Response` defaults to `encodeBody: "automatic"`, under which the runtime COMPRESSES the body to match the header it is given (Cloudflare's `Response` docs: "to serve data that is already compressed, this property has to be set to `manual`"). The fixed-bucket driver (iDrive and the regions) never sends `ContentEncoding` to the backend (`s3upload.go` passes `ContentType` only), so the backend's answer carries plain gzip bytes with no encoding header: the runtime gzips the gzip, under a `Content-Length` of the row's size that no longer matches. Lyve's single-PUT path does store it (`lyve.go:260`), so there the backend's body arrives marked and the passthrough rule may hold — two backends, two behaviours, neither proven. The origin serves such an object correctly today. Not in the pass-through matrix. | `edgeAdmitGet`: a row with `content_encoding != ""` passes through (`passThrough("content_encoding")`), a matrix row. Residual: `encodeBody: "manual"` on the client Response plus a subrequest that is not decoded (both backends, a lab probe) would bring those objects to the edge — Prompt 46b's Step 0. |
| RP66-2 | **P3** | **The edge serves bytes no one checks, and nothing counts that.** The origin verifies every whole 200 against the row's digest and cuts a short or wrong body (`object_integrity.go`, `vaultaire_object_integrity_unverified_total` for what it cannot verify). The edge path serves what the backend sends under the row's `Content-Length` — a truncated blob reaches the client as a short body with no server-side trace, and no counter says the edge path is unverified by design. The cheap half is a length check: the backend's `Content-Length` at the headers must equal the admitted span (`readCommit` already reads it). | `index.js` `readSucceeded`: `status === expect_status` AND (no `content-length` header OR its value equals the admit's `content_length`, a new field of the admit answer) — a mismatch is a `fallback` (the origin's integrity path then decides and logs); `settleEdgeGet` counts every `served` read in `vaultaire_object_integrity_unverified_total{path="edge",reason="unverified"}`. Worker 0.2.1 (a manifest row). Bit-rot of equal length stays with the backend's own checksums — written as a decision. |
| RP66-3 | P3 | **An edge read does not touch `last_accessed`.** `HandleGet` refreshes it on every cache hit (`s3_engine_adapter.go:515–520`, fire-and-forget); `settleEdgeGet` does not. The daily `smart_demotion` job reads it: an object read daily through the edge looks idle and is demoted after `SMART_DEMOTION_IDLE_DAYS`, after which its reads pass through (`demoted`) and promote it — correct, slower, and a tape round trip for nothing. Both Smart gates are closed on prod today (the flag OFF), so no customer is affected yet. | `settleEdgeGet` (served): the same detached `UPDATE object_head_cache SET last_accessed = NOW()` the origin runs. |
| RP66-4 | P4 | **A lost GET commit whose request the origin then served is metered twice.** The Worker's fallback is `fetch(request)`; its commit rides `ctx.waitUntil` with one retry. If the commit is lost (or the admit answered after the Worker's 10 s and the Worker went to the origin), the origin meters its serve AND the reaper meters the admitted size 20 min later (RB-6's half). Needs a control plane that answered the admit and then lost the commit while the origin served — rare. | Accept and document; or the Worker's fallback request carries `x-vaultaire-edge-fallback: <admit_id>` and `serveGetObject` (a Cloudflare peer only) settles that row `failed` detached after serving — ~20 lines, a later part. |
| RP66-5 | P4 | **The `x-amz-request-id` the client sees is not the one the logs hold.** `edgeAdmitGet` puts `generateRequestID()` on the response headers; the admit row, the access-log row and the Worker's log line carry the Worker's `request_id`. A customer quoting the header from a failed download cannot be found. `commitEdgePart` already sets `reqID = row.RequestID`. | `hrec.Header().Set("x-amz-request-id", req.RequestID)`. |
| RP66-6 | P4 | **One `edge_admits` row per range, kept 7 days.** aws-cli downloads in 8 MiB ranges (the prod proof: 29 admits for 243 MB); a 1 TB download writes ~131,000 rows, each with its access-log row and `object.downloaded` event (the origin writes the same two per range, so those are parity), and the terminal rows stay 7 days. The retention was sized for writes. | The reaper purges terminal `get` rows after 24 h (nothing later reads them; the access log has the bytes); writes keep 7 d. |
| RP66-7 | P4 | **A backend answer without `Content-Length` meters the admitted size with a Warn per read.** `readCommit` sends 0, `settleEdgeGet` warns and clamps. Neither backend answers a ranged GET chunked today. | Fold into RP66-2: no header = no length check, metered as admitted, Debug not Warn. |
| RP66-8 | P4 | **The stored Prompt 46 has two design errors** (not code; recorded here, the prompt rewritten in this PR). (1) Its D-EDGE-16 has the Worker send `HMAC(per-admit key, sha256(chunk))` and the control plane "re-derive and map to the tenant keyed hash" — impossible: `HMAC(K_tenant, h)` cannot be computed from `HMAC(K_admit, h)` without `h`. (2) It names the dual-key stream format `0x04` and says the chunk is sealed "in 0x03's segments": `0x04` is the CURRENT `StreamFormat` (every writer since WP-R8-3 A.2; `0x03` is opened only) and `0x05` is the SSE-C multipart header (`crypto/ssec_multipart.go`). | The Worker sends `sha256(chunk)` over the service-token channel; the control plane HMACs it with the tenant index key, in memory for the call, never stored or logged (`TestIndexHoldsNoPlainHash` tests storage, logs and metrics); the new format byte is `0x06`, verified against `stream.go` before use. |
