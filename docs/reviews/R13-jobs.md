## The job table

Trigger = what starts a run; Flag = feature-flag gate; Ctx = the context the goroutine runs on;
SF = single-flight protection; Overlap = can two runs of the same job overlap in ONE process
(the deploy is stop→swap→start on one box, so two binaries never overlap — but the admin
trigger and the ticker can); Tx = DB transaction boundaries; Cap = per-run bound; Fail =
failure handling; Metrics = series emitted; Stop = what happens at `Shutdown`.

## Invariants confirmed (R15 can trust these)

1. **Smart demotion never touches chunked objects, versioned buckets, `tier_preference='performance'` buckets, objects < `MinAge`, or empty objects** — `smart_demotion.go:277-283` (`NOT o.is_chunked AND o.size_bytes > 0 AND created_at < $3 AND NOT EXISTS (versioned OR performance)`), and the flip itself repeats `NOT is_chunked` (`:366`). Object Lock / legal hold are **not** checked — but demotion never destroys bytes (copy, flip, reclaim-under-guard), so a locked object stays intact and readable; recorded as a design note, not a finding.
2. **`floor` never changes on demotion or promotion** — the flip UPDATEs set `backend_name` (and `last_accessed`) only (`smart_demotion.go:364-367`, `smart_promotion.go:188-190`, `:284-286`); the bill does not move (R10 ledger).
3. **Every move updates `object_head_cache.backend_name` in the same transaction as the ledger write** (`smart_demotion.go:358-398`, `smart_promotion.go:180-202`, `:276-296`); `object_locations` is never written by the jobs (R6 fact re-confirmed: `grep object_locations internal/api/smart_*` → nothing) and `HintBackend` only mirrors the committed value.
4. **Cold write succeeds, ledger insert fails → no data loss:** the flip and the ledger insert are one tx; a failed insert rolls the flip back, the cold copy is an orphan (money) that the next run re-creates (R13-08 makes the trigger not cancel it). **Ledger insert succeeds, cold write fails** cannot happen (the write precedes the tx). **Reclaim `hot.Delete` succeeds, ledger update fails:** the row stays open; the next run finds the head row still cold with the same etag and re-issues the (idempotent) delete, then closes it. No path deletes the last copy except R13-01 (fixed) and the R2-05-class window in R13-06.
5. **Hot budget = 15 % × the `standard` floor limit (or the total when no floor row) + `pin_hot_bytes`** — `smart_demotion.go:191-197`, `:262-263` (R10-07 verified); the flag defaults OFF and is checked per tenant (`server.go:176`, `smart_demotion.go:224`); the knobs are bounded (R13-19).
6. **Dedup GC and smart demotion cannot touch the same bytes:** demotion excludes `is_chunked` rows and works on `<tenant>_<bucket>` containers; GC works on `_global` chunk rows only (`dedup_gc.go:247`). No lock ordering issue exists because they share no lock and no row. The GC's per-chunk **session** advisory lock is the same `(hashtext(scope), hashtext(hash))` pair the PUT path takes as a transaction lock (`s3_engine_adapter.go` `storeChunkLocked`, R8), acquired one at a time — no nested acquisition, no deadlock.
7. **Every alert rule's metric exists in code with the same labels:** `vaultaire_backend_health/probe_failures_total/circuit_open{backend}`, `vaultaire_backend_write_failures_total`, `vaultaire_errors_total`, `vaultaire_requests_total` (`prom_metrics.go:32-98`), `vaultaire_auth_failures_total{reason,key_known}`, `vaultaire_auth_failures_by_key_total{key_hash}` (`auth_metrics.go:28-35`), `vaultaire_dashboard_login_failures_total`, `_lockouts_total` (`dashboard/metrics.go:13-20`), `vaultaire_tls_cert_expiry_timestamp_seconds{sni}`, `vaultaire_tls_cert_probe_ok{sni}` (`cert_expiry.go:221-224`). `idrive-<region>` and `permafrost` probes register through `RegisterBackend` (`server.go:541`) and therefore appear in `vaultaire_backend_health` (R1-12 closed by R7; `TestBuildBackendProbes_RegionDriversWithOwnKeysAreProbedStaggered`, `_PermafrostUsesDriverProbe`).
8. **Probes are authenticated where a driver exists, TCP only for quotaless** (`backend_probes.go:61-136`); each probe is bounded (15 s / 45 s) and the breaker is untouched by probes (they update `BackendHealthChecker` only — the engine's breaker is driven by request failures, R6).
9. **Flag cache:** `Refresh` fails → last-known snapshot kept (`flags/service.go:126-149`); boot does a synchronous `Refresh` before `Start` and before `setupRoutes` (`server.go:179-183`), so the first request sees DB state; nil-DB serves in-code defaults.
10. **STS, session and idempotency cleanups delete by expiry only** (`sts.go:132`, `auth.go:310`, `idempotency.go:149`), hourly, on the `Start` ctx; exactly one idempotency sweeper (R11-20).
11. **Shutdown order** (`main.go:42-47`): HTTP drain + sync tracker flush → engine (`db.Close`). Ledger tables cannot be left half-written (every job write is one tx or an idempotent statement); the multipart staging dir is consistent (reaper removes dirs after the row flip; purge re-sweeps); audit rows are written synchronously with a detached ctx (`audit.go:143`) so a client disconnect never loses one.
12. **Deploy overlap:** `deploy.yml:84-88` is `systemctl stop` (blocks until exit) → swap → `start`; two binaries never run at once. The only in-process overlap is ticker vs admin trigger (R13-05, closed).
13. **`StartTiering` has no caller** (grep on `main` and this branch): the tiering engine never moves data (R6 fact holds; docs/ARCHITECTURE.md:198 "the only mover of customer data between backends is the Smart-tier demotion job" is accurate — plus the read-time promoter, which is the same subsystem).
14. **`audit.Record` is synchronous**, not fire-and-forget (correction to the prompt's assumption).
15. **Bandwidth alert dedup:** once per (tenant, threshold, type) per calendar month via `last_fired_at >= month start` (`bandwidth_alerts.go:180-190`); state resets at rollover without any write. Seeding is idempotent (`ON CONFLICT DO NOTHING`).
