# WP-R5-14 — the primary key pair can be rotated and revoked, for real

**With:** WP-R5-5 (STS IP intersection + parent-revoke cascade), WP-R5-10 (JWT revocation on
password change), WP-R5-9 (`api_keys.tenant_id`, folded in).
**Branch:** `wp/R5-14-credential-lifecycle` · **migration:** `076_credential_lifecycle.sql` ·
**date:** 2026-10-03 · **base:** `main` @ `350203f` (#564).

## The bug, as first seen

WP-R10-3b's note (2026-10-03, live on the dev build): rotating the `primary` row through
`POST /api/v1/user/apikeys/{id}/rotate` revoked that row and minted a `VLT_` key, but
`tenants.access_key` stayed what registration wrote, and every request signed with the
"rotated" pair — SigV4 header auth, the presigned export link — still answered **200**.

Why: registration wrote the pair twice (`tenants.access_key/secret_key` and an `api_keys` row
named `primary`, R12-02). `RotateAPIKey` / `RevokeAPIKey` wrote `api_keys` only;
`grep "UPDATE tenants SET access_key"` = 0 in the product. `lookupCredential` (header auth),
`verifyPresignedURL` (its own copy of the lookup) and `accessKeyExists` (the metric's
`key_known`) all resolved `tenants` **first**, with full `*` permissions and no revocation
check. The one credential every account has, shown once at registration, could not be killed.
A revoked key was also still in the in-process `keyIndex` until the next restart, and an STS
token minted from a key kept working after the key was revoked (`parent_key_id` was a free
string — `"tenant:<id>"` by default, a parent that could never be revoked).

Prod, read-only (2026-10-03, `vaultaire-slc`): 5 tenants, every one with a `primary` row whose
`key_id = tenants.access_key`, none revoked; **0 tenants lack a key row** for their pair, 0 lack
a user; 5 `api_keys` rows, 0 revoked; 0 `sts_tokens`; `users` had no `password_changed_at`. So
the `tenants` fallback for a key with no row could be dropped outright, and was.

## What was built

**One source of truth: the `api_keys` row is the credential** (migration 076).

- `api_keys.tenant_id` (WP-R5-9) — backfilled from the `users.email = tenants.email` join,
  indexed, kept **nullable**: a `SET NOT NULL` would fail a `make test-db` re-run on a shared test
  database with fixture leftovers, so instead a row the backfill could not attach never
  authenticates (`TestLookupCredential_RowWithoutTenantIsRefused`). No lookup joins on e-mail any
  more: `TestScopedKey_SurvivesAnEmailChange`.
- `api_keys.is_primary` — backfilled from `tenants.access_key = api_keys.key_id`; **one live
  primary per tenant** by a partial unique index (`idx_api_keys_one_live_primary`).
- `tenants.access_key/secret_key` — a **mirror** of the live primary pair: rewritten by the
  rotation transaction, loaded at boot as the tenant's pair, read by no credential lookup
  (`TestLookupCredential_TenantsPairWithoutARowIsUnknown`: a tenants pair with no row is unknown).
  Kept rather than dropped so an operator's `SELECT access_key FROM tenants` and the admin support
  search still say the truth (the search now also matches any key id of the tenant).
- `users.password_changed_at` (WP-R5-10) — `updated_at` is also written by the profile form
  (`settings.go:86`), so it could not carry the meaning.

**One lookup.** `auth.Auth.LookupCredential` (exported; was `lookupCredential`) is what the S3
header path, `verifyPresignedURL` (its private copy deleted) and the STS path use:
`api_keys` by `key_id` → a revoked row is the new typed `auth.ErrAccessKeyRevoked`, a NULL
tenant is refused, expiry stays in the scope for `handleS3Request` to enforce; then
`sts_tokens` for `ASIA` ids **LEFT JOIN the parent key** — parent missing, revoked or expired is
`ErrAccessKeyRevoked` too (WP-R5-5's cascade: nothing is deleted, no race, one query on the hot
path). `tenants` is not in the query.

**Rotation is one transaction** (`rotateRows`): `UPDATE api_keys SET revoked_at … WHERE
revoked_at IS NULL` (zero rows = `ErrKeyRevoked`, so of two concurrent rotations exactly one
succeeds — `TestPrimaryKey_ConcurrentRotationOneWins`, and live below), INSERT the successor with
the old scope and `is_primary`, `UPDATE tenants SET access_key, secret_key` for a primary. In the
same call the old key leaves the in-memory `keyIndex` (`markRevokedLocked`; it used to
authenticate from the cache until the next restart — the "same process" adversarial case) and the
successor becomes the tenant's in-memory pair. The audit row (`key.rotated`) carries `primary`
and `sts_tokens_invalidated` (unexpired children, counted).

**Revoke of the primary is refused** — `auth.ErrPrimaryKeyRevoke`: dashboard flash ("rotate it
instead"), user API **409**, management API **409 `primary_key`**. The decision, over
"NULL the pair": an account must keep one way in, and three surfaces mint from the primary (the
export download link, `GET …/presign`, the credentials pages); rotation is exactly "kill the
leaked pair" and hands the successor over in the same response, so refusing revoke never leaves a
leaked key alive longer. A scoped `VLT_` key with `*` is not the primary (`is_primary` is the
only marker; `TestScopedFullAccessKey_IsNotThePrimary`) and is revoked like any other key.

**Every credential surface reads the row:** registration response (the `APIKey` the service
returns, `IsPrimary = true`), dashboard keys page (`primary` badge, **Rotate** button on every
live key, Revoke hidden for the primary and refused server-side), `onboarding.go` (subselect of
the live primary), `presigned.go` and `account_export.go` (`auth.PrimaryPair`), the export's
tenant section (`primary_access_key_id` subselect) and keys section (`is_primary` per key),
`auth_metrics.go` (`accessKeyExists` = any `api_keys` row **including revoked** or an STS token),
`checkKeyCap` (`NOT is_primary` instead of the `tenants.access_key` subselect), `LoadFromDB`
(`keyIndex` from live rows only; the live primary overwrites the tenant's pair).

**The failure a dead key gets:** 403 **`InvalidAccessKeyId`** (new S3 code, AWS's for a key that
no longer exists) on header auth and presigned URLs (`presignError`: `Error()` is the S3 code so
`handleS3Request`'s switch keeps working, `Unwrap()` the cause so the metric can tell revoked
from unknown), counted as `vaultaire_auth_failures_total{reason="revoked"|"presign_revoked",
key_known="true"}` + the per-key hash series — the existing rule
(`sum(rate(…{key_known="true"})) > 0.2`) pages on a burst against a dead key.

**WP-R5-5.** `intersectIPRestrict` replaces `narrowIPRestrict` (which returned the REQUESTED
list whenever both sides were set — a token could drop the parent's restriction): no parent
restriction → the request's, validated; no request → the parent's; both → every requested entry
that lies inside some parent entry (same family, parent contains the network address, no wider
mask), none = `ErrSTSScope` → 400 `scope_error`. A token's TTL is clamped to the parent's
`expires_at`; an expired parent mints nothing. The STS route's default parent is now the
**primary row** (`GetPrimaryAPIKey`), never `"tenant:<id>"` — so a rotation of the primary kills
the tokens minted from it (live below).

**WP-R5-10.** `ValidateJWT`: `jwt.WithIssuer("vaultaire")`, `jwt.WithIssuedAt()`, `iat`
required, the user must be in `userIndex` (an erased / evicted user's JWT is refused — it was not
before), and `iat.Unix() < password_changed_at.Unix()` → `auth.ErrJWTRevoked` ("token issued
before the last password change", 401). Second precision on purpose: a token minted in the same
second as the change survives, one minted before does not, and a login right after a reset never
races the stamp. `setPassword` stamps the row and the in-memory user with one timestamp from
`ChangePassword` and `CompletePasswordReset`; `LoadFromDB` loads it. The dashboard session the
change was made from survives (`DeleteByUserIDExcept`, R12 — unchanged, re-proven live); the
API JWT holder signs in again. Audit metadata: `jwts_invalidated_before`.

**Locks.** `cacheMu` now covers every reader and writer of the credential maps in
`internal/auth` (`findOwnedKey`, `ListAPIKeys`, `GenerateAPIKey`, `GetOwnedAPIKey`,
`ChangePassword`, `CompletePasswordReset`, `ValidateJWT`, `record`, `GetUserIDByTenantID`) —
the WP-R5-6 "~25 readers predate it" note is closed, nothing widened.

## Decisions

- **Revoke of the primary is refused; rotate is the kill switch** (reasons above). Not: NULL the
  pair (three surfaces mint from it), not: promote another full-access key (silently changes what
  the export signs with).
- **`tenants.access_key/secret_key` stay as a mirror**, rewritten in the rotation transaction,
  read by no lookup. Dropping the columns is a later migration once nothing operational reads them.
- **`api_keys.tenant_id` nullable**, no FK: a `SET NOT NULL` / FK cannot be made idempotent on a
  shared test database with orphan fixture rows; a NULL row never authenticates. Prod has none.
- **The STS cascade is a join, not a delete**: no race between revoke and a request, and the audit
  row counts the children.
- **JWT `iat` at second precision**; the dashboard session that changed the password survives.
- **`InvalidAccessKeyId` for a dead key**, unknown ids keep `AccessDenied` (unchanged behaviour,
  R11's metric tests).
