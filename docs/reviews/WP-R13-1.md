## The rule

`engine.CustomerStorageClass(floor, backendName)` (`internal/engine/storage_class.go`) is the
one place the class a customer sees is derived:

| `object_head_cache.floor` | Class |
|---|---|
| `standard` (downstairs) | the backend's class, **never an archive class**: `geyser` → `STANDARD`. `idrive`, `idrive-<region>`, `lyve`, `r2`, `permafrost`, `s3` → `STANDARD`; `local` → `REDUCED_REDUNDANCY` as before (dev only) |
| `vault` (attic) | the backend's class, as before: `geyser` → `GLACIER`; an attic write that fell back to the primary is readable and says `STANDARD` |
| anything else | treated as downstairs |

**NULL floor:** it cannot occur. Migration 066 added the column as `NOT NULL DEFAULT 'standard'`
and backfilled `vault` for `archive` buckets and for rows on `geyser` with no ledger row, so a
row older than 066 is either an attic row or a downstairs row, never unknown. Prod on
2026-10-02 (read-only): 5,223 `standard` rows on `idrive` / `local` / `lyve` / `onedrive` /
`permafrost` / `r2` / NULL backend, 2 `vault` rows on `geyser`, **0** `standard` rows on
`geyser`, **0** `vault` rows off `geyser`, 0 `smart_demotions` rows, 0 `feature_flags` rows.
**Can the job move such a row?** The job selects on `backend_name = 'idrive'` and never reads
or writes `floor`: it moves any whole object on the hot backend, including a `vault`-floor one
that fell back there (none in prod). That object then presents as GLACIER (its floor) while
carrying a ledger row, so a GET promotes it like a downstairs object. Left as it is; it is
written down in *What is deliberately not done*.

### RestoreObject on a demoted Standard object — the choice

**403 `InvalidObjectState`, no backend call**: what AWS answers for RestoreObject on a STANDARD
object, with a message that names the class and says to read it with a plain GET. The
read-time promotion (`smart_promotion.go`) is what brings the object back: a GET either serves
it (hot copy still there → routing flip; hot copy reclaimed → served from the cold backend's
staging disk + asynchronous copy-back) or, when the bytes are on tape, submits the recall
itself. Accepting a RestoreObject for it would have told clients the object is an archive
object after all, and the listing says it is not.

### A read of an object whose bytes are on tape

`SmartPromoter.OnArchivedRead` + `writeArchivedRead` (`smart_promotion.go`) are one
implementation for GetObject, the CopyObject source and `/cdn`. The rule is the floor:

- **Downstairs object** → the recall is submitted on the reader's behalf (once; again when the
  recorded request is older than `RestoreRetry`, 6 h, and the object is still on tape) and
  the answer is **503 `ServiceUnavailable` + `Retry-After: 120`**, message: *"This object has
  not been read for a while and is being brought back from cold storage. No action is
  needed: retry the request. It is usually readable again within a few hours."* The code
  stays `ServiceUnavailable` (every SDK retries it); the message no longer says the backends
  are unavailable (`WithMessage`, a new `ErrorOption`), and `x-amz-storage-class: GLACIER` is
  no longer sent with it. **`markClientRefusal`**: it is one object's state, not a server
  failure, so it stays out of `vaultaire_errors_total` — a customer syncing a bucket of
  evicted objects must not fire `VaultaireServerErrorRatio`.
- This holds **with or without a ledger row**. A downstairs object on tape with no
  `smart_demotions` row (a lost row; a deployment whose primary is the archive) is STANDARD
  to the customer and RestoreObject refuses it, so a 403 "request a restore" would have been
  a dead end. It is restored on read; nothing copies it back hot, and it is logged at Warn.
- **The recall could not be submitted** (backend refused, cold backend has no restore
  concept, ledger unreadable) → the same retryable 503, **not** marked: it is ours and counts
  as a 5xx.
- **Attic object** → 403 `InvalidObjectState` + `x-amz-storage-class: GLACIER`, as before.
- `vaultaire_smart_restore_waits_total{result="restoring"|"failed"}` (server registry, no
  tenant label) counts both, so the refusals the 5xx series no longer shows are visible.

**The other paths that send `Retry-After`** (checked, unchanged): `s3_copy.go` and
`s3_multipart.go` answer 503 for `ErrAllBackendsUnavailable` (30 s) and for a region-pinned
bucket whose driver is not registered (300 s); `s3_engine_adapter.go` the same on PUT and
DELETE. All of them are server-side conditions — a backend down, or an operator who removed a
region's keys after buckets were created in it (creation refuses a region with no driver) —
and they keep counting as 5xx. The CDN's 429s are not 5xx.

### D-23, applied by default — **needs Isaac's confirmation**

(a): region-pinned Standard buckets are documented as always hot, not Smart. No code change.
The FAQ has two new answers ("Do I have to restore Standard data that moved to tape?" and
"Does the Smart schedule apply to buckets in another region?") and the getting-started guide
one sentence. **What the code does, exactly** (`bucketRegionDriver`): a bucket whose region is
*not the default* is on `idrive-<region>` — neither counted in the hot bytes nor demoted. A
bucket created **explicitly in the default region** (`us-central-1`) is served by the primary
and is Smart like any other. The copy therefore says "a region other than the default one",
not "region-pinned". If "I chose a region" should always mean "never moved", that is a code
change (the job would have to skip buckets with an explicit region), not a doc change. Prod
has one bucket outside the default region (`eu-west-1`).

## Adversarial pass — what it found in my own code

1. **A recorded restore request was never repeated — fixed.** `restore_requested_at` was a
   once-only stamp. A restore that landed and expired again before the copy-back ran (the
   daily job had not run — the R13-07 state of prod today) left the object on tape with the
   stamp set: every later read answered "being brought back" and submitted nothing, and with
   this WP that 503 is also hidden from the 5xx series. A request older than `RestoreRetry`
   (6 h) is now submitted again when a read still finds the object on tape (the assertion in
   `…AutoRestoresThenCopiesBack`).
2. **Marking every auto-restore 503 as a client refusal would have hidden a broken restore
   path — fixed before it was written that way.** A dead Geyser key makes every recall fail;
   those 503s are not marked and count, and `vaultaire_smart_restore_waits_total{result="failed"}`
   shows them.
3. **The same bug on the other entry points.** `ErrArchived` had a branch only in `HandleGet`:
   the CopyObject source and the CDN answered 500. Both fixed. The CDN also never promoted
   and never touched `last_accessed` — with the flag on, a public object read every day would
   have been demoted at 14 days, served from staging until Geyser moved it to tape, and then
   failed for every visitor. Fixed (promotion + a once-a-day touch).
4. **A dead end the rule itself would have created — fixed.** With the class from the floor,
   a downstairs object on tape *without* a ledger row would list STANDARD, GET 403 "request
   a restore", and RestoreObject 403 "not an archive object". The read restores it.
5. **The sentence "region-pinned buckets are always hot" against the code path that returns
   first.** `bucketRegionDriver` returns the primary for a bucket pinned to the *default*
   region: that bucket is Smart. The copy says "a region other than the default one" (above).
6. **An anonymous reader now moves data.** A public read promotes: a crawler over a public
   bucket brings its demoted objects back hot and can submit recalls. Bounded by the CDN rate
   limiter and bucket budget, four concurrent copy-backs with one in flight per key, one
   recall per object per 6 h; the job demotes again only after 14 idle days. It is the
   product ("reading it brings it back"), and the alternative was the failure in item 3.
7. **The CDN's error body was framed by the object's `Content-Length`** (noted, not changed,
   in WP-R10-9): every error branch there now drops the object headers and sets `no-store`,
   so an edge cannot cache the wait or a miss under the object's cache lifetime.
8. **Concurrent readers**: two reads racing the stale re-submit both call RestoreObject; the
   second gets `RestoreAlreadyInProgress`, which is success. The stamp is a single UPDATE.
9. **A crash between writes**: nothing here spans two writes — the recall is a backend call
   followed by one UPDATE; if the process dies between them the next read submits again
   (idempotent).
10. **What every gauge reads after a restart**: the new series is a counter (starts at 0, no
    rule reads it). The last-run gauges are WP-R13-3.

## What is deliberately not done

- **The job's selection is unchanged.** It still selects on `backend_name` only: a
  `vault`-floor object that fell back to the hot backend can be demoted (none in prod) and
  then reads like a Smart object while listing as GLACIER.
- **No `x-amz-restore` for a downstairs object that is being recalled.** HEAD says STANDARD
  and nothing else; the wait is visible only on the read.
- **The host-routed CDN (`cdn.stored.ge`) has no logging middleware** — its 5xx were never in
  `vaultaire_errors_total`, and `markClientRefusal` is a no-op there. Not changed.
- **Overwrite of a demoted object still leaks its cold copy** (R13-10, WP-R13-2).
- No changelog entry: the flag is off for every tenant, so no customer can have seen GLACIER.

## What I could not prove

- **The 503 path live.** The local backing store has no tape: `ErrArchived`, the recall and
  the 503 are proved with the archive stub in tests, not with the built binary, and not
  against Geyser (prod is read-only for workers; a real eviction takes ~13 days).
- **How long a real recall takes** — the message says "usually within a few hours", from the
  R13 review's reading of Geyser's behaviour (staging ~13 days, then tape).
- **`aws s3 sync` against a 503**: aws-cli retries a 503 a few times over seconds and then
  reports the file as failed; the next run gets it. Reasoned from the SDK's retry rules, not
  run.

## Decisions taken

- The class rule overrides **archive classes only**: `local` keeps `REDUCED_REDUNDANCY`
  (dev/test backends only; `aws s3 sync` does not skip it).
- RestoreObject on a demoted Standard object = AWS's STANDARD answer, no backend call.
- The floor, not the ledger, decides the read-side behaviour of an object on tape.
- The auto-restore 503 keeps the code `ServiceUnavailable` and `Retry-After: 120`.
- The inventory CSV's last column is `StorageClass` (it was `BackendName`). No bucket in
  prod has inventory enabled.
- D-23 (a), worded as the code behaves.
