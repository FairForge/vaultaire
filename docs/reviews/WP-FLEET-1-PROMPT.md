## What is wrong, measured

1. **The driver writes to whichever drive Microsoft lists first.** `internal/drivers/onedrive.go:1134` `getDriveID` calls `GET /users/{upn}/drives` and takes `out.Value[0].ID` (line 1164). Two of the three fleet users have TWO drives: a hidden system library named `PersonalCacheLibrary` and the real `OneDrive` library, same site id prefix, different drive ids. On `vierafun@viera.fun` and `fromhis@fromhis.com` the cache library is listed first, so **every prod object the fleet holds** — the `t-tenant-*` folders (≈ 0.9–2.6 GiB per account) and the fleet fingerprint `vaultaire/_fleet/fingerprint.json` — sits in the PersonalCacheLibrary; on `vierapics@viera.pics` the OneDrive library is listed first and `vaultaire/` is there. `GET /users/{upn}/drive` (the default drive) is the OneDrive library on every account and shows no `vaultaire/` on the two. Nothing pins the order; a flip makes every object on that account an off-home read (the fallback walk, `tenantsFor` line 261, finds it on no account) and the fingerprint `unknown`. SnapShelter's provider (`~/fairforge/snapshelter/src/services/storage-providers/onedrive.js`) pins `ONEDRIVE_DRIVE_ID` = the OneDrive library of the same user and never had the problem.
2. **A driver DELETE parks bytes in the recycle bin for 93 days, against the drive's quota.** `Delete` (line 549) sends `DELETE /drives/{d}/items/{id}` (line 575); `RemoveContainerTree` / `RemoveEmptyDir` the same (line 709). After one bench day the three fleet drives held **68.4 / 23.2 / 20.9 GiB of recycle bin** against 5 TiB each (SharePoint `site/usage`; the fleet users' live data is ~21 / 9 / 6 GiB). Verified app-only with the fleet data app: `POST /drives/{d}/items/{id}/permanentDelete` answers **204** and the item is gone with no bin entry (v1.0, `Files.ReadWrite.All`). The bin itself is emptied only by the SharePoint REST `POST https://<init>-my.sharepoint.com/personal/<alias>/_api/site/RecycleBin/DeleteAll` with a SharePoint token (`Sites.FullControl.All`) — the data app has no SharePoint role; the admin certificate apps on SLC (`~/vaultaire-bench/fleet-admin/fleet-recyclebin.py`) do.
3. **Graph's `quota` excludes what the bin and the other library hold** (`/users/{upn}/drive` reported `used` 23.11 GiB while SharePoint reported 89.60 GiB for the same user), so a probe reading Graph alone under-reports by 4× today.
4. OneDrive for Business returns `file.hashes.quickXorHash` on a simple PUT, on the upload session's final fragment and on every later GET of the item (no `sha256Hash`); a copy can be verified by it.

## Decisions (made — do not reopen)

- **D-F1-1** `getDriveID` selects the drive whose `name` is `OneDrive` (`driveType` `business`); `TENANT_N_DRIVE_ID`, when set, wins and is used without a listing. Never `drives[0]`. One drive listed = that drive (the new accounts have one). No `OneDrive`-named drive and no pin = an Error at construction naming the drives found, the slot skipped (as an incomplete slot is today).
- **D-F1-2** The fleet marker (`onedrive_fleet.go:48` `fleetMarker`, path `_fleet/fingerprint.json`) gains `drive_id` (additive: a marker without it reads as before). `CheckFleetFingerprint` (line 147) adds a verdict per account: the marker's `drive_id` ≠ the chosen drive = **one Error line per account** naming both ids + `vaultaire_permafrost_drive_mismatch{account}` 1; never an automatic switch, never a block of boot. The marker is rewritten with the chosen drive only through `PERMAFROST_FLEET_ACCEPT` (the existing door) or the migration tool's `-switch`.
- **D-F1-3** Before PR A ships to prod, every slot in prod's `.env` gets its `TENANT_N_DRIVE_ID` **pinned to the drive that holds its `vaultaire/` today** (the cache library on slots 1 and 3, OneDrive on slot 2), so the deploy changes nothing on disk; the migration (PR B) moves slots 1 and 3 one at a time afterwards.
- **D-F1-4** The migration is an operator tool, `cmd/tools/permafrost-migrate-drive`, never a boot action: `-dry-run` (default) lists every drive of the user with the item count and bytes under `vaultaire/`; `-copy` runs Graph `POST /drives/{src}/items/{id}/copy` of `vaultaire/` with `parentReference.driveId` = the OneDrive library, polls the monitor URL, then verifies the copy folder by folder — item count, bytes, and `quickXorHash` per file — and refuses to go on at any difference; `-switch` writes the marker's `drive_id` on BOTH drives' markers (the old one gains `moved_to`) and prints the `TENANT_N_DRIVE_ID` line to set; `-retire` `permanentDelete`s the old `vaultaire/` only after the operator passes `-confirm-retire` and the tool re-verifies the new tree once more. One account per run (`-slot N`).
- **D-F1-5** Every delete the driver makes — `Delete`, `RemoveContainerTree`, `RemoveEmptyDir`, the sweep's `Remove`, the migration's retire — is `POST …/permanentDelete`; a 404 is "already gone" (success); a 403 or 5xx is the error it is today. No DELETE remains (a structural test greps the package).
- **D-F1-6** The probe exports per account, from Graph `drive.quota` (what the data app can see): `vaultaire_permafrost_quota_bytes{account,kind="used"|"total"|"remaining"}` and `vaultaire_permafrost_quota_state{account,state}` (1 for the current `normal|nearing|critical|exceeded`); rule `PermafrostAccountNearFull` (`used/total > 0.8` for 1 h, warn). The bin's size is NOT a product metric in this WP (no SharePoint role on the data app): `onedrive_README.md` documents the operator script and the one-time purge. The one-time purge of the prod drives' bins is the **owner's decision** — ask, do not run it.
- **D-F1-7** `quickXorHash` gets a Go implementation in `internal/drivers/quickxor.go` (port the reference algorithm; a unit test against a vector the tool's `-selftest` records from a live Graph response — upload 1 MiB of a fixed seed, compare). Used by the migration's verify now; the driver's write verification is WP-FLEET-4, not this WP.
- **D-F1-8** No change to placement, the fragment size, the range size, pacing or the slot scheme (WP-FLEET-3/4/5/11). The fleet stays ≤ 15 slots in this WP.

## When a step does not go as written

- Graph `copy` refuses a cross-drive destination: fall back to a per-file copy (download URL → upload session into the target drive, verified by `quickXorHash`), keep `-copy` resumable; note it in the README.
- The reference quickXor port and Graph disagree on the self-test vector: stop, keep the tool's verify on count + bytes only, open a follow-up — never ship a hash check that fails on good data.
- `routing_truth` reports `missing` after a switch: do NOT retire; set the slot's `TENANT_N_DRIVE_ID` back to the old drive, restart, and report what the sample named.
- Anything that needs the owner (the bin purge, a prod `.env` change outside items 6 and 9): stop and ask; everything else in this prompt is yours to do.
