## State machine (item 1)

Container is always `<tenantID>_<bucket>`; every table read/write is `upload_id AND tenant_id` (initiate insert, part/complete/abort/list status checks) before the `upload_id`-only part rows, which cannot be reached without passing that check.

| Transition | DB writes | Disk / backend writes | Crash between them leaves |
|---|---|---|---|
| **Initiate** | `multipart_uploads` row (`active`, + attrs/class after 068) | `mkdir /tmp/vaultaire-multipart/<id>` (0700) | row without dir → UploadPart recreates it (after this PR; before: 500) |
| **UploadPart** (retries / same number) | `multipart_parts` upsert (etag, size, `created_at = NOW()` = reaper activity) — after the file is complete | temp file → rename over `part-NNNNN` (after this PR; before: truncate-in-place) | file without row → replaced by the next attempt, swept with the dir; row without file → complete answers 400 `InvalidPart` (before: 500) |
| **Complete** | reserve quota → *(backend write)* → tx{head row FOR UPDATE, displaced manifest release, head upsert with every column, `status='completed'`} → displaced release → `object_versions` → `object_locks` (bucket default) | pipe of parts → `placeObject` (region driver or engine, class → backend) → `RemoveAll(dir)` | after backend write, before tx: new bytes under the old head row, reservation charged, upload still `active` → client retry heals (R3-15, WP-R2-1); after tx, before `RemoveAll`: dir purged by the reaper's terminal pass |
| **Abort** | `status='aborted'` conditional on `active` (404 otherwise) | `RemoveAll(dir)` | row aborted, dir present → terminal purge removes it |
| **Reaper pass 1** (hourly + boot) | `status='aborted'` conditional (a racing complete wins) for uploads whose newest activity (row or part) is older than `AbandonAge` | `RemoveAll(dir)` | as abort |
| **Reaper pass 2** | `DELETE multipart_uploads` (parts cascade) for terminal rows older than `TerminalRetention` (keyed on the upload's `created_at`, not the terminal time — a long-lived upload completed today is purged on the next pass; harmless) | `RemoveAll(dir)` first (orphan re-sweep) | dir without row (only if `RemoveAll` failed) — never swept (WP-R3-5) |

**The two goroutines at complete** (`:466` writer, `:493` backend put): the writer streams part files into an `io.Pipe`; the put goroutine runs `placeObject` on the request context and closes the read end when it returns, so a failed or cancelled put makes every further `pw.Write` fail with `ErrClosedPipe` and the writer exits. Both are bounded (one each per request, `errCh` buffered 1); neither uses `context.Background()`. Two instances of the reaper are safe without an advisory lock: both passes are conditional UPDATE / idempotent `RemoveAll` / `DELETE` by primary key; prod is single-instance.

## Complete (item 2)

Part order (strictly ascending), per-part ETag equality (quotes stripped) and existence are validated; the final ETag is `hex(MD5(concat(MD5_i)))-N` (live: `a950e4c2…-5` for 5 × 8 MiB, identical across HEAD/GET/List); minimum part size is not enforced (R3-24); the total is bounded only through the per-part cap at upload time (parts ≤ 50 GiB per upload, measured); quota is reserved **at complete** for the assembled size on the floor of the resolved class, settled through the displaced row (overwrite) and released on every failure (verified in code and live: `tenant_quotas.storage_used_bytes == SUM(size_bytes)` after every step of the drive).

**Multipart object vs chunked PUT of the same bytes:**

| | Multipart complete | Chunked PUT (> 64 MiB, `auto`/standard bucket) |
|---|---|---|
| Backend | one whole blob at `container/key` on the class's backend (region driver, Lyve, Geyser, R2, primary) | chunks in `_global/_chunks/<hash>` on the **primary**, no blob at `container/key` |
| Head row | `is_chunked=FALSE`, `backend_name` = that backend (after this PR), `encryption_algorithm=''` (always plaintext) | `is_chunked=TRUE`, `backend_name` = primary, per-chunk AES256-CE when the chunk encryptor exists |
| Manifest | none | `tenant_chunk_refs` + `object_metadata` |
| ETag | `<md5-of-md5s>-N` | whole-object MD5 |
| GET / HEAD | plain path (native Range, integrity unverified — WP-R8-3) | chunked path (SHA-256 per chunk) |
| Copy | streams the blob (`counter.n` authoritative) | manifest copy, no bytes move |
| Versioning | ledger row + version id (after this PR); bytes overwritten in place | refused (chunked objects never enter versioned buckets) |
| Dedup / compression | none | yes |
| SSE-S3 bucket | plaintext (R3-07) | per-chunk encryption |

So GET/HEAD/Copy/Versioning behave identically at the API surface only for the ETag format difference and the encryption gap. **WP-R3-1** closes the gap: at complete, feed the part pipe into `handleChunkedPut`'s pipeline (chunker → pool → manifest) when the class allows chunking, keeping the multipart ETag; depends on WP-R8-4 (chunker identity decided) and is the natural place to add per-part reservations (WP-R10-8).

## Assembly (item 3)

Server-side streaming concatenation: parts are read one at a time into an `io.Pipe` (32 KiB `io.Copy` buffer); the API layer buffers nothing. For a 50 GiB upload in 10,000 parts: disk = the parts themselves (≤ 50 GiB under `/tmp` — the cap), RAM in the API = O(1); the complete step does 10,000 `stat`s (new) and 10,000 `open`s; the S3-class driver side is the manager's 8 × 16 MiB in-flight parts + 1 pooled buffer (R7-23: 144 MiB), local driver = temp file + rename. The framing-corruption fix (item 1.11, #334: `newAWSChunkedReader` on UploadPart, `s3_multipart.go:207-210`) had **no test** — added `TestUploadPart_AwsChunkedFramingIsStripped` (framed body with chunk-signature extensions and a trailer → stored bytes, ETag and size are the decoded payload's). Note for R5: the `chunk-signature` extension is stripped, not verified.

## Abort + reaper (item 4)

Idle abort is activity-based (newest of upload `created_at` and part `created_at`, so a slow live client is never killed); terminal purge cascades parts; orphan dirs with rows are re-swept, dirs without rows are not (WP-R3-5); boot reap runs once at start (live: a row backdated 49 h was aborted and its dir removed within the first second after restart). Two instances are safe (conditional UPDATE). Quota: nothing to release — parts are unreserved (R3-14) and the complete reservation is settled synchronously; the only leak is R3-15's crash window until reconcile. Backend orphan parts: none — the backend never sees parts (the S3-class drivers' own multipart uploads are aborted by the manager on failure).

## UploadPartCopy and CopyObject (item 5)

UploadPartCopy: R3-02 (was a silent empty part; now 501). CopyObject: dispatched as PutObject with `x-amz-copy-source`; source scope check `copySourceScopeDenied` (R5-02) confirmed on that dispatch; REPLACE vs COPY now applies to the whole attribute set (R3-06); cross-bucket same-tenant copy verified live; cross-tenant copy is impossible by construction — the source container is `t.NamespaceContainer(srcBucket)` from the credential's tenant, so another tenant's bucket name resolves inside the caller's namespace → 404 `NoSuchKey` (no 403 path exists because no cross-tenant resolution exists; R5's invariant 4); chunked source into a non-chunked destination = manifest copy (`is_chunked=TRUE` on the destination; a plain source over a chunked destination releases the manifest in-tx); self-copy with metadata change now works (R3-06); Object Lock on the destination refused (R3-01), bucket default retention applied after the copy, versioned destination gets a ledger row (R3-09; chunked sources into versioned buckets stay 501). Memory: streamed (`Get` → counting reader → MD5 tee → driver; the S3-class driver buffers ≤ 144 MiB, R7-23). Lyve CopyObject CRC32 quirk: not relevant — we never issue a backend `CopyObject` (the copy is a Get→Put through the hub), and the Go drivers do not enable `ChecksumMode` (R7-24).

## Batch delete (item 6)

Body 2 MiB, ≤ 1,000 keys (`MalformedXML` beyond, as AWS), quiet mode (only errors), per-key errors (`InternalError` on a backend failure, `AccessDenied` on a lock, `InvalidRequest` on an empty key), a failure mid-batch marks only that key (verified by reading the loop: `continue` per key, no shared state); missing keys are `Deleted` (AWS semantics; live with three keys, one missing). Versioned deletes: not implemented (R3-09, WP-R3-4).

## ListMultipartUploads / ListParts (item 7)

Both tenant-scoped (`:729`, and ListParts through the `upload_id AND tenant_id` status check); no pagination at all (R3-19).

## Invariants confirmed

- **Tenant scoping:** every multipart query carries `tenant_id` (initiate `:83`, status checks `:147`, `:300`, `:646` — now one helper `multipartUploadActive` — abort `:599`, list `:729`); the part-row statements keyed by `upload_id` alone run only after that check; the upload id names the staging directory and is hex-only, so no id from a request can escape `multipartTempBase`. Copy resolves both containers from the credential's tenant. Batch delete: container from the tenant, per-key lock/head/delete all tenant-keyed.
- **ETag:** parts = MD5 of the decoded part; object = MD5-of-MD5s `-N`; copy = MD5 of the streamed bytes; never the empty-string MD5 for a non-empty object (live).
- **Streaming:** no body is buffered in the API layer on any of the three paths; the Complete XML body is the only `ReadAll` and is now bounded.
- **Context and errors:** every DB/engine call takes `r.Context()` (quota bookkeeping deliberately detaches on `quotaCtx`); errors wrapped with container/key.
- **HEAD from `object_head_cache` only:** unchanged; multipart/copy rows now carry every column HEAD reads.
- **Quota:** reserve-before-write on both paths, release on every non-2xx (now including the failed head write), displaced size captured under `FOR UPDATE` and released after commit; `storage_used_bytes == SUM(size_bytes)` held after every live step (checked at the end: `t`).
- **Free-tier bucket cap** sits before any backend write on initiate and copy (live 403 ×4, nothing written).
- **Placement:** all three writers go through `placeObject` (region) and `resolvePutStorageClass` (class); `PUBLIC` still only from `publicBucketStorageClass`; the class header on CreateMultipartUpload is allow-listed by `clientStorageClass` like PUT's.
- **Object Lock:** checked before any write on PUT, complete, copy (plain and chunked), single and batch delete.
- **Chunked overwrite atomicity** (R8 7b): multipart complete and plain copy release a displaced manifest inside the head-row transaction (`atomicHeadUpsertReleasing`).
- **Prod state (read-only 2026-09-28):** `PrivateTmp=no`, `/tmp/vaultaire-multipart` empty, `multipart_uploads`/`multipart_parts` 0 rows, 62 multipart head rows with NULL backend (R3-03), 0 encrypted multipart rows.
