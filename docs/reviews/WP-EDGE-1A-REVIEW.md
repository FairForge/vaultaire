## Findings

| # | Sev | Finding | Fix |
|---|---|---|---|
| RP64-1 | **P2** | **`edgeCommit` runs on the Worker's request context; a commit call that dies mid-settle is replayed WHOLE.** The side effects are detached (`commitEdgePut`/`commitEdgePart` run on `context.WithoutCancel`), but the terminal `UPDATE edge_admits SET state=…` and `tx.Commit` run on `r.Context()`. The Worker aborts its commit call at 10 s (`AbortSignal.timeout`); the disconnect cancels the context, the UPDATE fails, the row stays `pending` — while the head row, version row, bill, notification and `object.created` event are already committed. The Worker's retry 2 s later (or the reaper 20 min later, for the release half) re-runs `settleEdgeAdmit`: a PUT on a **versioned** bucket gets a second version row of the same bytes with the first retained (`KeptByVersion` — the object billed twice) plus a duplicate notification and event; a part's replay runs the settle's delta at `−reserved` and releases a holding the part still has (quota under-count until Complete). A commit that takes > 10 s is not exotic: key-lock contention, a slow DB — and the `edgeDeleteBlob` path (a backend ETag that is not the MD5) takes up to 40 s *inside the transaction*, so there the Worker's timeout fires every time. RE-4 is this bug's sibling on the Complete path; the WP note did not name the admit/commit one. | `handleEdgeCommit` hands `edgeCommit` a `context.WithoutCancel(r.Context())` with its own deadline (the codebase's own rule: the request ending is not a cancel), so the terminal state is written whenever the settle ran. The crash window (process death between `commitBlobWrite` and the UPDATE) remains and is acceptable — note it beside RE-4, whose fix (recognise a landed write on replay) would close both. Move `edgeDeleteBlob` after `tx.Commit` while at it: 40 s of backend delete inside a row-lock transaction holds a DB connection and serialises the Worker's retries. |
| RP64-2 | **P3** | **The part admit discards the upload's recorded encryption.** `edgeAdmit` (op `part`) calls `multipartUploadAttrs` twice and drops `uploadEnc` both times; placement is evaluated with `SSERequested` from the PART request's headers — which never carry the Create's `x-amz-server-side-encryption` (089) or the SSE-C key MD5 (096). (a) An upload created with `--sse AES256` on a plain bucket: every part is admitted and lands plaintext, then Complete's placement says `placeWholeSealed` and the new refusal answers 400 "abort it and upload again" — the retry repeats exactly, an **infinite dead-end** for a client following our own docs (`request_checksum_calculation = when_required` is what makes aws-cli's parts edge-eligible). (b) A keyless part on an SSE-C upload is admitted (the origin's `uploadPartSeal` would answer 400 `InvalidArgument`): the plaintext part lands on the backend, the upload becomes edge, and the client's *correctly keyed* parts are then refused (`ssec` pass-through → staged on an edge upload → 400) — the upload is wedged until Abort, and Complete's sealed/ssec assert would 500. A bucket-level `sse_enabled` is handled (placement reads it); only the per-upload header and key are lost. | The part admit reads `uploadEnc`: `SSECKeyMD5 != ""` → `passThrough("ssec")` (the origin's `uploadPartSeal` then gives the right 400 or seals the keyed part); `SSERequested` → into the `placementRequest`, which makes the first part `placement_whole_sealed` → pass-through, and the upload stays a staged one. Before the flag goes beyond tenant zero. |
| RP64-3 | P4 | **Double quota release when an expiry's transaction fails after the release.** `expireEdgeAdmit` releases the reservation and queues the orphan on `s.db` (outside the row's transaction), then updates the row inside it; if `tx.Commit` fails the row stays `pending` and the reaper's next run releases again (same shape in `edgeCommit`'s own expiry branch and in `expireOne`). Downward drift on `tenant_quotas`, healed only by the admin quota-reconcile. | Release after the commit (the row flip is the guard), or tolerate: rare, customer-favourable, bounded by one admit's size. |
| RP64-4 | P4 | **A pending edge PUT's reservation is invisible to the billed-bytes definition.** `usage/billed.go` counts head rows, retained versions and `multipart_uploads.reserved_bytes` — edge PART admits ride the upload row and are covered, but a PUT admit's reservation (≤ 20 min) lives only in `edge_admits`. A quota-reconcile inside the window erases it; the release/settle then drifts until the next reconcile. The reconcile is admin-triggered, so not live today. | A `+ COALESCE((SELECT SUM(reserved_bytes) FROM edge_admits WHERE tenant_id = … AND state = 'pending' AND op = 'put'), 0)` beside the multipart fragment, when Part B touches this file anyway. |
| RP64-5 | P4 | **A completed edge upload whose `backend_upload_ended_at` stamp failed is unpurgeable for ever.** `completeEdgeUpload` stamps with a Warn on failure; the purge excludes every edge row with a NULL stamp, and the reaper's abort pass takes `status = 'aborted'` only — nothing ever retries the stamp of a completed row. One Warn'd UPDATE failure = one immortal `multipart_uploads` row. | Let `abortEdgeBackendUploads` take completed rows too: `AbortMultipart` of a completed upload answers `NoSuchUpload`, which the driver already maps to success, and the stamp follows. |
| RP64-6 | P4 | **`reserveEdgePart` creates the backend multipart upload inside the open transaction; a commit that then fails leaks an unrecorded backend upload.** No row names its `backend_upload_id`, so neither the reaper nor the purge guard can abort it; it idles on the vendor (our fixed buckets have no incomplete-multipart lifecycle rule). Also 40 s of backend call under the upload row's lock — accepted by design (the concurrent first part must wait), but the leak is not. | Record-then-create (a nullable `backend_upload_id` written before the call, finalised after), or accept and note: the leak needs a DB failure in exactly that window, and a vendor-side `list-multipart-uploads` sweep is a one-liner in `cmd/tools` when it ever matters. |
| RP64-7 | P4 | **`edge/s3-ingest/README.md` still describes the first build**: "while the Worker computes the MD5 and SHA-256 it reports at commit" — contradicted three paragraphs later ("nothing of the bytes") and by the merged Worker. A reader auditing the published script against the README trips here first. | Delete the clause. |
| RP64-8 | P4 | **The legal pages' new sub-processor sentence names `{{host "s3host"}}` — `stored.ge` today — while the edge host is `s3.stored.cloud`.** The sentence stays true (stored.ge is proxied, its upload bytes do transit Cloudflare), so nothing is false; but the host the sentence was written about is named nowhere until `VAULTAIRE_ENDPOINT` moves (WP-DOMAIN-1). | Fine to leave: the disclosure covers the broader fact. If counsel wants the edge host named before the endpoint flips, the sentence needs both hosts, not a different key. |
| RP64-9 | P4 | **A part commit racing Abort relays the backend's `NoSuchUpload` as 503 SlowDown.** The backend refused the part because the upload was aborted between admit and PUT; the settle's default branch answers 503 + Retry-After, the client retries once and then gets the admit's correct `NoSuchUpload`. One wrong answer, converges. | A `req.BackendCode == "NoSuchUpload"` arm in `settleEdgeAdmit` answering `ErrNoSuchUpload` for op `part`. |
| RP64-10 | P4 | **An admit whose answer the Worker never received double-holds the quota for up to 20 min.** The Worker falls back to `fetch(request)`; the origin's own reservation then sits beside the orphaned admit's until the reaper expires it — a tenant near quota gets a spurious `QuotaExceeded` on the fallback write. Self-healing, narrow (a lost admit answer). | Note only; the fallback-not-a-dropped-upload trade is right. |
| RP64-11 | P4 | **Edge writes are invisible to ingress bandwidth and carry no client user agent.** `recordEdgeAccess` writes the access-log row (user agent literally `edge`, though the admit's description holds the real one) and nothing feeds `bandwidth_usage_daily` ingress — the dashboard's ingress chart undercounts an edge tenant. Egress is unaffected (reads stay on the origin), and ingress is not billed. | Keep the client's `user-agent` on the admit row; Part B ("every byte by host") is the right place for the ingress counter. |
