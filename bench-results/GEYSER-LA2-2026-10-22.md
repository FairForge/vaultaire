# Geyser LA2 against LA1 — PUT shapes, threshold, GET width, from SLC, 2026-10-22

Why: LA1's S3 endpoint (`la1.geyserdata.com`, 38.89.89.106) stopped answering at 17:38 UTC —
"no route to host", then TCP timeouts, from SLC and from a Mac — its second multi-hour outage
after 2026-09-19 (~80 min). LA2 (`la2.geyserdata.com`) answered throughout. LA1 accepts no new
collections and ours cannot be resized; prod held 0 Geyser rows, so moving the Vault leg costs
nothing yet. This measures LA2 with the tool and matrix of
`GEYSER-MULTIPART-2026-10-22.md` (LA1, that morning) so the two compare.

Setup: `slc-vaultaire-01` → `la2.geyserdata.com`, the prod key, bucket `la2rot1-…` (the 1 TB
`StoredLA2r1` collection, versioning disabled), objects under `t-_bench-mpu/`. Tool:
`cmd/tools/geyser-put-bench -endpoint https://la2.geyserdata.com` (new flag
`-multipart-min` for §3). Every read-back SHA-256 matched; all objects deleted except the
canary (§5); 0 open uploads, 0 delete markers after. Run 1 20:10–20:24 UTC (single runs),
run 2 20:48–21:02 UTC (3 runs per raw/threshold point, 2 per GET point). LA1 was down, so
LA2 is compared with LA1's morning numbers, never paired.

## 3. A lower threshold on LA2 (`-multipart-min 128MiB`, 3 runs each)

| Size | Streamed | Multipart (driver parts: 64 MiB…) | Gain |
|---|---|---|---|
| 128 MiB | 60–73 (median 67) | 81–95 (median 94) | 1.4× |
| 256 MiB | 71–85 (median 79) | 138–182 (median 177) | 2.2× |
| 512 MiB | 83–94 (median 93) | 184–259 (median 231) | 2.5× |

The driver's fixed 64 MiB part floor is not the limit it looked like in §1: through the
driver, 256 MiB as 4 × 64 MiB (138–182) matches the raw 8 × 32 MiB (133–206). No code change
is needed; `GEYSER_MULTIPART_MIN=128MiB` (the floor's minimum is above 64 MiB) is the setting
for LA2. It would lose on LA1 (Complete's 5 s floor; LA1 §2: 45 vs 63 MB/s at 256 MiB).

## 4. GET width — the read bottleneck is per stream (2 runs each)

| Size | 8 streams | 16 | 32 | 64 |
|---|---|---|---|---|
| 256 MiB | 25–29 | — | — | — |
| 1 GiB | 23 | 41–46 | **83–97** | **167–195** |
| 2 GiB | 19 | — | — | — |
| 4 GiB | 19–23 | 35–44 | **77–79** | **138–140** |

About 2.5–3 MB/s per 8 MiB range stream, near-linear to 64 (the driver's maximum). LA1 read
the same per stream (8 streams 22–28 MB/s, 16 ≈ 41 on 10-04; a Go bench reached 76 MB/s at 32
streams on 07-29), so this is a Vail property, not an LA2 one. **Cost:** a Get holds up to
`GEYSER_GET_CONCURRENCY` × 8 MiB (512 MiB at 64) and nothing bounds that across concurrent
Gets — 20 Vault reads at 64 would hold 10 GiB against prod's `GOMEMLIMIT=40GiB`. 32
(256 MiB a Get) is safe now; 64 wants a process-wide budget like
`LARGE_GET_PARALLEL_BUDGET_BYTES` first.

## 5. Tape: the canary and restore

Kept: `la2rot1-…/t-_bench-mpu/mpu-canary-la2-20261022/default-2147483648.bin` (2 GiB,
16 × 128 MiB, ETag `227d80f1…-16`; same name and ChaCha8 bytes as the LA1 canary, sha256
`cceac3bb…`). SLC user timers `mpu-canary-la2-1024..1027 06:00 UTC` run
`~/vaultaire-bench/mpu-canary-la2/check.sh`: HEAD; once GLACIER, RestoreObject, wait up to 6 h
(`restore_timeout` otherwise), stream back, compare sha256 → `result.jsonl`.

Why it matters: LA2 does evict (the 2026-09-19 canaries went to tape in 33 h–4 days; a plain
GET was then refused `StorageClass: GLACIER`), and the only LA2 restore attempted (09-23) never
finished in 92 min while the console's `restoreToCache` answered 500 — in a bucket that was
found broken by 09-27 (console 18.7 GB, S3 `NoSuchBucket`), so that failure is not yet LA2's.
LA1: 1 GiB restored in ~200 s (09-27). Until this canary restores, LA2 is proven for writes and
reads from the landing zone, not for recall.

## 6. What changes for prod

| Setting | LA1 (today) | LA2 |
|---|---|---|
| `GEYSER_ENDPOINT` / `GEYSER_BUCKET` | default LA1 / `stored3lib-…` | `https://la2.geyserdata.com` / a prod collection's bucket (owner, console) |
| `GEYSER_MULTIPART_MIN` | 1 GiB | **128MiB** |
| `GEYSER_PUT_CONCURRENCY` / `_PART_MAX` / `_BUDGET` | 16 / 256 MiB / 4 GiB | unchanged |
| `GEYSER_GET_CONCURRENCY` | 16 | **32** now (either site); 64 after a process-wide GET budget |
| `backend_plans` row `geyser` | 20 TB (LA1 `Stored3`) | the LA2 collection's size |

Caveats: one evening, LA1 not paired (the 2026-09-19 aws-cli A/B had LA2 at 60–70 % of LA1's
sustained ingest — LA2 may have been quiet tonight); ~40 GiB written and deleted within
seconds in `la2rot1`, which may affect the pending "does 256 MiB alone flush to tape" check of
`rot-test/rot-256m.bin`.
