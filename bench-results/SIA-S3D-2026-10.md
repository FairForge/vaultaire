# Sia via s3d — conformance + bench, 2026-10-21

The Sia network reached through **s3d** (github.com/SiaFoundation/s3d v0.2.1), the
Sia Foundation's localhost S3 gateway: client-side encryption, 10-of-30 erasure
across Sia hosts, paid by the sia.storage account the gateway is registered to.
Account: partner@fairforge.io, **free plan (50 GB)** — all numbers below are on it.
The `sia` driver (PR #825) is `NewFixedBucketS3Driver("sia", …)` against this
gateway.

## Why this exists

Decentralized-backend re-check of 2026-10-21: Solstice (FIP-0118, NV29,
activated ~2026-10-19) deprecated Filecoin Plus DataCap in full — free verified
deals are dead (every new sector gets 10× QAP regardless of content, the service
reward stream pays only Filecoin Pay settled volume). The cheapest surviving
decentralized S3 is sia.storage: Pro $14.99/mo = 5 TB (~$3/TB-mo), Unlimited
$19.99/mo = 10 TB + $4.99/TB over (~$2/TB-mo at 10 TB). Filecoin's remaining
play is the paid Onchain Cloud (~$5/TB, 2 copies, PDP) — proof tier only.
Nothing here beats Geyser's $1.55/TB on cost; this is the privacy/decentralized
story, not a COGS play.

## Conformance (Mac, 2026-10-21)

CreateBucket, PUT (ETag = body MD5), HEAD, GET byte-match, Range GET,
ListObjectsV2, 16 MiB multipart byte-match, DELETE→404: **all pass**.
Post-flush reads match (served from the Sia network, local buffer 0 B).
s3d gaps that don't block a target-only leg: tagging, bucket policies,

## Findings

1. **Vaultaire adds almost nothing to accept latency** — multipart + chunking
   accept 1 GiB at ~295 MB/s; s3d's local buffer absorbs it.
2. **Chunked flushes slower than whole** (~25–30 MB/s vs ~137 MB/s logical):
   a chunked object is ~65 separate ≤16 MiB s3d objects; s3d packs them into
   slab groups (log: "uploading object group … waste 2–28 %") but per-object
   overhead and padding waste dominate against one 1 GiB stream.
3. **Chunked reads have fat tails** (87→7→25→37 MB/s across four identical
   1 GiB GETs): every chunk GET is a fresh Sia host lottery, and one slow host
   stalls the ordered stream; vaultaire's chunk hedge (400 ms) hedges against
   s3d, not against s3d's hosts. Raw whole-object reads were far more
   consistent (85–107 MB/s). **For a `sia` tier, prefer whole objects** —
   `storageClassDisablesChunking` for a SIA class, like RESILIENT/SYNC — or
   accept the tail.
4. **Durability semantics**: like the Sync bridge, a 200 is not on-Sia.
   A `sia` leg needs either flush-aware settlement or acceptance of the lag
   (s3d's auto-flush interval is configurable upstream since 2026-10-20).

## Optimized run (2026-10-21, same lab): chunking OFF + parallel_get ON per tenant

Two per-tenant flag rows, zero code: `chunking=false` (simulates the
whole-object-only `sia` tier — multipart Completes store as ONE blob) and
`parallel_get=true` (the fixed-bucket driver implements `GetRangeInfo`, so
`sia` is parallel-read eligible automatically).

| Op | Baseline (chunked) | Optimized (whole) |
|---|---|---|
| PUT 1 GiB accept | 3.47 s | 2.95 s |
| **Durable on Sia, 1 GiB** | 34.4 s (~30 MB/s) | **7.9 s (~135 MB/s)** — 4.5× |
| GET 1 GiB, gateway busy | 87/7/25/37 MB/s | 90/67/40/11 MB/s (still fat-tailed) |
| **GET 1 GiB, gateway quiet** | — | **13.2 s / 13.2 s (~78 MB/s, stable)** |

Head row verified `backend_name = sia` (not `chunked`), byte-compares pass.

### What the read investigation found

1. **The fat read tail is read/write contention at the single s3d gateway,
   not Sia.** Controls: a fresh 512 MiB object read raw 3× right after its
   flush = 4.7–5.8 s consistent (~90–108 MB/s from the network); the same
   1 GiB that read at 7–40 MB/s through Vaultaire during s3d's background
   uploads read at a stable 78 MB/s once the gateway was quiet. Same lesson
   as the single Sync bridge (2026-10-06) — and the same fix shape: **run
   several s3d instances** (one seed registers many; we already run two) and
   route/fan like the multi-bridge driver, or keep reads off the leg during
   heavy ingest.
   **Refuted by SIA-BENCH-2 below:** a second gateway does not isolate
   reads from ingest. The cuts hit every instance of one seed in the same
   windows, so the bottleneck is not per-process.
2. **`parallel_get` barely engages for real clients**: aws-cli splits
   downloads into 8 MiB ranged parts, below the 64 MiB parallel threshold —
   only 2 requests took the parallel path (single ranges ≥ 64 MiB), and its
   slow-range hedge fired 15× during the busy window. It is not the lever
   here; whole-object placement is.
3. **Whole-object placement is the one decision that matters**: 4.5× durable
   write rate, one s3d object per key (no slab-packing waste), consistent
   reads. A `SIA` storage class belongs in `storageClassDisablesChunking`.
4. s3d serves recently-written/read blobs from local disk at memory speed
   (the 1 GiB read raw in 0.4 s) — nice for hot-read patterns, irrelevant
   for the durability story.
5. The bench tenant tripped the egress allowance counter 421× (free-tier
   allowance, `egress_throttle` off → counted, not paced) — a reminder that
   a real `sia` tier bench needs a tenant with a bought house.

## SIA-BENCH-2 (2026-10-21, SLC only): a second gateway, crash recovery, DR

Two s3d v0.2.1 instances on SLC, registered with the same seed:
**gateway #1** (`~/s3d-lab/`, 127.0.0.1:9000/9001) and **gateway #2**
(`~/s3d-lab2/`, 127.0.0.1:9002/9003, own admin password, own S3 user
`vaultaire`). Gateway #2's login used the pty recipe: `expect` over
`ssh -tt` sends the phrase from `SEED.txt`, and one Allow click at
sia.storage approves it. Reads are single-stream `s3api get-object`, which
is one HTTP GET, like Vaultaire's whole-object read. The aws-cli
`s3 cp` (10 × 8 MiB ranges) gave the same picture. "Complete" means the
whole body arrived and its md5 matched. Data is /dev/urandom. Harness
scripts and logs are in `~/s3d-bench/` on the box.

### What a failed read looks like

s3d answers 200, streams part of the body and then closes the connection.
The client sees `IncompleteRead`, at anything from 32 KiB to 967 MiB in.
s3d logs nothing at info level. With `log.file.level: debug` the line is
`failed to write object body … error: failed to download slab: not enough
shards`, logged at **debug**. The siastorage SDK's congestion limiter drops
from 64–512 requests in flight to 1 (at goodput 0) in about a second and
stays there for 30–50 s before the slab fails. No bytes are ever wrong:
every body that completed matched.

Through Vaultaire (lab :8100, whole 1 GiB object), 3 of 4 GETs failed. The
parallel-get first range got `read: unexpected EOF` and fell back to the
single stream. That stream was cut as well and logged `failed to stream
artifact: unexpected EOF`, and the client saw the connection close. **A
`sia` GET can fail after its 200.**

### Test A: does a second gateway isolate reads from ingest? No.

Ingest ran on gateway #1 the whole time. Fresh 512 MiB objects were PUT
without waiting, a flusher loop kept the background upload busy at
200–300 MiB/s to Sia, and objects were deleted six iterations back. Each
round read 1 GiB from #1 and then 1 GiB from #2.

| Window | g1 reads its object | g2 reads its object |
|---|---|---|
| Quiet, before (1 GiB × 1 each) | 10.6 s, 101 MB/s | 9.7 s, 110 MB/s |
| **Ingest on #1, run 1** | **0/3 complete** (cut at 1 MiB / 24 MiB / 32 KiB, 1.7–11 s) | **0/3 complete** (cut at 784 / 280 / 5 MiB) |
| **Ingest on #1, run 2** | 1/3 (8.9 s, 120 MB/s), then 2 cuts at 32 KiB | **0/3** (cut at 31 / 5 / 65 MiB) |
| Ingest on #1, run 3 | 4/4 (9.3–53 s, 20–115 MB/s) | — (Mac read instead, below) |
| Right after ingest stopped and drained | 0/2, cut at 32 KiB in 1.0 s | 1/2 |
| 40 s later, 6 reads over 5 min | 6/6, 55–157 MB/s | |

**Acceptance fails.** Gateway #2's reads during #1's ingest completed 0 of 6.
They don't fall in a 2× band and are nowhere near 3× the p50 on #1. **The
multi-instance design does not fix read/ingest contention, and a
`MultiSiaDriver` modelled on `webdav_multi.go` would not buy isolation.**

The bottleneck is not inside one process:

- **Cuts on both gateways cluster in the same windows.** With no ingest
  anywhere (12:46:41–12:47:46), g2 cut twice and g1 cut its 1 GiB copy at
  13 MiB. From 12:48 both were clean again.
- **Every instance on one seed shares one app key.** The `app_key` in
  `global_settings` of both instances' `s3d.db` hashes the same, and so
  does the Mac's. The dashboard shows one S3d app. Per the indexd v0.5.0
  source, each app key's per-host account is topped up to a fixed target
  every 5 min, and uploads and reads both spend from it. A read on an
  empty account gets a fast payment error. The SDK scores that as a host
  failure, never retries it after a refill and never logs it.
  - That fits the shape we saw: fast cuts at the first chunk, one gateway's
    upload breaking the other gateway's reads, failures that last about
    40 s after the ingest stops, and full recovery afterwards.
  - It is an inference: s3d has no API that shows the balances.
- **Ruled out:**
  - Process age: g1 restarted cold read 6/6 at 78–175 MB/s.
  - The objects themselves: g1 read a copy of g2's bad object's bytes
    3/3 while g2 cut its own copy 3/3. Then g2's newly written 1 GiB
    object degraded the same way.
  - Box CPU or the link: 2.4 Gbps out of 10 Gbps, and the cuts outlast
    the load.
- **Not resolved: IP-level or account-level.** The Mac instance (same seed,
  home IP) read a 64 MiB object 12/12 during two ingest windows on #1. But
  neither window cut a read on SLC either, so it doesn't discriminate.
- **Gateway #2 reads worse than #1 even when quiet,** for reasons not found:
  13/29 complete against 26/27 on g1. Gateway #2 ingest uploaded to Sia at
  only 32–51 MiB/s, against 200–300 on g1, and g1 read 3/3 clean while it
  ran.
- **Size matters.** During ingest, 256 MiB reads (7 slabs) completed 4/4,
  just slower (32–70 MB/s), and 64 MiB reads completed every time. 1 GiB
  (26 slabs) is where it breaks.

What this means for a `sia` leg:

- Expect read failures in bursts across the whole seed's fleet, worst while
  anything on that seed is uploading.
- Separate app keys don't isolate either: tested in SIA-BENCH-2b below.
- Upstream issues to file:
  - The cut is logged at debug only.
  - Payment errors are not told apart from host failures and are not
    retried after a refill.

### Test B: a crash with a full buffer. No loss.

All of this ran on gateway #2, with 8 × 64 MiB fresh objects per set and the
exact PID killed (never `pkill`). aws-cli sent each 64 MiB object as a
multipart upload. After every restart the set was flushed and every object
read back from Sia.

| Set | Crash | State at the kill | After restart | Read-back |
|---|---|---|---|---|
| B1 | `kill -9`, buffer full, upload not started | 8 pending, 512 MiB, 8 files in `uploads/` | 8 pending, 512 MiB, intact; flush 8 s | **8/8 byte-identical** |
| B2 | SIGTERM during `s3d flush` | upload just started | s3d **drained**: finished the flush (all 8 pinned, the flush client got exit 0) and exited 4.4 s later | **8/8** |
| B3 | `kill -9` mid-upload | 130 MiB already sent to Sia | 8 pending, intact; **re-uploaded from scratch**, flush 6 s | **8/8** |
| B4 | SIGTERM, then a 2nd SIGTERM 1 s later, mid-upload | upload active | the 2nd signal cut the drain (`failed to finalize upload: context canceled`); flush client got EOF; 8 pending, intact | **8/8** |

A buffered object survives any crash: its file in `uploads/` and its row
stay until it is pinned, and the next upload loop or flush re-uploads it
whole. Nothing resumes partway. Slabs from a cut upload are left unpinned
and pruned after 24 h. **No P1 against the leg design.**

Two operating facts follow:

- **s3d's graceful shutdown has no deadline.** It waits for in-flight
  requests, including an admin `/objects/flush` that blocks until its
  upload finishes (`cmd/s3d/main.go`). A future systemd unit's
  `TimeoutStopSec` decides when the SIGKILL comes, which is safe per B3.
- **Deleted objects are unpinned only by the orphan loop**, which runs
  hourly plus once at startup. A gateway stopped before that pass leaves
  their slabs pinned and counted against the plan until it runs again.

### Gateway down: what the customer path sees

The lab Vaultaire (:8100, `STORAGE_MODE=sia` → gateway #1) ran while gateway
#1 got a SIGTERM, with aws retries off:

- PUT and GET answered **503 `ServiceUnavailable` from the first request**
  (~1 s), and HEAD kept answering from `object_head_cache`.
- The breaker opened within ~16 s and `/health` went `degraded` (`circuit
  breaker open on the primary backend sia`). By ~40 s the reason also said
  `probe failing on sia`.
- After the restart the breaker went half-open and then answered **200
  within 18 s**.

### DR: a fresh instance recovers nothing. Back up `s3d.db`.

- **Finding, DR test of 2026-10-21:** a FRESH s3d instance registered with
  the same seed recovers NOTHING. The key → Sia-object map lives only in
  that instance's `data/s3d.db`, and the seed only re-derives the app key.
  Upstream backups are unbuilt (s3d issues #202, #219, #288).
- v0.2.1 does have an admin `POST /snapshots`, which uploads a gzipped DB
  backup to Sia as a tagged object, but no command or endpoint restores
  one.
- Each instance owns only its own keys, so every gateway has its own
  catalogue to lose.
- **Mitigation: back up every instance's `s3d.db`.** An online copy through
  SQLite's backup API is consistent while the daemon writes: 0.01 s for
  g1's 2.3 MB file with 662 objects, `integrity_check ok`. Today's copies
  sit in `~/s3d-lab{,2}/backups/` at mode 0600.
  - **The file holds the app key**, so the backup is a secret.
  - Ship it off-box like the pg dump.
  - Restoring it is untested. Proving it means a second live instance on
    one catalogue, and the two could prune each other's slabs.

### The Mac is retired

- Its `vaultaire-smoke` bucket was emptied and removed through its own
  endpoint, and the daemon was restarted once so its startup orphan pass
  unpinned the deleted objects (orphans 2 → 0). Then it was stopped. The lab
  is SLC-only now.
- `~/fairforge/s3d-lab/SEED.txt` stays until the owner confirms the
  Keychain copy. SLC has its own copy (`~/s3d-lab/SEED.txt`, 0600).
- Approving a login works from any browser signed in to sia.storage.

### Space

The account held ~7 GB at the start and 10.5 GB at the peak (seeds plus the
ingest live set). It ended at **5.7 GB of 50 GB** after every test object
was deleted on its own gateway and the orphan passes ran. Gateway #1 is
back at its pre-session 662 objects / 4.64 GiB, and gateway #2 is empty.
Both are running (nohup, user1).

## SIA-BENCH-2b (2026-10-21): a separate app key, an upload cap, and what the box was doing

**Separate app key: no isolation.**

- Gateway #2 was rebuilt from v0.2.1 source with one line changed:
  `cmd/s3d/login.go` app ID `HashBytes("s3d")` → `HashBytes("stored-s3d-app2")`,
  name "Stored s3d 2". The binary is `~/gopath/bin/s3d-app2`, built on the box
  (source copy in `~/s3d-src-app2/`).
- It logged in with the same seed into a fresh data dir. The dashboard now
  shows **2 / 3 apps**, each with its own key, and the `app_key` hashes
  differ (g1 `9a0267dd3f66`, g2 `1a0a9e5e97e8`).
- Same harness as Test A, two runs:

| 1 GiB reads | Quiet | During g1 ingest | In the 5 min after |
|---|---|---|---|
| g1 (app "S3d") | 3/3, 111–135 MB/s | **1/6** complete | 4/6 |
| g2 (app "Stored s3d 2") | 3/3, 95–158 MB/s | **2/6** complete | 3/6 |

- Both apps degraded together, and the bad window outlasted the ingest by
  about 5 min (ingest ended 13:33:10; both clean again from 13:39).
- Per-app-key host accounts are therefore **not** the cause. The SIA-BENCH-2
  inference about the shared app key was wrong. **SIA-BENCH-3 found the real
  cause:** host balances (`not enough funds`), shared across every app of the
  sia.storage account.
- Gateway #2 stays on its own app key anyway. The s3d README says "Run a single
  s3d instance per app key and data directory", because instances sharing
  either "can unpin each other's data". Earlier today g1, g2 and the Mac all
  shared one key.
- A check afterwards found g1's data intact. All 8 `slc-bench` objects and
  40 random objects of 654 in `vaultaire` were read back with matching size
  and MD5 (48/48). The shared-key catalogue of g2's first incarnation, which
  was empty, was deleted.

**Upload cap: no fix.**

- g1 with `sia.uploadThreads: 1` (default 4) still uploaded ~100–114 MiB/s
  (1 GiB flushed in 10 s).
- During its ingest, 1 GiB reads completed 2/6: the first round was clean on
  both gateways, then all four reads after it were cut. The setting was
  reverted afterwards.

**The box itself.** From the box's Prometheus (`node_network_transmit_bytes_total`):

- Outbound reached **6.6–7.7 Gbps on the 10 Gbps link** during these ingests.
  s3d writes ~3× the logical bytes (10-of-30 shards).
- Other traffic shared the box during the session: a 2.9 Gbps outbound spike
  at 13:13 while this bench was idle (a parallel lab session; a Blomp lab
  Vaultaire has run since 11:20), and seven prod deploys.
- Nothing network-related was changed today (no sysctl, firewall or limits
  changes). Conntrack held 1,176 of 262,144 entries; s3d's nofile limit is 1M.
- The quiet-window cuts (11:37–11:53, 12:46) happened at under 0.5 Gbps out,
  so uplink saturation explains the ingest windows at most, not every cut.

**Upstream state** (researched 2026-10-21):

- No fix exists upstream.
  - s3d v0.2.1 is the latest release.
  - The sia-storage-go download and congestion code is unchanged since our
    pinned commit.
  - No GitHub issue matches the symptom.
- The SDK fails a whole download as soon as any 1 MiB chunk can't reach 10
  shards. There is no chunk-level retry, and the per-host error is never
  logged.
  - A 1 GiB object is about 1,000 chunks, so its failure odds dwarf those of
    a 64 MiB object (64 chunks). That fits "1 GiB breaks, 256/64 MiB mostly
    fine".
- The client dials hosts over TCP SiaMux only; QUIC is disabled upstream.
  Each process keeps one connection per host, which carries both sector
  writes and reads.
- Snapshots:
  - `snapshots create/list/delete` merged upstream on 2026-10-21 (s3d #219,
    unreleased, experimental).
  - `snapshots restore` is still open (#288).
  - The backups tracker #202 is open.
- `sia.uploadDeadline` (auto-flush, #313) merged 2026-10-20.

**Verdict** (superseded by SIA-BENCH-3, which found the cause):

- Read reliability for large objects is the blocker. Neither more gateways
  nor more app keys on one box fixes it.
- What could:
  - **Client-side:** Vaultaire retries a cut `sia` GET, resuming with a Range
    from the last byte delivered. A cut never yields wrong bytes, so a
    resume is safe. Or keep `sia` objects small: Vaultaire's 16 MiB chunks
    already are, and the original bench's chunked reads did complete, just
    slowly.
  - **Upstream:** a chunk-level retry in sia-storage-go, plus logging of the
    per-host error.
  - **Placement:** a gateway on another box, to tell box/link effects from
    host-side ones (not done).
- To find the real cause, the next step is a locally patched SDK that logs
  `res.err` in `downloadSlab`, with `ss -ti` and `conntrack -S` watched during
  a run.

## SIA-BENCH-3 (2026-10-21): the cause, the read budget, Cloudflare in front, other techniques

### The cause: `not enough funds`

Gateway #2 ran a patched s3d (`s3d-app2-retry`; the diff is
`bench-results/sia-sdk-chunk-retry-2026-10-21.patch`). The patch makes the
siastorage SDK log every failed host read with its error, retry a failed
1 MiB chunk up to 5 times (0.5–8 s backoff), and take `S3D_DOWNLOAD_HOST_TIMEOUT`.

- In the first two minutes it logged **49,386 failed host reads, and 49,381 of
  them were `failed to read response: not enough funds (5)`**, across 41 hosts.
  The other 5 were closed connections.
- A typical failed chunk tried 30 hosts: 21 answered "not enough funds" and only
  2–3 delivered, short of the 10 needed.
- **It is not the network, the box or flaky hosts.** The app's prepaid account
  on each host is empty.
- The indexer tops every account up on a 5-min cycle, to a per-host target set
  by the plan's quota (`fund_target_bytes`, indexd `accounts/manager.go`).
- Uploads and reads both spend from those balances, **and the pool is shared by
  every app of the sia.storage account.** Gateway #2 (its own app) uploaded
  nothing, yet ran dry while gateway #1 ingested.

This explains everything in SIA-BENCH-2/2b:

- the cuts on every gateway at once, and that a second app key doesn't help;
- the bad windows lasting until the next top-up;
- short client retries failing, since they spend more of the same empty balance;
- 1 GiB failing where 64 MiB doesn't, since a read spends ~1.5× its bytes
  (15 of 30 sectors per chunk).

**The plan's "speed" column is this budget:** Free 500 Mbps, Plus 500 Mbps,
Pro 1 Gbps, Unlimited 5 Gbps (sia.storage/plans, 2026-10-21).

### The read budget, measured (free plan, no uploads anywhere)

| Phase | Back-to-back 1 GiB reads (patched gateway) |
|---|---|
| Balances full | 3 reads at 82–136 MB/s (a ~3 GiB burst) |
| Draining | 4 more at 16–27 MB/s, completed by the chunk retry |
| Empty | 8th read failed (14:39:09) |
| Refill | a 256 MiB read 39.5 MB/s 30 s later, 63.5 MB/s at +60 s |

- That is 7 GiB in 4.5 min ≈ **26 MB/s ≈ 210 Mbps of logical reads**. This is
  consistent with half of 500 Mbps for reads, spent at ~1.5× the bytes
  delivered.
- Scaled the same way, Pro would sustain roughly 2× and Unlimited roughly 10×.
  That is a projection, not measured.

### Read techniques at the source (gateway #2, `siaread.py`; ingest on #1 = 9 GiB bursts)

| Technique | Quiet | During/after ingest | Note |
|---|---|---|---|
| Single GET (baseline) | 2/2 | **1/4** | fails at 0.7–15 s |
| Resume on cut (Range from the last byte, If-Match) | 3/3 | **2/4** | stuck: 11 cuts in 33 s at the same offset (60 MiB) |
| Parallel 16 MiB ranges × 8, each retried | 2/3 | **1/4** | 105–235 range retries on the same ranges (2–7); it spends the budget fastest |
| Patched SDK chunk retry | — | 7/8 back-to-back (budget run); 0/2 right after run B had drained the account | turns cuts into slow successes until the account is fully empty |

- **Retries at the client cannot outlast an empty balance.** Only waiting does
  (a top-up), or reading slower than the budget.
- Vaultaire's own whole-object `parallel_get` has no per-range retry: 3/4
  through the lab, SIA-BENCH-2.
- Its chunk-GET hedge would *add* spend.

What wasn't tested, and why:

- **Cache Reserve:** refused on the Free zone (API 1135, 2026-10-05).
- **Argo, Load Balancing, Spectrum:** paid or Enterprise, and they act on the
  Cloudflare→origin leg. The budget sits on the s3d→host leg.
- **Containers (s3d inside Cloudflare):** no Docker runtime on the Mac to build
  the image. The cause is now known, so it would only move the same budget.
- **Queues and the DO copier:** the Workflow covers durable retries; the DO
  copier was proven on 2026-10-09.

### Verdict and the shape that works

1. **Never serve a customer read straight from Sia.** The plan's read budget
   (~26 MB/s sustained on Free, shared with uploads and with every app on the
   account) makes large reads fail in bursts.
2. **Hydrate once, serve from Cloudflare.**
   - A Workflow (or a Vaultaire job) copies an object into R2 part by part with
     durable retries. It survived both a drained account and an origin outage.
   - Reads then come from R2 or the edge cache at 80–190 MB/s with zero Sia
     spend.
   - R2 stays a working set with lifecycle expiry (R2 is never the vault,
     docs/CLOUDFLARE.md).
   - Sippy only fits objects up to ~500 MiB.
3. **Pace Sia reads to the budget.** A token bucket at the plan's read rate
   keeps hydrations out of the empty-balance zone. Parallel parts spend faster,
   not cheaper.
4. **The plan is the rate lever.** Pro (1 Gbps, $14.99) or Unlimited (5 Gbps,
   $19.99) for a real tier.
   - A second sia.storage account separates budgets between workloads, but an
     object is readable only through the account that wrote it.
   - So it can't take reads off an ingesting account, and running extra free
     accounts to dodge a plan limit is a terms question.
5. **Upstream:**
   - Report that a payment error (`not enough funds`) is scored as a host
     failure, never retried after a top-up, and never logged; s3d logs the cut
     at debug.
   - Offer the chunk-retry and logging patch.
   - Reading MinShards instead of 1.5× would cut read spend by a third.
     Untested.

- The patched binary stays at `~/gopath/bin/s3d-app2-retry` for diagnostics.
- No tunnel, Worker, Workflow, R2 bucket or DNS record remains.

### Operating our own indexd: the checklist

Sources: [docs.sia.tech/store-your-data/setting-up-indexd](https://docs.sia.tech/store-your-data/setting-up-indexd)
(overview, docker, connect-application, operations) and the indexd and s3d
source and issues at their 2026-10-20/21 commits.

- **Shape:**
  - PostgreSQL 18 (one indexd per database; failover is active/passive only).
    Recommended hardware: 4 cores, 8 GB RAM, 256 GB SSD.
  - The node and wallet are built in.
  - Ports: admin 9980 (never public), syncer 9981 (public), app API 9982
    (only behind a TLS proxy).
  - `consensus.network: mainnet|zen`. `-instant` checkpoint sync needs the
    explorer enabled (`explorer.url`, `https://api.siascan.com/zen` on Zen).
  - It downloads a GeoIP database at start.
- **Backups:**
  - The seed "is not a backup of the indexer".
  - Use scheduled `pg_dump` plus WAL archiving for point-in-time recovery,
    kept off the box, with restores tested.
  - Also back up `indexd.yml`, the data directory and `consensus.db`, plus
    every s3d's `s3d.db`.
  - When restoring, run the same version first and verify the wallet,
    contracts, accounts, connect keys and object health.
  - The last resort is re-pinning from an app's cached metadata, started
    promptly.
- **Versions:**
  - Both projects are 0.x with releases every 2–3 weeks and breaking changes
    (indexd 0.6.0 switched the app API to CBOR and turned pruning on by
    default).
  - Pin exact versions, upgrade indexd and s3d together, and take a
    `pg_dump` before every upgrade.
  - s3d v0.2.1 pins indexd v0.5.0; master pins v0.6.1.
- **Contracts and hosts:**
  - Maintenance is **off by default**
    (`PUT /api/settings/contracts {"enabled":true,…}`).
  - Use ~50 wanted contracts for 10-of-30, which leaves ~20 hosts spare for
    repair.
  - Default price limits are 3000 SC/TB for storage, ingress and egress;
    about 40% of hosts are above them. Pin in USD instead.
  - Hosts must answer on SiaMux **and** QUIC.
  - Geographic spread comes from the blocklist; the built-in rule only keeps
    hosts 10 km apart.
  - Known issues: over-aggressive auto-blocking (indexd #773) and spurious
    lost sectors (#1102).
- **Funding target (`quotas.fundTargetBytes`):**
  - Per host, each 5-min top-up covers half the target's write cost plus half
    its read cost.
  - Read capacity ≈ hosts × target ÷ 2 per 5 min. The Foundation's internal
    reference is 16 GiB ("~1 Gbps per host for 2 minutes; 30 hosts ≈ 30 Gbps").
  - No refund path for unspent balance was found; treat it as committed
    spend.
  - indexd 0.6.0 fixed a funding backoff bug that "stall[ed] funding for all
    other hosts".
- **Apps:**
  - A quota (`PUT /api/quotas/{key}`) plus a connect key
    (`POST /api/apps/connect/keys`).
  - s3d's `login` takes the bare advertise URL. Approval happens at
    `{advertiseURL}/auth/connect/{id}`, with the connect key typed into the
    page.
  - Scripted login: `POST /api/apps/preauthorized/keys`.
- **Monitoring:**
  - indexd `GET /api/prometheus/metrics`. Watch: wallet spendable, hosts good
    for upload, bad or renewing contracts, unrecoverable or stuck slabs, lost
    or unpinnable sectors, sync height against scan height, and `GET /alerts`.
  - Raise the scrape timeout: the Foundation's own scrape timed out at 10 s
    (#1127).
  - s3d `GET /prometheus` on its admin port: failed uploads, unpinned or
    orphaned objects, buffer used against the limit.
- **s3d limits:**
  - Pinning is sequential (#318).
  - The built-in HTTPS certificate is self-signed and regenerated each start,
    so use a proxy.
  - Snapshots are experimental and restore (#288) is open.
  - Object Lock state lives in `s3d.db`, so restoring an older copy undoes
    retention.
  - Not implemented: ACLs, CORS, tagging, bucket encryption.

### Community and roadmap (thin)

- Public first-hand reports of indexd, s3d or sia.storage are scarce: nothing
  on Reddit, Hacker News or YouTube. The GitHub discussion boards are empty.
- renterd is maintained (v2.9.4, 2026-09-10) but no longer recommended; new
  renterd grant projects are frozen in favour of indexd.
- The only published throughput figure is the Foundation's SDK upload,
  1.46 Gbps of file data. No download figure was published.
- A community fork,
  [s3d-smart-autopilot](https://github.com/MainQuestion/s3d-smart-autopilot),
  caps concurrency from the indexer's transfer limits. It is the same pacing
  idea as ours, and it confirms that retries and racing spend the budget
  faster.
- **No one was found running a CDN in front of s3d**, so SIA-BENCH-3's edge
  cache and copy-once-to-R2 results appear to be new.
- Roadmap: "full S3 compatibility" was estimated for Q3 2026 and is in
  progress. On s3d master but unreleased: Object Lock, auto-flush, read-only
  bucket policies. The v0.2.2 release is pending.

## SIA-BENCH-5 (2026-10-21): the two SDK fixes on mainnet, the fill rate, the customer's view

All of this ran at $0: the sia.storage **free plan** (mainnet), gateway #2 on
its own app key, and `s3d-app2-funds`.

- `s3d-app2-funds` is s3d v0.2.1 with the patched siastorage SDK and indexd
  **v0.5.0** client copy (`~/indexd-050-funds`).
- The redundancy check stays at upstream 99.99%.
- The two fixes, both developed on the Zen lab:
  - **Funds-aware reads.** A host's `not enough funds` refusal no longer
    counts as a failed RPC in indexd's client (`isFailedRPC`) and no longer
    feeds the SDK's congestion limiter. A chunk failing mostly on refusals
    waits for a refill: 15, 30, then 60 s steps, about 10 min in all.
  - **Overdrive switch.** `S3D_READ_OVERDRIVE=0` makes each chunk start
    exactly MinShards reads instead of 1.5×.
- On Zen (2-of-6, 512 MB target, 10 × 256 MiB reads):
  - funds-aware: 10/10 complete (stock: cut);
  - overdrive off: 5–6 full-speed reads per refill against 4, and 10 reads
    in 6.3 min against 10.5.

### Bench 1: 8 × 1 GiB back-to-back reads after a full refill (mainnet, free plan)

| | Run A: funds-aware, stock overdrive | Run B: funds-aware, overdrive off |
|---|---|---|
| Complete | **8/8** | **8/8** |
| Total | 5 min 42 s (≈ 25 MB/s) | 5 min 29 s (≈ 26 MB/s) |
| Reads on a full balance | 122–168 MB/s (first 4) | 49–116 MB/s |
| Longest single read | **268 s** (one stall waiting for the refill) | 118 s |
| Host `not enough funds` refusals | ~68,000 | ~49,000 (−28%) |
| Chunk refill waits | 1,518 | 238 (−84%) |

- **The funds-aware fix carries over to mainnet: 16/16.** Before it, stock
  s3d cut these reads and the chunk-retry patch alone managed 7/8
  (SIA-BENCH-3).
- **Overdrive off is not a throughput gain on mainnet.**
  - The refill rate is the ceiling: ≈ 25 MB/s sustained on the free plan
    either way.
  - What it changes is shape: fewer wasted refusals and a shorter worst
    stall, but slower bursts. Real hosts are slow enough that the 1.5×
    hedge pays for itself.
- **Setting:** keep the overdrive for interactive reads; turn it off for
  background bulk copies (R2 hydration), where smooth spend matters more than
  burst speed.

### Bench 2: the fill rate

8 fresh 1 GiB objects, each PUT then flushed, back to back:

- **8 GiB in 104 s ≈ 83 MB/s logical**, about 250 MB/s of shards at 3×.
- Individual flushes ran at 51–162 MB/s.
- 215 shard writes were refused, 196 of them `not enough funds`. All were
  absorbed by the SDK's own write racing; every flush succeeded.
- Takeaway: on the free plan a burst fills at roughly 3× the sustained read
  budget. A longer run would find the sustained write ceiling.
- Capacity planning: 10 TB at ~80 MB/s is ~35 h of wire time if the rate
  held.

### Bench 3: the customer's view through Vaultaire

The lab Vaultaire (:8100, tenant flags `chunking=false`, `parallel_get=true`)
was restarted with `SIA_ENDPOINT` pointed at gateway #2 (env override; restored
afterwards). It then served a 1 GiB whole object PUT through Vaultaire, right
after bench 2 had spent the budget:

| aws-cli GET | Results |
|---|---|
| Default timeouts ×3 | 24.3 / 29.8 / 23.5 s, all byte-exact |
| `--cli-read-timeout 0` ×3 (later, budget lower) | 47.3 / 193.1 / 114.2 s, all byte-exact |

- **6/6 completed with no client errors.** The longest idle gap inside a
  read was not measured, so whether a 60 s read timeout would trip on a fully
  drained account is open.
- **Side finding (Vaultaire, not Sia):**
  - All 6 GETs logged `insert event: context canceled`. The cause:
    `s3_engine_adapter.go` records `object.downloaded` with `r.Context()`
    *after* the body, and a client that closes on the last byte cancels it.
  - Effect: a lost `object.downloaded` row and webhook.
  - Prod's journal shows 0 occurrences in 7 days, so it's latent and seen on
    large downloads.
  - Fix: emit on a context detached from the request
    (`context.WithoutCancel` + a short timeout).

### What SIA-BENCH-5 settles

- With the funds-aware SDK, Sia reads on any budget **never fail; they run at
  the budget's rate.** Free ≈ 25 MB/s sustained after a ~4 GiB burst.
- Uploads burst at ~80 MB/s.
- Vaultaire's whole-object path serves it to an unmodified aws-cli.
- The remaining knobs are economic: the plan (hosted) or `fundTargetBytes`
  (self-hosted). The software no longer adds failures.
- The patches are lab builds:
  - `~/gopath/bin/s3d-app2-funds` (mainnet, gateway #2);
  - `s3d-self-funds` / `indexd-lab` (Zen);
  - the diff is in `bench-results/sia-sdk-chunk-retry-2026-10-21.patch`.
- They are worth offering upstream.

## SIA-BENCH-6 (2026-10-21): lower redundancy, the local cache, budget isolation

All $0. Mainnet = the sia.storage free plan, gateway #2 on the reproducible
build (`deploy/sia/build-s3d.sh`). Zen = the self-hosted indexd lab.

### 13-of-30 (2.31×) against the default 10-of-30 (3×), mainnet

13-of-30 passes s3d's own 99.99% recovery check (99.995% at 75% host
availability). Run: 1 GiB fresh, flushed, then a full refill, then 8
back-to-back reads with the funds-aware build, compared with SIA-BENCH-5 run A.

| | 10-of-30 | **13-of-30** |
|---|---|---|
| Bytes stored on hosts | 3.00× | **2.31× (−23%)** |
| 1 GiB flush | 8 s (26 slabs) | 7.1 s (20 slabs, waste 1.54%) |
| Reads complete | 8/8 | **8/8** |
| Burst on a full balance | 4 GiB at 122–168 MB/s | **5 GiB at 84–288 MB/s** |
| Longest read (refill wait) | 268 s | 382 s |
| Host `not enough funds` refusals | ~68,000 | ~102,000 |

- Reads spread over more hosts per slab, so bursts are faster and longer.
  Sustained throughput is still the refill rate.
- **Self-hosted:** a straight ~23% cut of the storage bill. At median
  prices that's $3.45 → $2.66/TB-month, and about $1.84 with cheapest-quarter
  hosts through USD pins.
- **Hosted sia.storage:** the plan meters logical bytes (an inference from
  indexd's `pinned_data` against `pinned_size`), so the gain there is the
  faster burst.
- Lower settings that also pass the check, for a self-hosted indexer with
  enough hosts: 25-of-50 (2.0×), 41-of-75 (1.83×). Each needs that many good
  contracts, and small objects pay more slab padding.

### s3d keeps no read cache

A 256 MiB object, flushed, then read 3×: each read came from the network at
138–145 MB/s.

- The local buffer and data directory stayed empty: 0 B, `tmp/` empty.
- `diskUsageLimit` is an upload buffer only. Raising it does nothing for
  reads.
- The memory-speed reads of the optimized run came from objects not yet
  flushed.
- So repeat reads must be cached by us: R2, the edge cache, or a Vaultaire
  cache.

### Budgets are isolated per connect key (Zen, our own indexd)

Gateway #4's pool (connect key → quota `lab-funds`, 512 MB) was drained with
back-to-back reads. While it waited for its refill (its 5th read took 250 s),
gateway #3 read on another connect key (quota `lab`, 16 GiB) against the same
10 hosts:

- **4/4 reads at 52–69 MB/s, 0 `not enough funds`.**
- On a self-hosted indexer, each connect key's pool is its own budget.
- **The unit of isolation is the dataset, not the workload.**
  - An app key (the identity that owns the objects) is registered under
    exactly one connect key, so it has one pool: indexd's `accounts` row
    carries one `connect_key_id`.
  - Interactive reads, background hydration and ingest of the **same**
    objects share that budget.
  - Isolation needs separate gateways with their own app keys and their own
    data, for example a group of tenants per gateway, each with its own
    connect key and quota.
- That is more than SIA-BENCH-2/2b could get from one sia.storage account,
  where the pool is the account's.
