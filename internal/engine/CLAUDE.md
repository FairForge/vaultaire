# internal/engine

Core orchestration layer — connects the API layer to storage drivers. This is the middle of the three-layer architecture (API → Engine → Drivers).

## Key Types

- **`CoreEngine`** (`engine.go`) — the main orchestrator. Holds `map[string]Driver` (named drivers), the configured primary, the per-backend circuit breakers (`FailoverManager`) and the object→backend routing cache. Implements the `Engine` interface. The read cache, access tracker, cost optimizer, health-score selector, backup replication and tiering engine were inert in production and were deleted in Review R15 (WP-R6-4/5/6); `Config` is now just `DefaultBackend`.
- **`PutOutcome`** (`put_outcome.go`, RP13-1, Prompt 13) — `WithPutOutcome(o)` asks `CoreEngine.Put` to record which backends' attempts ended **without an answer** (a deadline, a reset, a cancel that landed after the request went out): those may still commit the body (RP8-11). `PutAnsweredOrUnsent(err)` is the rule: an HTTP status > 0 (aws-sdk-go-v2's `ResponseError` reports `StatusCode: 0` when nothing came back), a `smithy.APIError`, a `PermissionError`, `ErrInvalidInput` / `ErrChunkAddress`, a refused dial or a DNS failure = nothing committed. Drivers ignore the option; the chunk store's claim is its one user (`api/chunk_claim.go`). Tests: `drivers/put_outcome_test.go` (the real fixed-bucket driver, SDK and engine against a stalling fake S3)
- **`Engine`** interface (`interface.go:9`) — top-level contract: `Get`, `Put`, `Delete`, `List`, `HealthCheck`, `GetMetrics`, plus future stubs (`Execute`, `Query`, `Train`, `Predict`) and `GetContainerMetadata` / `GetArtifactMetadata` (`interface.go:30-32`), which nothing outside the package calls.
- **`Driver`** interface (`interface.go:38`) — the sacred backend contract: `Name`, `Get`, `Put`, `Delete`, `List`, `Exists`, `HealthCheck`. All storage drivers implement this.

## Request Flow

- **Put**: resolve storage class (the API layer's `resolvePutStorageClass` + `storageClassToBackend` are the ONLY placement inputs — the engine never re-derives placement; the access-tracker "recommendation" override was removed in R6, it had been relocating `auto`-bucket overwrites to Lyve, R6-03) → build WRITE candidate list (`buildWriteCandidateList`: target, primary, then the general-purpose durable backends; **target-only backends** `local`, `r2`, `geyser`, `permafrost`, `sync`, `blomp` and every `idrive-<region>` receive a write only as the explicit target or the configured primary — WP-F + R6-04; a **strict target** (`strictTargetBackends`: `sync` and `blomp`) is asked ALONE — see "Strict targets" below) → failover.Execute tries in order → the backend that took the bytes is returned for the caller's head row (nothing recorded in the engine, WP-R6-1). If every eligible backend fails with a genuine backend failure (`isBackendFailure`), Put returns `ErrAllBackendsUnavailable` (API layer → 503 + Retry-After), logs at Error level, and bumps the `write_failures` counter (exposed in GetMetrics) — customer data is never silently stranded on the hub's local disk. Client-level outcomes (quota, invalid input) keep their error identity (403/400, not 503). **`ErrInvalidInput` ends the failover chain** like `ErrArchived` (2026-10-07): a key the target cannot hold (a name Sync's bridge refuses) is never stored on the next candidate — the object would land silently off the tier its bucket promises.
- **Get / GetRange — location-authoritative (WP-R6-1, `recorded_backend.go`)**: ask ONE backend, the one the object's row records — the context's `WithRecordedBackend(ctx, name)` (the API sets it from `object_head_cache.backend_name`, a version row's, the parity row's object), else the primary (a row with no backend on record). Never a walk of the other registered backends (R6-07: a genuine miss cost 18 round trips on prod and a stale copy anywhere was served as the object — measured on `origin/main` 9f3d0c1: an open breaker on the recorded backend served the primary's stale copy with a 200). A miss there is a miss (404); a failure, an open breaker, or a name no driver is registered under (`ErrBackendNotRegistered`, Error line; WP-R7-5's fan-out fallback is gone — prod had 0 such rows) is `ErrAllBackendsUnavailable` → 503 + Retry-After. `readCandidates(target, op)` returns `[target]` or that error.
- **Strict targets (Prompt 2b.4 E1.1 — departs from R6-04 for these backends only):** `sync` never has another backend asked after its own failure, for a write (`buildWriteCandidateList` returns `[sync]`) nor a read of an object recorded there (`readCandidates`, Get and GetRange) — the region-pinned precedent (`errRegionDriverUnavailable`). Its failure — charged (three bridges failing, the probes notwithstanding) or an open breaker — is `ErrAllBackendsUnavailable` → **503 + Retry-After**. Before: a sync PUT whose bridge failed before reading the body (MKCOL into a folder the process had not cached, every 0-byte object) landed on the primary and answered 200 — and with the breaker open every sync PUT did; a GET of a key whose older copy sat on the primary (pre-flag, or an earlier fall-over; WP-R6-1 never removes it) answered 200 with the OLD bytes under the new head row's ETag. Delete was strict already (2b.2 C2). **An unregistered strict target is never substituted on the write side either** (Prompt 2b.6 G1): `ResolveStorageClass` returns `sync` for SYNC whether or not a driver is registered (every other mapped class still degrades to the primary when its driver is missing — R6-04), and `Put` refuses it before reading a byte with `ErrAllBackendsUnavailable` wrapping `ErrStrictTargetUnregistered` (503 + Retry-After at the API, no head row, reservation released; `strict_target_unregistered_total{op="put"}`). Before: the resolver handed the primary back, `buildWriteCandidateList`'s guard was never reached, and a sync-tier PUT / multipart Complete / CopyObject destination on a process without the driver landed on the primary with a 200 (#675's test called the inner function). Tests at the handler: `api/strict_target_write_test.go`. The other target-only backends (tape, permafrost, r2, `idrive-<region>`) keep R6-04's WRITE fall-over (every read asks the recorded backend alone since WP-R6-1); Vault-parity rebuilds are untouched (they key on a failed read of the recorded backend, which still errors). A veto by the owner would restore R6-04 for `sync`: off-tier objects counted in `vaultaire_engine_fallover_total{from="sync"}` but served/stored.
- **Delete — every known copy (WP-R6-1 A3, R6-24)**: the recorded backend (resolved as Get resolves it) plus every backend the context names as holding another copy at the same address (`WithKnownCopies` — the API passes the Smart-demotion ledger's other copy and a `retired_blobs` row's backend, `api/object_delete_shared.go` `knownBlobCopies`). EVERY candidate is attempted (`deleteOn`, through its own breaker); a miss on one is fine (`IsObjectMiss`, the local driver's `*fs.PathError` included — Prompt 2b.4 E1.4), a failure on ANY — a backend failure, an open breaker, `ErrPartiallyUnavailable`, an unregistered name — is the delete's failure (`ErrAllBackendsUnavailable` → 503, the head row, quota and aftermath kept; never "deleted" while a copy may remain); misses everywhere return the miss (the API's idempotent delete). Never the primary in place of the recorded backend (Prompt 2b.2 C2: the primary's DELETE of an absent key succeeds on every S3-class store). It used to stop at the first success and keep the second copy.
- **No tenant, no call (WP-R6-1 A5, R6-22)**: `Put`, `Get`, `GetRange`, `Delete` and the `*On` calls refuse a context with no tenant — `ErrNoTenant` (wraps `ErrInvalidInput`: a caller's bug, never a miss, never a breaker charge), an Error line, `vaultaire_engine_no_tenant_refusals_total{op}` (put, get, get_range, delete, exists; must stay 0 — `api`'s `TestMain` fails the package on an undeclared one, `TestEngineCalls_CarryTheTenant` lists every call site with where its tenant comes from). `common.GetTenantID` answers `""` for no tenant (it answered `"default"`: a shared namespace). The chunk container and the probes name their reserved tenants (`ChunkContext`, `ProbeTenant` = `_probe`).
- **List**: delegates to primary driver only (no pagination; the API uses it only as the no-DB fallback)
- **The one address of a chunk blob (WP-R8-7, `chunk_address.go`)**: `ChunkContainer` (`_global`) + `ChunkAddressTenant` (`_global`) in the driver context, built by `ChunkContext(ctx)` — THE helper every chunk Put/Get/Exists/Delete runs on (the API's `chunkStore`, dedup GC, the chunk move, `cmd/tools/dedup-migrate`). Fixed-bucket drivers key `t-<tenant in the context>/<container>/<artifact>`, so before this a chunk lived under its first uploader's prefix and a second tenant's deduplicated object was unreadable. `Put` refuses a write into the chunk container under any other tenant (`ErrChunkAddress`, wraps `ErrInvalidInput`). `LegacyChunkContext(ctx, tenant)` addresses a blob written before — for the read fallback and the chunk move only; it goes with the fallback. `IsReservedTenantID`: `""` or a leading `_` — the S3 front door refuses such a credential, the erasure sweep refuses to list under one. `GetOn` / `PutOn` / `DeleteOn` / `ExistsOn` ask ONE named backend through its breaker (a chunk is on its row's `backend_id` and nowhere else; `Get`'s candidate walk would try every other backend after a miss): a miss is the driver's miss, an unregistered name is `ErrBackendNotRegistered` (never a miss), an open breaker is `ErrAllBackendsUnavailable`. `KeyAddresser` (optional, every driver but quotaless): the key a call would address — the chunk move's proof that an old copy is a different object from the blob before it deletes it.

## The registry and its lock (WP-R6-2)

`CoreEngine.drivers` (the name → driver map) and `CoreEngine.primary` are read and written inside `e.mu` sections only — `AddDriver`, `SetPrimary`, `SwapPrimary`, `view`, `GetDriver`, `GetDriverNames`, `GetPrimary`, `SharedStores`; `engine_locking_test.go` (`TestEngineRegistry_ReadOnlyUnderTheLock`) parses the package and fails on a read anywhere else, a listed site that takes no lock, or an in-place write into a driver map. Every data-path entry point (`Get`, `GetRange`, `Put`, `Delete`, `List`, `GetOn`/`PutOn`/`DeleteOn`/`ExistsOn`, `CanAsk`, `ParallelRangeSource`) takes **one view** at its start — `e.view()`: the primary and the map, read together under `RLock` — and threads it through `preferredBackend`, `readCandidates`, `buildCandidateList`, `buildWriteCandidateList`, `deleteOn`. A call therefore sees one primary from its first line to its last: a Put resolves its target and builds its candidates against the same primary however the admin swaps it meanwhile (on `origin/main` 2903d84 the two were separate reads). The operator's reads (`CheckDriver`, `HealthCheck`, `GetMetrics`, `CheckPrimaryEligible`) take a view too.

- **Copy-on-write map.** `AddDriver` publishes a new map (copy + entry), never writes one a view holds — so a view's map is read after the lock is released.
- **Registration closes at `Seal()`** — explicit, called by `main.go` (and `cmd/tools/dedup-migrate`) right after `SetPrimary`, before `api.NewServer`. `AddDriver` on a sealed engine returns `ErrEngineServing` and logs an Error; nothing is registered and no breaker created (main's `addDriver` makes a refusal a boot Fatal). Not sealed on the first call: 17 `internal/api` tests swap a driver in after seeding (a panicking delete driver, a region driver added after a 503) — with the copy-on-write map that is race-free (`TestAddDriver_UnsealedDuringTraffic_IsRaceFree`), and a call in flight keeps the map its view took. Test fixtures ignore the return (`.golangci.yml` errcheck exclusion for `AddDriver` in `_test.go`; none seals).
- **`SwapPrimary(name) (previous, error)`** is the admin's lever (`dashboard/handlers/admin_backends.go`): `CheckPrimaryEligible`'s rules and the swap under one `Lock`. `SetPrimary` stays (boot after main's own checks, tests) and is unchecked. Calls already running finish on the primary their view took. The swap is process memory only — the other slot and a restart read `STORAGE_MODE` again (WP-R12-13).
- **Before (measured on 2903d84, `TestEngine_ServingCallsDuringPrimarySwapsAndLateRegistrations`):** 14 `DATA RACE` reports under `-race`; without it the test process died in 3 of 5 runs with `fatal error: concurrent map read and map write` / `concurrent map iteration and map write` — a runtime fault the server's recover cannot catch.
- The `FailoverManager` keeps its breaker map under its own `f.mu`; the three reads from outside (`CanAsk`, `ParallelRangeSource`, `RecordReadOutcome`) take `e.failover.mu.RLock`.

## Object Location Routing (Phase 7.1-7.2)

**No routing state in the engine (WP-R6-1 Part B).** The in-memory `objectBackends` map (R6-09: unbounded, one entry per object ever PUT/GET/hinted) and `HintBackend` are gone, and so is the `LocationStore` (`routing.go`): `Put` no longer writes `object_locations` (one row per chunk per store, R8-19), no read looks it up or touches its `last_accessed` in a goroutine (R6-14/15). Every call names the object's backend on its context (`WithRecordedBackend`) — the head row is the one truth. The table stays (additive rule) with its old rows: read only by the chunk store's legacy-uploader fallback, the chunk move and the erasure sweep's bucket sources; dropping it is a later migration.


Tables created in migration 048: `object_locations` (routing cache), `tiering_policies` and `tenant_cost_daily` (both orphans since the tiering engine was deleted — D-12). Also adds `last_accessed` column to `object_head_cache`.

## Tiering

There is no age-based tiering engine (deleted in Review R15, WP-R6-4: it never ran, never updated the routing truth and would have moved `_global` chunk rows to tape — R6-10). The only mover of customer data between backends is the Smart-tier demotion job (`api/smart_demotion.go`, 5.15.8).

## Bucket Tier Preference (Phase 7.5)

`bucketTierStorageClass()` in `s3_engine_adapter.go` queries `tier_preference` from `buckets` and maps it to an S3 storage class: performance→STANDARD, standard→STANDARD, archive→GLACIER. Used in HandlePut when no explicit `x-amz-storage-class` header is present — does not override explicit headers. `auto` returns empty string (normal routing applies).

## Per-Bucket Region Routing (Phase 5.14.7)

`GetDriver(name string) (Driver, bool)` — returns a named driver from the registry. Used by the S3 adapter to route PUT operations directly to a region-specific iDrive driver (e.g., `idrive-eu-west-1`) when a bucket has a non-default region.

`WithRecordedBackend(ctx, backend)` / `WithKnownCopies(ctx, backends...)` (`recorded_backend.go`) — the backend the object's row records, and (for a Delete) the other backends known to hold a copy at the same address. The S3 adapter sets them from `object_head_cache.backend_name` on every GET, DELETE, copy source and `/cdn` read. `dormantBackends` (`wasabi`): never a write fall-over destination unless target or primary, still primary-eligible.

## Parallel ranged reads (2026-10-10)

`VersionedRangeGetter` (interface.go) is the optional driver interface of a range read that reports the object's identity (`RangeInfo{ETag, Size}`); implement it only where a range is one plain request (today `IDriveDriver`: idrive, idrive-<region>, wasabi, `LyveDriver` since the 2026-10-12 bench, and `SwiftDriver` (blomp) — never Geyser). `parallel_range.go`: `ParallelRangeSource` resolves the backend Get would ask first (`preferredBackend`) and returns its `VersionedRangeGetter` only while its breaker is CLOSED; the caller reads ranges from the driver directly and settles the whole read with ONE `RecordReadOutcome(backend, err)` (failover rules: client-level outcomes are not charged). Used by `api/s3_large_get.go` behind the `parallel_get` flag. `NoHedgeDeclarer` / `IsNoHedge` (interface.go): a driver whose reads the API never requests twice — the `sia` driver (a hedge spends the Sia account's read budget twice); the large GETs then run with no hedge. `ErrObjectChanged` (errors.go): a resumed read found another object at the key — never a breaker charge (`isBackendFailure`).

## Circuit Breaker (Phase 5.12.4)

Each registered backend gets an independent `BackendCircuitBreaker`:
- **Closed** (healthy): all requests pass through
- **Open** (broken): after 5 consecutive failures within 60s — all requests rejected
- **Half-Open** (probing): after 30s in open state — allows one probe; success → closed, failure → open

`FailoverManager.Execute(ctx, candidates, fn)` iterates the candidate list in order, skipping backends with open breakers, recording success/failure. Returns the first successful backend name.

**Verdict when nothing succeeds (R6-02):** the FIRST candidate is the recorded/target backend. If it answered with a client-level outcome (not found, quota, archived, consumed body) that is the verdict — `all backends failed: <that error>` — and failures elsewhere do not change it. If it was unavailable (open breaker, timeout, 5xx, refused), nothing a fallback said — including "not found" — is a verdict about the object: the aggregate is `ErrAllBackendsUnavailable` (API → 503 + Retry-After, never 404). Before R6 an iDrive outage answered every GET with 404 NoSuchKey because the walk ended on `local`'s ENOENT. A cancelled request context stops the walk immediately (the client is gone; no other backend is tried or charged).

**`isBackendFailure` taxonomy** (its miss half is `IsObjectMiss`, which `api/not_found.go` `isObjectMissingErr` calls — one predicate): misses are `NotFoundError` (value or pointer), `os.ErrNotExist`, and aws-sdk-go-v2 chains carrying the `NoSuchKey`/`NotFound` API codes or HTTP 404 — checked **by type only** (`smithy.APIError`, `*smithyhttp.ResponseError`), because the SDK formats the status as `StatusCode: 404` and renders an empty-body 404 as `api error NotFound: Not Found` (R6-01: every such miss opened breakers). **Never by text** (Prompt 2b.5 F1.1): the drivers and the engine put the key in every message, so the old fallbacks (`not found`, `NotFound`, `NoSuchKey`, `404`) read a 403/5xx on `errors/page not found.html` or `NotFound-0` as a miss — GET 404, DELETE 204 + route dropped, breaker never charged, PUT 500. Every driver returns a typed miss (permafrost: `odStatusError` 404 → `NotFoundError` at Get/Delete). An error wrapping `ErrAllBackendsUnavailable` or `ErrPartiallyUnavailable` is never a miss, whatever a fallback said inside it. `NoSuchBucket` is a backend failure (misconfigured backend). `context.Canceled` is neither — the client hung up (R6-06). **`ErrCallerAborted`** (the request body broke off or trickled below a driver's minimum rate — Go's server hands the handler the body's read error *before* it cancels the context, so the `context.Canceled` rule missed a client dropping mid-body; `Put` itself tags any driver failure whose source returned a read error, whatever the driver wrapped) and **`ErrPartiallyUnavailable`** (the part of a backend holding THIS object is out while the backend is up — one Sync bridge of five; wraps `ErrAllBackendsUnavailable`, so the API answers 503 + Retry-After) are never failures and **end the failover walk** (Prompt 2b.2 C1: one bridge down — ≈ 20 % of `sync` reads — and client aborts each opened the whole `sync` breaker, every `sync` read then 503'd for 30 s, repeatedly, and SYNC-tier writes landed on the primary). `context.DeadlineExceeded`, 5xx, 403 (dead key), connection/DNS errors are failures. `failover_sdk_errors_test.go` produces the shapes from a real `s3.Client` against `httptest`.

## Storage Class Routing (Phase 5.12.4)

`x-amz-storage-class` header on PUT maps to a target backend:
- STANDARD → the primary (unmapped since 2026-10-03, when Wasabi became the interim primary: a fixed `idrive` entry sent every Standard PUT to iDrive whatever the primary was), GLACIER/DEEP_ARCHIVE → geyser, RESILIENT → lyve, PUBLIC → r2; STANDARD_IA and REDUCED_REDUNDANCY unmapped (→ primary at STANDARD)
- RESILIENT → lyve (internal class — what the `resilient` bucket `tier_preference` resolves to via `tierPreferenceToStorageClass` in `api/s3_engine_adapter.go`; NOT the removed STANDARD_IA mapping: objects land on Lyve at its default class, never Lyve's IA service tier)
- BLOMP → blomp (internal class, never sent by clients — `tier_preference = 'blomp'` + the `blomp_backend` flag; written sealed unless `BLOMP_ALLOW_UNSEALED`, its storage URL being plain HTTP — `CleartextTransportDeclarer`, interface.go)
- SYNC → sync (internal class, never sent by clients — set by `api.resolvePutStorageClass` only for a `tier_preference = 'sync'` bucket of a tenant with the `sync_backend` flag; the Sync.com WebDAV bridge, reported STANDARD to the customer)
- PUBLIC → r2 (internal class, never sent by clients — set by `api.resolvePutStorageClass` for public-read buckets when an `r2` driver is registered; R2 is the public-bucket / CDN origin only, not a tier)

If the target backend isn't registered, falls back to primary silently. Storage class is a hint, never an error.

`BackendToStorageClass(backendName)` is the reverse mapping; responses to customers (GET/HEAD/listings/inventory/dashboard) go through `CustomerStorageClass(floor, backendName)`, which never reports a downstairs object in an archive class.

## Connection to Other Layers

- **API layer** (`internal/api/s3_engine_adapter.go`) wraps `CoreEngine` to translate S3 protocol → engine calls
- **Drivers** (`internal/drivers/`) implement the `Driver` interface; registered via `eng.AddDriver(name, driver)` in `main.go` (its `addDriver`: a refusal is a boot Fatal), every one before the first call — see "The registry and its lock"
- **Quota** (`internal/usage/`) — quota accounting lives entirely in the API layer since WP-1 (single reservation site in `handlePutObject`, atomic displaced-size capture on head-cache upserts, releases on delete). The engine does no quota work.

**Metrics** (`metrics.go`, `engine.Collectors()`, registered in `api/prom_metrics.go`): `vaultaire_engine_fallover_total{from,to,op}` — every time `ExecuteOp` moved on from a backend that failed (or whose breaker was open) to ask the next candidate (Prompt 2b.4 E1.1; before, a Warn `backend failed, trying next` only); a strict target never appears as `from`; `from` is the backend the request walked away from, never a later candidate skipped as open (`[idrive fails, lyve open, s3 serves]` = `idrive→s3` — Prompt 2b.5 F3.6). `vaultaire_engine_strict_target_unregistered_total{backend,op}` — a call routed to a strict target (`sync`) that no driver is registered under on this process: Get/GetRange/Put/Delete ask nobody and answer `ErrAllBackendsUnavailable` (503), logged at Error (Prompt 2b.5 F3.1: a redeploy without `SYNC_WEBDAV_URLS` fanned sync-row reads out to the primary, which served its older copy with 200; a Delete asked the primary, 204 + row dropped). `vaultaire_engine_partial_unavailable_total{backend,op}` — every `ErrPartiallyUnavailable` answer `FailoverManager.ExecuteOp` saw (op `get`, `get_range`, `put`, `delete`, `other` for `Execute`). Never a breaker charge, so this is the only count of what one Sync bridge out costs (Prompt 2b.3 D1.2).

**An object-level 403 on the recorded backend** (the 2026-10-11 iDrive shape: HeadBucket/List 200, every object call `AccessDenied`, HeadObject a bodiless 403 the SDK names `Forbidden`). It is a backend failure — charged to the breaker, never a miss (`failover_sdk_errors_test.go`, `api/backend_403_test.go` with the real fixed-bucket driver), and the probe sees it within one interval (the object canary, `api/backend_canary.go`, Prompt 2b.5 F2). What each path answers:

| Path | Breaker closed | Breaker open |
|------|----------------|--------------|
| GetObject / Range GET | 503 + Retry-After (charged) | 503 + Retry-After |
| Chunked GET (a chunk row on that backend) | 503 + Retry-After (F1.2; was 500) | 503 + Retry-After |
