# internal/usage

Quota and allowance bookkeeping in PostgreSQL. Everything here is in LOGICAL bytes.

## Files

- **quota_manager.go** — `QuotaManager`: `tenant_quotas` (the single total quota). `CheckAndReserve` / `ReleaseQuota` are the WP-1 reservation pair (`SELECT … FOR UPDATE`, one transaction; no `quota_usage_events` row since WP-R10-8 — `GetUsageHistory` is `bandwidth_usage_daily`); `ReconcileStorageUsage` / `ReconcileTenantStorageUsage` rewrite usage from the billed bytes (never call the global one from a test — the test database is shared).
- **ledger_tx.go** — WP-R10-8: `ApplyLedgerTx(ctx, tx, tenant, LedgerChange)`, the ledger inside the caller's transaction (the flip's settle, every delete, the upload's parts): the total's row locked only when the total moves, floors after it (standard, then vault), clamped at 0, an optional `Guard` that refuses (`ErrOverQuota`) a change that ends past a limit. The lock order is in its file comment.
- **billed.go** — what is billed (WP-R2-1 C2): every head row plus every RETAINED non-current version, plus every ACTIVE multipart upload's `reserved_bytes` on `UploadHoldingFloor` (WP-R10-8, 091); `BilledBytes(ctx, tenant)` reads what the reconcile would write (tests compare the ledgers with it) (`RetainedVersionsFrom`: `storage_key` set, not a delete marker, not the head row's own blob — the latest version is counted once, as the head row), on `RetainedVersionFloor` (the version's `floor` (088), else the head row's, else vault on `geyser`, else standard). The reconciles and `SetHouse` read the constants built from them; `internal/api` (gauge, version delete) and the dashboard use the two exported fragments. Metered reporting reads `tenant_quotas.storage_used_bytes`, so it reports version bytes too.
- **floor.go** — the house: `tenant_floor_quotas` (066), one row per (tenant, `standard`|`vault`). `SetHouse` / `ClearHouse` are idempotent, and their bodies are `SetHouseTx` / `ClearHouseTx` on a caller's transaction (WP-PAY-1: `internal/payments` writes the entitlement record and the floors in one — the Stripe webhook and the dashboard resize go through it since 097; the total is locked before the floors in both); `ReserveOnFloor` (`Reservation{OK, Floor}`: whether the floor row was charged too) / `ReserveTx` (the same rule inside a caller's transaction) / `CheckAndReserveFloor` / `ReleaseFloor` move the total and the floor together; a new floor row is seeded by the reconcile's computation (uploads included); `FloorOf(storageClass)` decides the floor of a write. `TB` = 2^40.
- **holders.go** — the holders of a tenant's bytes (WP-KEY-1 PR B, migration 121; F-39; D-RP88-2): besides the tenant and its pool, a write's bytes count to the KEY that wrote it (`api_keys.storage_used_bytes`; rows name it in `written_by_key`; the primary pair and background writes none) and to its BUCKET (`buckets.storage_used_bytes`, counted only while it has a storage cap — `SetBucketCaps` seeds it under the bucket's lock). This package is their ONE writer (RP82-3's rule): `LedgerChange.Holders` (applied by `ApplyLedgerTx` after the tenant half `applyTenantLedgerTx`; a holders-only change locks no tenant row), `ReserveTxFor` / `ReserveOnFloorFor` (the check min(key, bucket, tenant, pool) after the tenant's own row and before its floors — nothing charged unless everything fits; `Reservation.Cap` names the first that failed in that order: `CapKey`, `CapBucket`, `CapTenant`, `CapPool`; a guarded change's holder refusal is a `*CapError`, `CapOf`), `ReleaseFloorFor`. A release lands on the removed row's own writer. `SetKeyCaps` (`ErrPrimaryNeverCapped`, `ErrNoSuchHolder`), `SetBucketCaps`, the notes `storage_cap_above_tenant` / `egress_cap_above_tenant` (F-39 (b)); `KeyHeldBytes` / `BucketHeldBytes` (the rows' truth), `ReassertHolders` (the reconciles and the sandbox purge), `HolderDrift` (the gauge), `ListKeyCaps` (the dashboard). `TestLedger_LockOrder_*` name `ReserveTxFor` and `applyTenantLedgerTx` as the bodies.
- **pool.go** — the quota pool (WP-PLAT-1, 117): a platform's child (`tenants.parent_tenant_id`) has a `tenant_quotas` row of limit 0 that counts ITS bytes; `ReserveTx` and a guarded `ApplyLedgerTx` change check the POOL — `lockPoolOwner` resolves `COALESCE(parent_tenant_id, id)` and locks the owner's row FIRST (before the tenant's own: the lock order), `poolUsed` sums the owner's and every child's counter in a SEPARATE statement after the lock (a sum inside the locking statement keeps the snapshot of before the wait) — against the owner's limit. A tenant with no tenants row is its own pool; a sandbox is never in one. `PoolBilledBytes` (billed.go) = the owner's billed bytes + every child's. **Floors are pooled like the total (RP82-1, Stage 1a Prompt 52 Part 0):** a child has counting floor rows (limit 0) — written by `auth.CreateChildTenant` for each floor its owner has, by `SetHouseTx` for every existing child (seeded from its billed bytes, a row it has kept), and by `ReserveTx` itself when one is missing (`ensureChildFloorRow`, before the write) — and a pooled tenant's floor check (`ReserveTx`, a guarded `ApplyLedgerTx`, total moving or not) is the OWNER's floor limit against the pool's sum on that floor (`lockPoolFloor` + `poolFloorUsed`); a child's own floor limit never decides. Lock order: owner total → child total (`lockPool`) → owner floor (`lockPoolFloor`) → child floor — `TestLedger_LockOrder_PoolOwnerFirst_Structure`. The reconcile rewrites a child's floor rows like any other. `PoolRoot(ctx, q, id)` is the ONE resolver of the egress side (`COALESCE(parent_tenant_id, id)`; WP-ACCT-1 swaps it for `pool_root_id`). `TestLedger_LockOrder_TotalBeforeFloors_Structure` names `ReserveTx`'s total lock as `lockPool`'s.
- **free_tier.go** — `FreeTierLimits` (5 GiB, 1 bucket, 1 API key).
- **egress.go** — the egress allowance (WP-R10-9), **the one definition** read by the throttle and the alerter (`internal/api/egress_meter.go`, `bandwidth_alerts.go`), the dashboard overview, the admin tenant page and `/api/v1/user/usage`:
  - `QuotaManager.EgressAllowance(ctx, tenantID)` — derived at read time, one query, **of the tenant's pool root** (`PoolRoot`, D-STRIPE-31: a child's downloads spend its platform's allowance; its own limit-0 row is never read as an allowance of 0 = unpaced — RP82-2; `EgressAllowance.Root` names it). A sandbox (`tenants.sandbox_of`) answers `SandboxEgressAllowance` (5 GiB, source `sandbox` — RP80-1: metered and paced, never billed) before any other rule. Precedence: admin override (`tenant_quotas.bandwidth_limit_bytes > 0`) → the house (Standard ratio × the `standard` floor limit + Vault ratio × the `vault` floor limit) → no house (Standard ratio × `storage_limit_bytes`; the free tier's 5 GiB gives 2.5 GiB). Ratios come from `prices.json` through `landing.Get()` (`EgressRatios`). Nothing is seeded: `SetHouse`/`ClearHouse` never write `bandwidth_limit_bytes`, so an override survives a webhook replay and the end of a subscription. Override 0/NULL = the plan's allowance (not "unlimited" — exempting a tenant is a per-tenant `egress_throttle` flag row).
  - `EgressMonthStart` / `EgressResetAt` — the month is the **UTC calendar month** for every reader; `MonthEgressBytes` sums `egress_bytes` only (uploads never count — Review R13-16) **over the pool** (the root's rows and every child's; each tenant's rows stay its own).
  - `EgressThrottle` (`DefaultEgressThrottle`, `Rate`) — the D-25 knobs: `max(MinBytesPerSec, Factor × allowance / 2,592,000 s)`, `MaxStreams`.
  - `EgressStatus` / `EgressStatusReader` / `EgressStatusFromDB` / `EgressOver` — a tenant's position this month; the API server's live counter implements the reader, `EgressStatusFromDB` is the same answer without responses in flight.

## Tests

DB-backed against `vaultaire_test` (`make test-db`); each test creates its own tenant (`newTestTenant`) and touches only its rows. `egress_test.go` pins the ratios to `prices.json` and the override-survives-SetHouse/ClearHouse requirement.
