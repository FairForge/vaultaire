# internal/payments

The provider-neutral core of billing (WP-PAY, design of record `docs/PAYMENTS.md`; WP-PAY-1 built 2026-10-20, migration 097). **What a tenant has bought lives in our database with a date**; a payment from any provider extends the date; the `entitlement_lapse` job (`internal/api/entitlement_lapse.go`) clears a house whose date plus grace has passed. Stripe (`internal/billing`) is one provider that writes here; BTCPay (`internal/payments/btcpay`, WP-PAY-4) will be the second. Imports `internal/usage` and `internal/api/landing` (the price sheet) — **never a provider SDK**: the dashboard imports this package and nothing that reaches `stripe-go` (`TestDashboardImportsNoStripe`, WP-PAY-2).

## Providers (`provider.go`, WP-PAY-2, Stage 1a Prompt 19)

`Provider` is `docs/PAYMENTS.md` § 2.2: `Name`, `Renewal`, `Ready` (configured ∧ verified), `StartCheckout(Checkout)`, `Resize` → `ResizeOutcome{Applied *Order | RedirectURL}` (the design calls the type `Resize`; that name is the record's function here — D-P19-B1), `StopRenewal`/`ResumeRenewal`, `Cancel` (stop the money now; `ErrProviderUnconfigured` when the provider has no credentials), `ManageURL`, `Webhook`. Customer creation is not on it (it is `StartCheckout`'s business — no third party knows a tenant until it buys, 43.2). `Checkout.StartAt` (RP24-1, Prompt 21 Part 0) is the date the first charge may land — a renew of a GRANTED prepaid row carries its `paid_through`, Stripe defers with `subscription_data.trial_end` when it is ≥ `MinDeferredStart` (48 h, Stripe's minimum) ahead; closer (or zero) starts now and the page says the remaining days are forfeited.

`Registry` (`NewRegistry(db, flags, grace, logger)`, built in `api/server.go`, `Deps.Payments` of the dashboard): `Register(p)` (exports `vaultaire_payment_provider_ready{provider}` at once), `Provider(name)` (whatever the flag — cancel, manage link, webhooks), `For(ctx, tenant, name)` → `ErrUnknownProvider` / **`ErrProviderDisabled`** (flag `pay_<name>` off for the tenant: 409 `provider_disabled`) / **`ErrProviderUnavailable`** (not Ready), `Enabled` (what the page offers), `Ready`, `Status` (= `StatusOf` with the grace), `StartCheckout`, `Resize` (the house's provider — the row's, else stripe; when the provider changed it in place the record + floors are written in one transaction, `payments.Resize`), `ManageURL` (never flag-gated). **The double-billing guard** is the package function `StartCheckout(ctx, registry, tenant, provider, Checkout)` (§ 2.5): under `Lock`, a granted row (`lapsed_at` NULL) renewed `auto` by ANOTHER provider → **`ErrOtherProviderLive`** (409 `other_provider_live`); then the provider's own checkout (Stripe's `HasLiveSubscription` → `ErrLiveSubscription` for a second Stripe subscription), the lock held across the provider call so a webhook and a checkout cannot pass each other.

Readiness (three states since Prompt 20 Part 0, D-P20-1): `Provider.Ready` answers a typed `Readiness` — **`Unready`** (a verdict: no key, a price mismatch, a missing price id; the zero value), **`Ready`**, **`Pending`** (configured, no verification completed yet — the minute after a boot). `For` needs `Ready`; `StartReadiness(ctx, 60s)` records every provider into the `ReadyLog` (`readiness_store.go`) and the gauge (`vaultaire_payment_provider_ready` = 1 for Ready, **0 for Unready and for Pending**). The log keeps the last unready time in memory AND, with a database, in **`payment_provider_readiness`** (migration 098, RP21-1: written on a state change — the first observation of a process counts — and once an hour; `last_reason` = why it was last unready; Pending is never written), so `Registry.UnreadyWithin` — the lapse job's `ReadyHistory` — reads a real 24 h across restarts (a provider unready NOW counts; one pending NOW does not; an unregistered provider — `manual` — never). Tests `TestReadiness_PendingAtBootIsNotUnready`, `TestReadiness_Persisted`. **The guard's transaction** (`StartCheckout`) sets `SET LOCAL lock_timeout = '10s'` (`checkoutLockTimeout`) before `Lock`: Postgres's `55P03` is `ErrProviderUnavailable`, never a hang (RP22-4). Flags: `FlagPrefix` + name (`pay_stripe`, `pay_btcpay`), `FlagEntitlementLapse`. Tests `provider_test.go` (fake provider: flag → readiness order, gauge from Register, the history window, the guard with a Stripe `auto` row, resize writes the record and keeps the date).

## WP-PAY-3 (Stage 1a Prompt 20): receipts, reminders, the admin money operations, the mails

- **`receipts.go`** — a receipt is rendered from the ledger row, never stored: `ReadReceipt(ctx, db, tenant, paymentID)` (the tenant's own settled/refunded row, else `ErrNoReceipt` — the tenant comes from the session, never the URL alone), `ListReceipts` (numbered rows, newest first), `ListLedger` (every row, the admin view). `Receipt` carries the house snapshot's lines (`QuoteHouse` of `std_tb/vault_tb/pin_hot_tb/period`), the crypto fields (empty until WP-PAY-4), `Amount()`, `PeriodWords()`.
- **`reminders.go`** — the four steps `t-14d`, `t-3d`, `t+1d` (the second day of grace: "N days left"), `last-day` (`ReminderSteps`); `DueReminders(ctx, db, grace, now)` = prepaid, granted rows whose step at `now` (`stepAt`) is not yet in `entitlements.reminders_sent` (098: `"<step>@<paid_through RFC3339>": sent_at`, so a renewal resets every step by itself; the first day of grace sends nothing, past grace is the lapse job's); `MarkReminderSent`; `ReminderKey`; `ReminderLead` (14 d — also the window inside which the billing page offers Renew, RP24-1). The job is `internal/api/payment_reminders.go` (hourly); its GRACE steps (`t+1d`, `last-day`) go only where `entitlement_lapse` is ON for the tenant (RP24-2: they announce an ending only the lapse job performs; a withheld step is `skipped_flag_off` in the result, not marked sent).
- **`admin.go`** — the operator's money, each one transaction under the entitlement lock, audited AFTER the commit with the actor (an admin's user id → `performed_by`; a named actor such as `stripe-webhook` lives in `metadata.actor`, the column is a UUID), the subject tenant and a **required reason** (`ErrReasonRequired`): `RecordManualPayment` (a settled, numbered `manual` row; no entitlement row → `Grant` of the `Order` the payment names, `ErrOrderRequired` without one; a row → `Extend` by one period; `billing.payment_recorded_manual` + `billing.house_granted`), `AdjustEntitlement` (one of the TWO writers that may SHORTEN a date; sets `paid_through` and/or the house, floors written, a lapsed row given a future date is granted again; `billing.paid_through_adjusted`), `RecordRefund` (a settled `refund` row — a credit-note number from the same counter — `refund_of` the charge, the charge `refunded` once its refunds reach its amount, `ErrRefundExceeds` past it, counted under the CHARGE's provider — RP24-3; `ShortenPaidThrough` is the other shortener: its own guarded UPDATE under the entitlement lock — it does NOT call `AdjustEntitlement` (RP24-4) and writes no `billing.paid_through_adjusted`, the `billing.refund_recorded` row carries `shortened_by` — taking the refunded share of the charge's `period_start..period_end` off the date, `ErrRefundNoPeriod` when the charge records none). **One refund, one row (RP28-1, Stage 1a Prompt 24):** `Refund.FromProvider` marks the provider's own notice (the Stripe webhook); `RecordsOwnRefunds(provider)` (Stripe only) — an operator may CREATE a refund of such a charge only under the provider's refund id (`re_…`, else `ErrRefundProviderRef`); `PaymentID` may name the charge OR a refund row, and a refund already in the ledger (by row or by `(provider, ProviderRef)`) is never recorded again: `ErrRefundRecorded` for the provider, an idempotent hit (`RefundResult.Existing`, nothing audited) for an operator — with `ShortenPaidThrough`, the date is shortened by THAT refund's share once (`metadata.shortened` = {seconds, at, actor} stamped on the refund row, `MetaShortened`; a second time `ErrRefundShortened`), audited `billing.paid_through_adjusted` (no new refund row, so no `billing.refund_recorded`); another charge or another amount = `ErrRefundMismatch`. Every shortening (new or existing refund) goes through `shortenPaidThrough` and stamps its row. Manual and BTCPay charges keep a generated `refund:<uuid>` for a blank reference. A manual payment on a tenant WITH a row extends it and audits the ROW's own provider and renewal (RP24-3: a wire on a Stripe `auto` row is not re-providered). `GrantRecorded` is `Grant` reporting `Granted{Changed, Previous, …}` through the upsert's `RETURNING` (a replay changes no row → `AuditGranted` writes no `billing.house_granted`); `StopRenewalChanged` the same for `StopRenewal`; `AuditRenewal` writes `billing.renewal_stopped` / `_resumed`.
- **`mail.go`** — `Mailer{DB, Sender, BaseURL, Legal, Logger}` sends the three mails through the one `email.Sender`, best effort for its caller: `SendReceipt` (the webhook, on a NEWLY settled row), `SendReminder` (a `DueReminder`), `SendHouseLapsed` (the lapse job after its Revoke committed). `Detached(ctx)` = a 15 s context that outlives the request. Templates and copy are `internal/email` (`payment_receipt.html`, `renewal_reminder.html`, `house_lapsed.html`); the issuer is `hosts.Legal()`.
- **`metrics.go`** — `vaultaire_payment_reminders_total{step,outcome=sent|failed}` (every pair at 0 from boot — the RP14-9 lesson), `vaultaire_payment_webhook_total{provider,outcome=ok|duplicate|rejected|error}` (`CountWebhook`, the webhook handler's own counter: no per-route HTTP series exists, D-P20-A2), `vaultaire_payment_provider_enabled{provider}` (`EnabledCollector`: the flag `pay_<name>`'s global state on scrape, registered by `internal/api/prom_metrics.go`). Rules `deploy/monitoring/vaultaire-payments.yml`.

## The one writer of a house

`tenant_floor_quotas` + `tenant_quotas` stay the enforcement truth the write path reads; `entitlements` is the billing truth. Every function that changes a house takes the **caller's transaction** and writes both in it:

| Function | What it does |
|---|---|
| `Lock(ctx, tx, tenant)` | `pg_advisory_xact_lock(hashtextextended('entitlement:'‖tenant, 0))` — one tenant's grants, extensions, clears (and WP-PAY-2's checkout start) one at a time. Taken first by every function below; re-entrant within a transaction |
| `Grant(ctx, tx, tenant, Order, paidThrough, provider, ref, Renewal)` | upsert the row (`lapsed_at` cleared) + `usage.SetHouseTx`. **Never shortens a running date** (`GREATEST(paid_through, given)` — a stale or replayed event cannot take paid time away; only an operator refund shortens one, WP-PAY-7); a lapsed row takes the given date. Idempotent: a replay with the same values updates no row (`updated_at` unchanged) |
| `Extend(ctx, tx, tenant, Period)` | `paid_through = GREATEST(paid_through, now()) + 1 month | 1 year`, in UTC; grants a lapsed row again (floors restored). **Month-end rule (accepted):** `2026-01-31 + 1 month = 2026-02-28` (Postgres), and the date stays on the 28th after |
| `StopRenewal` | `renewal = 'prepaid'`: nobody will extend it; the house runs to `paid_through` + grace |
| `Revoke` | `usage.ClearHouseTx` (free-tier limits, **used bytes untouched** — billing never deletes data) + `lapsed_at = now()`. Writers of `lapsed_at`: the lapse job, and — while the `entitlement_lapse` flag is OFF — the Stripe webhook's clearing branch **while `entitlement_lapse` is OFF for the tenant** — ON, a terminal Stripe status only stops the renewal (WP-PAY-2) and the job is the only writer. Marking the row is what keeps the job's reconcile from granting back a house the webhook took away |
| `EndByStatus` | the webhook's flag-OFF terminal-status write, under the lock: a granted row with `paid_through` > now → `StopRenewalChanged` only (`Ended.Kept`); otherwise `Revoke` + stop renewal (RP26-1: paid time is never taken by a status) |
| `Resize` | the dashboard's in-place resize: the lines of a granted row change, the date stays; floors written |
| `HouseWriter` | `billing.HouseQuotas` over `Resize` / `Revoke` in one transaction each — what `server.go` wires into the webhook and the dashboard (`houseQuotas`), so no path changes a house's floors without its entitlement |
| `Get`, `StatusOf(ctx, db, tenant, grace, now)` | the read model (`Found`, `Granted`, `InGrace`, `GraceEnds`) the billing page renders from (`Registry.Status`, WP-PAY-2) |
| `InTx` | begin → fn → commit |

Lock order: entitlement lock → `tenant_quotas` → `tenant_floor_quotas` (`usage/ledger_tx.go`). Nothing that holds a key, head-row or upload lock takes the entitlement lock.

`Order` = `{Std, Vault, PinHot int; Period}` (`Words()` says it the site's way, `Period.Word()` = yearly/monthly) — `billing.HouseOrder` and `billing.Period` are aliases of `payments.Order` / `payments.Period`. `Order.Validate()` returns the exported, `errors.Is`-able **`ErrInvalidOrder`** (unknown period, a negative line, `PinHot > Std` — migration 097's CHECK `pin_hot_tb <= std_tb` is the same rule); `Grant` checks it before it takes the lock or runs any statement, so a caller's transaction is intact after the refusal and a webhook can tell the order's fault from a transient one (RP20-4).

## The ledger (`ledger.go`)

`payments` rows keyed by `(provider, provider_id)` (a Stripe invoice id, a BTCPay invoice id, `manual:<uuid>`). `RecordPending`, `Settle` (creates or moves the row to `settled` and assigns **our invoice number** `ST-<year>-<000001>` — unless `Payment.Unnumbered` (RP24-1: the $0 `subscription_create` invoice of a trialing subscription settles with `invoice_number` NULL, spends no number, gets no receipt) from `invoice_counters` — the year's row is incremented with `INSERT … ON CONFLICT DO UPDATE … RETURNING` inside the settle transaction, so concurrent settles are numbered one after another and a rolled-back settle gives its number back: gapless per UTC year; a replay of a settled row returns it, `Newly` false), `Fail` (a declined charge; never moves a settled row back), `Expire` (partial or not) / `Invalidate` (open rows only), `Credit` (a settled `credit` row, no receipt number). Statuses: `pending processing settled failed expired expired_partial invalid refunded` ('failed' is WP-PAY-1's addition to the design). **Metadata keys:** `ids` (provider ids, kept), `addresses` and `txids` (dropped at erasure). The ledger is an accounting record: never pruned by the retention job; `account.EraseRows` nulls `tenant_id` and `note` and drops `addresses`/`txids`.

## Knobs, readiness, metrics

- `ENTITLEMENT_GRACE` (`GraceFromEnv`): a Go duration, 1h–60d, default 14 d (336h, F-26); a rejected value is a Warn and the default.
- `ReadyHistory` — `UnreadyWithin(provider, 24h)`: the lapse job skips a tenant whose provider was unready in the window (a house is never lost because our processor was down). Production wiring = the `Registry` (WP-PAY-2); `AlwaysReady` is the runner's default without one (tests).
- `vaultaire_payment_provider_ready{provider}` — 1 while the provider can take a payment; every registered provider's series from `Register` (prod without a Stripe key: `stripe` 0).
- `vaultaire_payments_total{provider,kind,outcome=settled|failed|replayed}` (`CountPayment`, called AFTER the caller's commit; Stripe charge outcomes at 0 from boot), registered through `Collectors()`. The lapse job adds `vaultaire_entitlements_lapsed_total` and `vaultaire_entitlements_expiring{window=7d|30d|in_grace}` (read from the table) in `internal/api`.
