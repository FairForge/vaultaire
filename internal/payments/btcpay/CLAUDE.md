The BTCPay Server provider (WP-PAY-4, Stage 1a Prompt 24; design `docs/PAYMENTS.md` § 3, the lab's facts in § 3.2 "Verified" and the § 3.3 rows marked **Lab**). Imports `internal/payments` (and `audit`), never a provider SDK; nothing in `internal/dashboard` imports it.

`payments.ClaimEvent` (`internal/payments/claim.go`) is the dedup contract on `payment_events (provider, event_id)`, mirroring billing's `claimEvent`: the claim tx held across the handler, rolled back on a retryable error, the tenant written on commit.

## Verdicts and the store's queue (Prompt 25 Part 0, RP30-1…6)
BTCPay 2.4.5 sends one delivery at a time per webhook (`MultiProcessingQueue` keyed by webhook id), on an `HttpClient` with no timeout (100 s), and its automatic redelivery waits 10 s, 1 min, 6 × 10 min **inside the queued task**: one 5xx stalls every other invoice of the store for ~71 min. So the handler answers 5xx only for what a retry can fix (DB error, Greenfield 5xx / no answer, the lock not free in 15 s). Every delivery that applies nothing is a **verdict** (`applied.verdict`): 200, the claim **rolled back** (a redelivery — same `originalDeliveryId` — is handled fresh, RP30-3), counted under its outcome: `foreign` (not ours, unknown at BTCPay, metadata/amount mismatch — Warn; rule `BTCPayWebhookForeign` warns), `settled_unpaid`, `mark_refused`, `fetch_refused` (Error; rule `BTCPayPaymentNotApplied` pages). `IsPermanent(err)` (`client.go`) = a 4xx other than 408/429. A second webhook on the store has its own queue: overlapping deliveries are serialised by the lock (RP30-1) — the store keeps ONE webhook, ever. Tests `wp_p25_part0_test.go`: `TestBTCPayWebhook_TwoSettleDeliveriesOverlap_GrantOnce`, `_ExpiredAfterConcurrentSettle_NoCredit`, `_ForeignThenRedeliveredAfterFix_Applies`, `_MarkStatus422_200Counted`, `_FetchRefused_200Counted`, `_SettledUnpaid_Counted`, `_NewOutcomesExistAtZero`; `config_test.go` `TestLoadConfig_PlainHTTPOnlyToLoopback`.

| `provider.go` | `Provider` (`payments.Provider` + `payments.LockedCheckout`): Name `btcpay`, Renewal `prepaid`. **Readiness** = its own 60 s `Check` (`Start`): `Health` (the body's `synchronized`) + `ProbeInvoices`; Pending before the first check, Unready after **two** consecutive failures, Ready after one success; `Ready()` never touches the network (the registry asks on every checkout) — the registry records it into `payment_provider_readiness` like Stripe's. **Checkout** (`StartCheckoutTx`, under `payments.StartCheckout`'s guard and lock): the charge from `QuoteHouse`, less the tenant's ledger credit (`payments.CreditBalance` — `Checkout.CreditCents` is not trusted); the pending row (`pending:<ledger uuid>`) is committed in its OWN transaction BEFORE `CreateInvoice`, then renamed to the invoice id (`payments.AdoptPending`; a crash between leaves a pending row — the webhook adopts it from the invoice's `metadata.payment_id`); a failed create marks the row `failed`; invoice: USD, metadata {tenant_id, payment_id, purpose, order, period, charge/credit cents, orderId}, `expirationMinutes` 30, `monitoringMinutes` 1440, `speedPolicy` MediumSpeed < $200 ≤ LowMediumSpeed, redirect = the return URL, receipt on. **An order the credit covers** = a $0 charge settled **unnumbered** + the grant, in the guard's transaction, no invoice. **Resize** = `PriceTopUp` (`topup.go`: (new − old period charge) × remaining days / period days, inputs in the invoice metadata `top_up`) — up opens a `resize` invoice (the house changes when it settles), down / nothing left = applied in place; a period switch is refused. StopRenewal / ResumeRenewal / Cancel = no-ops (the deletion runner treats a btcpay row as nothing to cancel — `TestDeletionRunner_BTCPayRow_NothingToCancel`); ManageURL "" |
| `states.go` | `ServeHTTP` (POST /webhook/btcpay): cap → `VerifySig` (400) → parse → another store = 200 `foreign` → `payments.ClaimEvent(DedupKey)` (duplicate 200) → resolve the TENANT from OUR row by invoice id (a plain read; adopt from metadata if needed) → **`Lock` (wait ≤ 15 s, `webhookLockWait`) → re-read the row `payments.LockedPending` (FOR UPDATE) → GET the invoice** (RP30-1, Prompt 25 Part 0: everything that decides a write is read under the lock, so overlapping deliveries of one invoice apply one after the other) (unknown = 200 `foreign`; another 4xx = 200 `fetch_refused`; a 5xx / no answer 500, the claim rolled back) → metadata tenant / store / USD amount must match the row (else 200 `foreign`) → GET payment methods → `apply` the FETCHED invoice in the claim's transaction → commit with the tenant → after the commit: `vaultaire_payments_total`, `billing.house_granted`, `billing.invoice_marked`, the receipt mail. `apply` (§ 3.3, money from `paidAmount`): **Settled** with `paidAmount ≥ amount` → grant (new/renew/switch: `Grant` to `PaidThroughAfter` — Extend's arithmetic — provider btcpay, renewal prepaid, `pending_provider` cleared; resize: `payments.Resize`, date kept) + `Settle` (numbered unless $0) + `RecordCrypto` (rate, BTC amount, addresses, txids) + the `partial:` credit to 0 + the `overpaid:` credit = paid − amount; only on a NEW settle (a replay changes nothing); Settled with less paid (marked by hand) = no grant, an Error, verdict `settled_unpaid`. **Expired** — only while the row is still open (`Opened.Open`: pending/processing/expired*; a settled or refunded row = nothing, an Info) — with paid ≥ amount = paid late → `MarkStatus(Settled)` (audit `billing.invoice_marked`, reason `paid_late_in_full`; the InvoiceSettled that follows grants; a 4xx refusal = verdict `mark_refused`, a 5xx = 500); else `Expire` (partial when anything arrived) + the `partial:` credit = paid. **Invalid** → `Invalidate` (a settled row stays, Warn). **Processing** → status only. New / Created / Refund → nothing |
