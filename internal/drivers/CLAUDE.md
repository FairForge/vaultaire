# internal/drivers

Storage backend implementations for the Vaultaire engine. Every registered driver implements `engine.Driver` (defined in `internal/engine/interface.go`); `S3Driver` (`s3.go`) is the one exception — an embedded base type whose `Put` takes no options, so it is not an `engine.Driver` itself.

## Driver Interface Contract

```go
type Driver interface {
    Name() string
    Get(ctx context.Context, container, artifact string) (io.ReadCloser, error)
    Put(ctx context.Context, container, artifact string, data io.Reader, opts ...PutOption) error
    Delete(ctx context.Context, container, artifact string) error
    List(ctx context.Context, container string, prefix string) ([]string, error)
    Exists(ctx context.Context, container, artifact string) (bool, error)
    HealthCheck(ctx context.Context) error
}
```

All registered drivers implement `engine.Driver` directly (the old `driver.go` alias + `PutOption` shim was removed in Review R0; put options are `engine.WithContentType` etc.). `S3Driver` is only ever embedded (`QuotalessDriver`), never registered.

## The bound invariant (WP-R6-3, RP8-9)

**Nothing on the data path waits more than 30 s for a backend's first byte
or answer.** On 2026-10-17 three 60 s timers raced: the transport's
response-header timeout, the PUT deadline of a body under 64 MiB, and
aws-cli's default read timeout. A stalled Lyve chunk PUT was retried in the
same second the client gave up, a 400 to nobody. A backend that does not
answer must trip ITS breaker within seconds, never a client's timeout.

| Request | Bound | Where |
|---|---|---|
| HEAD (HeadObject/Exists, HeadBucket = the probe), DELETE, a listing page, bucket and multipart bookkeeping | **15 s** first byte, hedged at 2 s on a fresh connection | `s3OpTimeouts.Meta`, `hedge.go` |
| GetObject (Get, GetRange, GetRangeInfo, Geyser's ranges) | **25 s** to the first byte; the body is ctx-bound | `s3OpTimeouts.Get` |
| PutObject / UploadPart | the per-size deadline: **10 s** floor, 15 s for a 16 MiB part, 60 s per 64 MiB (`s3PutDeadline`), one retry on a fresh connection; the transport's PUT bound (25 s, after the body) never fires first | `put_deadline.go`, `s3OpTimeouts.Put` |
| SDK attempts | **2** on a request path, 3 on a background job | `sdkCallOptions`, `common.WithJob` |
| the probe | 15 s for the whole probe (bucket + canary) | `api/backend_probes.go` |

Exceptions, each with its reason:

- **CompleteMultipartUpload (and a server-side copy): 10 min.** The vendor
  assembles or copies the object before it answers. A re-sent Complete whose
  first copy committed answers NoSuchUpload (Prompt 2b.5 F3.8).
- **Geyser: 5 min** for a GET's first byte and a PUT's answer (tape, Vail).
  Its HEAD, DELETE and listing page are 15 s. A streamed PUT (WP-R7-2) has
  no per-size deadline and no fresh-connection retry: one attempt under
  that 5 min and the caller's context.
- **The Sync bridge (`webdav.go`)** keeps its own bounds: a PUT 2 min per
  64 MiB (`webdavPutDeadline`), an answer 5 min, metadata 60 s, a listing
  10 min, the 60 s idle watchdog. A bridge answers a PUT only after its own
  upload to Sync's cloud finished.
- **Jobs**: a tenant-walk page 60 s (`s3WalkPrefix`) and a chunk-orphan
  listing page 60 s (`s3ListPage`, WP-R8-2 B.2) over the 15 s transport
  bound; the fleet's boot (30 s).
- **The Lyve console probe** (management plane, root key): 45 s with its one
  403 retry.
- **Permafrost** (OneDrive Graph, WP-R7-4): a Graph call's headers 15 s, a
  CDN range's first byte 25 s, an upload fragment's answer **2 min** (the
  last fragment commits the file, like a Complete); 2 attempts on a request
  path, 3 under a job, every wait on ctx (`onedrive_README.md`).

A GET whose first byte never comes costs 25 s + backoff + 25 s ≈ 51 s with
its one retry, about HAProxy's 50 s server timeout. That is still under
aws-cli's 60 s.

`data_path_bounds_test.go` holds it in two ways. It reads every S3-class
client's per-class bounds from the real constructors. It also lists every
`TunedHTTPClient(...)` call and every `context.WithTimeout` in this package
with what bounds it, so a new one fails the test until someone says why.
