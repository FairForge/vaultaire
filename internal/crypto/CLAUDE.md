# internal/crypto

Encryption, key management, and chunking/dedup primitives for Vaultaire. The "post-quantum" part is ML-KEM-768 inside SSE-S3 only. Tenant keys are stored, random and versioned since WP-R8-1 (migration 084): rotation and crypto-shredding are real; encryption is not enabled in prod (no `ENCRYPTION_MASTER_KEY`). Runbook: `docs/ENCRYPTION.md`.

## Key Files

- **ssec_multipart.go** — **format 0x05, the SSE-C multipart blob (WP-SSEC-1, Stage 1a Prompt 17 Part B):** `[0x05][kind 0x02][part count u32 BE][per part: plaintext length u64 BE, sealed length u64 BE]` then the parts' streams in order, each a complete 0x04 SSE-C stream of its own (own salt, segments from 0, last flag on its final segment) sealed at UploadPart under `StreamIdentity{Tenant, Bucket, Key, Part: n}` — the part number after the identity in the AAD (`streamPartLabel` ‖ u32; a whole object's `Part` is 0 and its AAD unchanged), so part 3's stream cannot be presented as part 2 and a blob moved to another key fails at part 1. Complete needs no key: the header is a pure function of the plaintext lengths (`NewSSECMultipartHeader`, `SSECMultipartSealedLength`; every sealed length = `SSECSealedLength(plain)`), nothing of the layout is in the database. `ParseMultipartHeader` / `ReadMultipartHeader` refuse 0 or > 10,000 parts, a sealed length that is not the function, a plaintext over 1 PiB or a cut table BEFORE anything is sized from it (`ErrMultipartHeader`); `MultipartOpener` (`SSECMultipartOpen`) opens the parts in order — part 1's first segment verified before it returns, every part's plaintext checked against its table length, a part that does not open `ErrSSECKeyMismatch`, a later segment `ErrStreamCorrupt` — keeping its own copy of the key until the last part is open; `PlanMultipartRange` maps a plaintext range onto the parts it spans (`MultipartRangeSpan`: part, stream offset, offset and length inside the part) and each span is read as a range of that part's stream (its 29-byte header at `StreamOffset`, then `PlanStreamRange` + `SSECRangeOpener` under the part's identity — `api/sse_stream.go`). Tests `ssec_multipart_test.go`: round trip, the length function, the part-number binding (swapped parts, a copied blob, a whole-object stream as part 1), every absurd header, a range across a part boundary and inside the last segment, a tampered part cut with part 1 whole, an empty last part
- **ssec.go** — SSE-C (customer-provided keys). Since WP-R8-5 Part B on the streaming codec, kind 0x02: `SSECSeal(key, id, src, size)` / `SSECOpen(key, id, src)` / `SSECOpenRange(key, id, …)` / `SSECRangeOpener(key, id, h)` (a first segment that does not open — a wrong key, or since 0x04 a blob of another object under the right key — is `ErrSSECKeyMismatch`), `SSECSealedLength`; DEK = HKDF-SHA256(key, a random 16-byte salt from the header, "vaultaire-sse-c-stream-v3" ‖ header), derived before the call returns (the caller zeroes the key at once). Row value `SSECAlgorithmV3` = "AES256-SSE-C-v3"; `SSECAlgorithm` = "AES256-SSE-C" rows are the old `[nonce][ct+tag]` format, opened whole by `SSECOpenLegacy` / `SSECDecrypt` (bounded); no writer makes them (`SSECEncrypt` is gone, a test fixture). `IsSSEC(alg)` for every check. S3 header parsing (algorithm, key, MD5 validation). No DB, no key storage
- **tenant_keys.go** — `TenantKeys` (WP-R8-1, replaced `KeyManager` and the key half of `SSEService`): per tenant, numbered versions in `tenant_key_versions`, each holding a RANDOM 32-byte chunk key and the ML-KEM-768 seed of the SSE-S3 key, both wrapped under `ENCRYPTION_MASTER_KEY` with AES-256-GCM and AAD = `"vaultaire-tenant-key"‖0‖tenant‖0‖version(u32 BE)‖purpose` (a wrapped value moved to another tenant, version or column does not open). `Current` creates v1 on first use under `pg_advisory_xact_lock(hashtext('tenant_key_versions'), hashtext(tenant))` + `ON CONFLICT DO NOTHING`, then re-reads (two first writers on two processes hold the one stored key — `TestTenantKeys_TwoFirstWritersAgree`); `Version(v)` (cached 1 h, 10k bounded); `Rotate` inserts max+1 and stamps `retired_at` on the previous (the current NUMBER is cached ≤ 60 s per process, so another slot writes with the old version for up to a minute — it records it, so it stays readable); `CurrentVersion` reads past the cache (the re-encrypt job); `Forget` (the erasure); `RewrapAll` / `RewrapTenant` (rows that open only under `ENCRYPTION_MASTER_KEY_PREVIOUS` are re-wrapped; rows neither key opens are reported — `ErrKeyUnwrap`, reads fail closed) — run at boot and by every `key_reencrypt` run while PREVIOUS is set; **`Version` re-wraps a row it opened through PREVIOUS at its first use** (WP-R8-1 A3: the boot pass sees only the rows that existed at boot, and the old slot of a switch creates rows under the old master after it). All three share `rewrapRow`, the UPDATE guarded on the old wrapped bytes (two processes: one write lands); `OnRewrap` is called once per landed write. Tests use `RewrapTenant` — a global re-wrap under another master breaks other packages' rows on the shared DB. A deleted row = `ErrNoTenantKey`: the crypto-shred. The old HKDF derivation is gone with no compatibility path (prod had 0 encrypted bytes; a dev DB's encrypted chunks are unreadable)
- **stream.go** — the streaming codec (WP-R8-5, keystone K1): blob formats **0x04** (written) and **0x03** (opened), the STREAM construction (Hoang–Reyhanitabar–Rogaway–Vizár, CRYPTO 2015; Tink AES-GCM-HKDF-STREAMING / age's payload shape). `header = [0x03][kind u8][kind material][segment_size u32 BE][nonce_prefix 7]` (kind 0x01 SSE-S3: `[key_version u32][ML-KEM ct 1088]`, 1105 bytes; kind 0x02 SSE-C: `[salt 16]`, 29 bytes — Part B); segment i = AES-256-GCM(DEK, prefix ‖ i u32 ‖ last u8, aad); **aad = header (0x03) or header ‖ "vaultaire-sse-identity-v4" ‖ len‖tenant ‖ len‖bucket ‖ len‖key (0x04, u32 BE lengths — WP-R8-3 A.2, `StreamIdentity`, `streamAAD`)**: a 0x03 blob copied to another key's address under the same tenant decrypted and was served as that key (R8-10); a 0x04 one fails at its first segment, and so does one whose first byte is rewritten 0x04 → 0x03 (the header is in the DEK's derivation and the AAD). The identity is the object's KEY, never the blob's address (a retained version, a re-addressed or re-encrypted blob keeps it). A seal with an incomplete identity, or an open of a 0x04 blob without one, is `ErrStreamIdentity`. The two formats have one header layout and length, so `streamHeaderLen`, `SealedLength`, `StreamCiphertextLength`, `MaxStreamHeader` are unchanged (`IsStreamFormat` for every first-byte check); 1 MiB segments (`StreamSegmentSize`, written into the header); n = max(1, ceil(size/S)); `StreamCiphertextLength` = header + size + 16n (a pure function of the size: the backend PUT carries it). The file comment argues each tamper class (modified, reordered, dropped, duplicated, truncated, extended, header changed) and `stream_test.go` tests each: the opener returns no byte of a segment that does not authenticate, and its constructors verify the header and the FIRST segment before they return. `PlanStreamRange` maps a plaintext range onto the segments it spans (ciphertext offset/length, the bytes to skip). At most one plaintext + one ciphertext segment per stream in memory (`TestStream_OneGiB_BoundedMemory`)
- **credential_wrap.go** — the S3 secrets' wrap (Stage 1a Prompt 42, plan 43.7, migration 108): `(*TenantKeys).SealCredential(ctx, tenant, keyID, secret)` → (wrapped, version) under the tenant's CURRENT version, `OpenCredential(ctx, tenant, keyID, version, wrapped)` under the recorded one — THE seam the key broker (F-20) later replaces. Key = HKDF-SHA256(the version's chunk key, no salt, info `stored/credential/v1`) → AES-256-GCM; format `[0x01][nonce 12][ct+tag]`; AAD = `"vaultaire-credential"‖0‖tenant‖0‖keyID‖0‖version(u32 BE)`; empty names or a NUL in one are refused (the separators stay unambiguous); every refusal wraps `ErrCredentialOpen`, a shredded version is `ErrNoTenantKey`. No new key or `tenant_key_versions` column (contract rule 4); a master re-key leaves the wraps untouched (the chunk key's bytes do not change). Golden vector from Python `cryptography` in `credential_wrap_test.go`
- **sse_s3.go** — SSE-S3 service on `TenantKeys`: a fresh ML-KEM-768 encapsulation per object against the tenant's CURRENT version, DEK = HKDF-SHA256(shared secret, info "vaultaire-sse-stream-v3" ‖ header). `Seal(ctx, id, src, size)` → a 0x04 sealing reader for the object `id` (`StreamIdentity{Tenant, Bucket, Key}`; the key store is `id.Tenant`'s) + the key version (recorded on `object_head_cache.encryption_key_version`); `SealedLength(size)`; `Open(ctx, id, src)` opens a whole blob — 0x04 (as `id` only) or 0x03 streaming, a **0x02** `[0x02][key_version u32][KEM ct][nonce][ct+tag]` (5-byte AAD) or **0x01** (version 1, no AAD) blob, written before WP-R8-5 and ≤ 256 MiB, by the compatibility opener (`DecryptBytes`, the only whole-object buffer left; no writer makes these — `EncryptBytes` is gone, kept as a test fixture); `OpenRange(ctx, id, …)` a planned range, `RangeOpener(ctx, id, h)` the key once for many ranges; `SSEBlobKeyVersion` reads any of the four headers; `OnOpen` feeds `vaultaire_sse_blobs_opened_total{format}` (0x01–0x04); `SetSegmentSize` is for tests. `Current` replaced `EnsureTenantKey`
- **chunk_encryption.go** — `ChunkEncryptionService` on `TenantKeys`: per-chunk convergent encryption (AES-256-GCM with HKDF-derived deterministic nonce), convergent key = `SHA-256(chunkKey_v ‖ plaintext hash)`. `EncryptChunkData(ctx, tenant, hash, data)` seals under the CURRENT version and returns it (recorded on the GCI row and the ref); `DecryptChunkData(ctx, tenant, version, …)` opens under the RECORDED one; `EncryptChunkDataVersion` seals under a given one (the re-encrypt job). Same tenant + same version + same content → same ciphertext (dedup-safe). Ciphertext format: `[nonce 12B][GCM ciphertext+tag]` (28B overhead). **R8-01 (2026-09-27):** the key is fixed by `(tenant, plaintextHash)` but the sealed bytes are the chunk AFTER the compression decision (raw or zstd, per request Content-Type), so the nonce is `HKDF(convergentKey, salt = SHA-256(sealed bytes), info "vaultaire-chunk-nonce-v2")` — a function of the message, never of the plaintext identity alone (the v1 derivation reused one (key, nonce) for two different messages when two stores compressed differently — NIST SP 800-38D §8). Decrypt reads the nonce from the blob prefix, so v1 blobs still decrypt (`TestChunkEncryption_LegacyV1BlobDecrypts`). The version a blob is sealed under is recorded with it since WP-R8-1
- **encryption.go** — `Encryptor` interface: AES-256-GCM, ChaCha20-Poly1305, Noop. Only `NewChunkEncryptionService` reaches it from the product; the rest is unreachable (Review R0 → R8)
- **compression.go** — LZ4/Zstd/Snappy compression with auto-detection
- **chunker.go** — Content-defined chunking via `restic/chunker` (Rabin fingerprinting): `RabinChunker`, `DefaultChunker()`, ≈2 MiB real average. **Its identity is one constant set and on record (WP-R8-4)**: `ChunkerIdentity` = library `github.com/restic/chunker` @ `v0.4.0` (pinned in go.mod; `TestChunkerIdentity_MatchesGoMod`), polynomial `0x2ADD89E3B790BB`, min 1 MiB, **average bits 20** (passed explicitly now — it was the library's default, never ours), max 16 MiB; written into every chunked object's `object_metadata.pipeline_config` (`PipelineConfig.Chunker`, `RecordedPipeline`), and `TestRabinChunker_GoldenBoundaries` cuts a fixed 24 MiB pseudo-random input at eleven recorded offsets, so a dependency bump or any change to the set fails the build. Decision (status quo, to be confirmed by Isaac): keep the 2 MiB average — `SetAverageBits(22)` would reset dedup for everything stored
- **gci.go** — Global content index for deduplication
- **config.go** — Crypto configuration types

## SSE-S3 Architecture (Phase 5.14.4)

**SSEService** provides transparent server-side encryption at rest:

- **master_key_source.go** — `LoadMasterKeys(getenv, readFile)` (WP-R8-1 A5): per key, the systemd credential `$CREDENTIALS_DIRECTORY/encryption_master_key` (`_previous`), then `ENCRYPTION_MASTER_KEY_FILE` (`_PREVIOUS_FILE`), then the variable; trimmed, 64 hex; a source set but unreadable/malformed — or PREVIOUS without a master — is `ErrMasterKeySource` (the server makes it fatal); errors name the source, never a character of the value (`encoding/hex` would quote one); `Ignored` lists lower sources also set. A credential directory without the key falls through (the unit may carry other credentials).
- **Key hierarchy**: ENCRYPTION_MASTER_KEY (32B hex: a TPM-sealed systemd credential on prod, a file or the env) → wraps each tenant key version (`tenant_key_versions`) → that version's ML-KEM-768 keypair → per-object shared keys via KEM encapsulation → HKDF-derived AES-256 DEKs
- **Encrypted blob formats** — what each binds:

  | format | written | layout | each piece authenticated with |
  |---|---|---|---|
  | `0x01` | before WP-R8-1 (opened only) | `[0x01][KEM ct][nonce][ct+tag]`, whole | nothing (no AAD); key version 1 |
  | `0x02` | WP-R8-1 → WP-R8-5 (opened only) | `[0x02][key_version][KEM ct][nonce][ct+tag]`, whole | the 5-byte prefix (format, version) |
  | `0x03` | WP-R8-5 → WP-R8-3 A.2 (opened only) | `[0x03][kind][material][segment_size][nonce_prefix 7]` + 1 MiB segments | the header (kind, version, KEM ct, segment size, nonce prefix) + the segment's index and last flag in its nonce |
  | `0x04` | **every writer since WP-R8-3 A.2** | the 0x03 layout, first byte 0x04 | the header + **the object's tenant, bucket and key** (+ **the part number** for a part sealed at UploadPart, WP-SSEC-1) + the index and last flag |
  | `0x05` | **CompleteMultipartUpload of an SSE-C upload (WP-SSEC-1)** | `[0x05][0x02][count u32][per part: plain u64, sealed u64]` + the parts' 0x04 streams | each part by its own stream (above); the table by the lengths it must satisfy (every sealed = `SSECSealedLength(plain)`) and by the parts opening in order under their numbers |

  Prod held no sealed blob of any format when 0x04 shipped (no master key), so there was nothing to migrate; a 0x03 blob (labs, tests) is re-sealed 0x04 by the next `key_reencrypt` whole pass that moves it. **Chunk encryption is not changed**: a chunk is shared by every object of a tenant that holds its bytes (the dedup), so it has no bucket or key to bind; what binds its content is the check after the open — the plaintext's SHA-256 must equal the chunk's hash (the index row's `plaintext_hash`), so a chunk blob swapped for another chunk's fails there
- **Size overhead**: 1105 + 16 × segments (`SealedLength`); 1121 for a 0x02 blob, 1117 for a 0x01
- **No size limit**: one segment is in memory per stream (the 256 MiB `MaxEncryptableSize` is gone, WP-R8-5)
- **ETag**: computed on plaintext, not ciphertext (S3 compatibility)
- **object_head_cache.size_bytes**: stores plaintext size (matches AWS SSE-S3 behavior)
- **Tenant seed protection**: AES-256-GCM under the master key with AAD tenant‖version‖purpose, `[0x01][nonce][ct]`, in `tenant_key_versions.kem_seed_wrapped` (`tenant_encryption_keys`, 037, is read by nothing since 084 — D-12 drop)

**Activation**: a master key from the credential, `ENCRYPTION_MASTER_KEY_FILE` or `ENCRYPTION_MASTER_KEY` (64 hex chars). When absent, SSE-S3 is disabled; when set but unusable, the boot is refused. Per-bucket via `sse_enabled` column, per-request via `x-amz-server-side-encryption: AES256` header.

**One ML-KEM implementation**: `sse_s3.go`, Go stdlib `crypto/mlkem`. The dead cloudflare/circl copy (`postquantum.go`) was deleted on 2026-10-10 (decision D-3) and `github.com/cloudflare/circl` left go.mod with it.

## Chunking + Dedup Architecture (Phase 8.3-8.5)

**Content-defined chunking** splits large objects (>64 MB) into chunks. The **Global Content Index** (GCI) deduplicates unencrypted chunks across all tenants — identical content is stored once; encrypted chunks dedup within the tenant only (scope = tenant ID). `gci_test.go` runs against the real migrated test DB (`testutil.DSN()`, per-test `dedup_scope`, scoped cleanup — R8-13; it had never run before). Since Phase 10, chunking and encryption are no longer mutually exclusive: per-chunk convergent encryption (AES256-CE) is applied when `ENCRYPTION_MASTER_KEY` is set.

**Global chunk store** (Phase 8.5.1; **one address since WP-R8-7**): chunks are stored in a shared, tenant-independent container `_global` (`engine.ChunkContainer`), NOT the per-tenant/bucket namespace. Because dedup spans tenants, a chunk first written by tenant A / bucket X must be reachable when tenant B / bucket Y dedups against it. "Tenant-independent" needs the DRIVER CONTEXT too: a fixed-bucket backend (iDrive — prod's primary — Lyve, Geyser, R2, permafrost) keys every object `t-<tenant in the context>/<container>/<artifact>`, so a chunk written during A's request sat under `t-<A>/_global/…`, B's GET of the deduplicated object answered 500, and dedup GC (no tenant in its context) "deleted" under `t-default/` (WP-R8-7, found by WP-R10-3c). A chunk's one address is now its index row's `backend_id` + `_global` + the reserved tenant `engine.ChunkAddressTenant` (`_global`) in the context: `t-_global/_global/_chunks/<hash>`. Every chunk blob call — the PUT pool, the chunked GET, GC, the chunk move — goes through `api/chunk_store.go`, which builds that context with `engine.ChunkContext` (the engine refuses a chunk container write under any other tenant, `ErrChunkAddress`). Blobs written before are read from the uploader's prefix as a fallback until the operator's chunk move (`POST /api/v1/admin/chunk-move`) has brought them over. Isolation is preserved at the manifest layer: a tenant reaches a chunk only through its own `tenant_chunk_refs` (queried by `tenant_id`), and `_global` is not addressable via the S3 API (a tenant's containers are `<tenant>_<bucket>`, under its own id; the S3 front door refuses a reserved id).

- **chunker.go** — content-defined chunker (`RabinChunker`: 1 MiB min / 16 MiB max / 20 average bits — a boundary is the first position after the minimum where the fingerprint's low 20 bits are zero, so the real average is ≈2 MiB = `ChunkExpectedAverage`: 36 chunks per 70 MiB measured, 33 per 70 MB in the WP-R8-7 proof, 127 per 256 MB in prod — R8-11; the former "4 MiB avg" constructor argument was accepted and ignored and is gone, WP-R8-4) using `restic/chunker`. `ChunkBytes()` for sync, `Chunk()`/`ChunkContext(ctx)` for streaming (context-cancellable — goroutine exits on ctx.Done). SHA-256 per chunk.
- **gci.go** — `GlobalContentIndex`: DB-backed dedup index with 100K-entry in-memory cache. **Every accessor reads `state = 'ready'` rows only** (WP-R8-2, 093): `LookupChunk`/`LookupChunkFresh`, `LookupChunks` (the GET plan), `IncrementRef`/`IncrementRefTx` (0 rows on a pending row → the caller stores, i.e. waits on the claim), the global stats; a pending row's blob may not be there yet. `InsertChunk`/`InsertChunkTx` insert ready rows (tools and tests); the product's chunk store claims through `internal/api/chunk_claim.go`; an entry is served for at most `gciCacheTTL` (5 min, Stage 1a A3) — rows are repointed by other processes (chunk move on the admin slot, key re-encrypt, the inactive slot during a switch) that `InvalidateCache` cannot reach. Batch lookups (`LookupChunks`), ref counting (`IncrementRef`/`DecrementRef`), cache invalidation (`InvalidateCache` — used by the GC sweep, WP-6), tenant chunk manifests (`AddTenantChunkRef`), object metadata (`SaveObjectMetadata`), transactional delete (`DeleteObjectChunks`/`DeleteObjectChunksTx` — the Tx variant releases a displaced manifest atomically with a caller's plain PUT/copy/multipart overwrite), atomic manifest swap on overwrite (`ReplaceObjectManifest`/`ReplaceObjectManifestTx` — releases old refs + installs new manifest + metadata; the Tx variant runs inside the PUT's head-upsert transaction so swap and head cache commit together), chunk insert inside a caller-owned tx (`InsertChunkTx` — pairs with the WP-6 advisory lock; invalidates rather than sets the cache since the caller may roll back). **`IncrementRef` returns `(rowsAffected, error)` (WP-6)** — 0 rows means the chunk row vanished (GC swept it after a stale cache hit); callers MUST re-store instead of proceeding, or the manifest points at deleted data. Both `IncrementRef` and `DecrementRef` cache-delete their entry; `insertChunkSQL`'s ON CONFLICT arm also unmarks (`marked_for_deletion=FALSE, marked_at=NULL`) so re-referencing a marked row rescues it from sweep.

**PUT flow** (s3_engine_adapter.go `handleChunkedPut`, streaming since Phase 8.4.1):
1. Gate: `gci != nil && size > threshold && !versioned && body unencrypted` — SSE-C bodies never chunk; versioned/suspended buckets keep the plain path (manifests lack version_id); tenant IDs are strings, no UUID gate (WP-C). On chunked-path error, return 5xx (never fall through — the body is consumed).
2. `ChunkContext(ctx, hashingBody)` streams through the MD5 hasher+chunker — peak memory is one chunk (~16 MB) regardless of object size. Per-chunk: `LookupChunk` → if new → `storeChunkLocked` (`internal/api/chunk_claim.go`, WP-R8-2 B.1, migration 093: a short claim transaction under `pg_advisory_xact_lock(hashtext(scope), hashtext(hash))` writes the row `pending` at ref 0, then `chunkStore.put` (= `engine.Put` on `engine.ChunkContext`, `_global/_chunks/{sha256}`) runs with NO lock and NO connection held, then a second short transaction flips it `ready` with the writer's reference — before 093 it was one transaction across the PUT; still serialized against the GC sweep, WP-6); if existing → `IncrementRef`, and **rows-affected 0 → the chunk vanished → re-store as new** (WP-6). Collect the new manifest refs and accumulate `measuredSize`.
3. `ReplaceObjectManifestTx` + `object_head_cache` upsert (`is_chunked=TRUE`, `measuredSize`) commit in ONE tx via `atomicHeadUpsert` (review-A): release the previous version's chunk refs + install the new manifest + upsert `object_metadata` + head row — a failed install leaves the previous version fully intact. New chunks are ref'd in step 2 *before* this, so a chunk shared between old and new versions never transiently hits ref_count 0. After install, the stale pre-chunking whole-object blob at the key is deleted (best-effort).
4. **Abort compensation (WP-6/F10)**: every chunk processed takes one GCI ref; if the PUT errors before the manifest install commits, a deferred compensator `DecrementRef`s each taken ref on a cancellation-immune context — otherwise aborted PUTs leak increments on shared chunks until reconcile.

**DELETE flow** (s3_engine_adapter.go `HandleDelete`):
1. Query `is_chunked` from `object_head_cache`
2. If chunked → `gci.DeleteObjectChunks` (transactional: deletes refs, decrements counts, deletes object_metadata)
3. Chunk data stays until GC (Phase 8.7) — `marked_for_deletion=TRUE` when `ref_count=0`. GC deletes at the chunk's one address (each GCI entry's `backend_id`/`storage_key`, through `chunkStore.delete` on `engine.ChunkContext`), never in a tenant namespace — and, since WP-R8-7, asks the backend for the blob BEFORE the row goes: a backend that cannot be asked keeps the candidate; a blob still only at a legacy address keeps the row (`legacy_pending`) for the chunk move.

**GC coherence (WP-6, item 1.7)**: the dedup GC sweep (`internal/api/dedup_gc.go sweepOne`) invalidates the GCI cache before and after each row delete, and holds a session-level `pg_advisory_lock(hashtext(scope), hashtext(hash))` on a dedicated connection across row-delete → blob-delete (row delete commits first; every failure mode leaks at most a blob). The PUT-side `storeChunkLocked` takes the same lock as `pg_advisory_xact_lock`, closing the delete-vs-reref race. GDPR `ExecuteDeletion` releases the tenant's GCI refs set-based inside the deletion tx and marks zero-ref rows for sweep (F5). Advisory locks and cache keys are always keyed on BOTH `(dedup_scope, plaintext_hash)`.

**GET flow** (s3_engine_adapter.go `handleChunkedGet`, Phase 8.5 → streaming in 8.6):
1. `HandleGet` reads `is_chunked` from `object_head_cache`; if set and `gci != nil`, branches before the normal `engine.Get`
2. Preflight: `GetObjectChunks` → ordered manifest; per chunk `LookupChunk` resolves storage key + `BackendID` + `SizeBytes` WITHOUT reading data. A missing index entry → return error → caller falls through (→ NoSuchKey). Done before any byte is written.
3. **Bounded streaming** (8.6): each chunk is read into a bounded buffer (≤ max chunk size, ~16 MB) via `fetchAndVerifyChunk` (`chunkStore.get`: `engine.GetOn(backend_id, _global, "_chunks/{sha256}")` on `engine.ChunkContext`, falling back to the uploader's prefix only when the one address answers "not there" — never on an error), its SHA-256 verified against the expected plaintext hash, then written to the response. Peak memory is ONE chunk, not the whole object (was a full `bytes.Buffer` in 8.5 — violated "always stream"). Order is `chunk_index` ASC → byte-identical to upload → plaintext ETag matches. Cross-bucket/cross-tenant retrieval works because chunks live at one address, in shared `_global` under the reserved tenant.
4. Range requests touch only chunks overlapping `[start,end]`, located via `tenant_chunk_refs.chunk_offset` + per-chunk `SizeBytes`; the first/last overlapping chunks are trimmed (`skip`/`take`). No whole-object materialization.
5. **Integrity** (8.6): corrupt chunk (sha256 mismatch) → never served. First-chunk corruption → clean 500 (`errChunkIntegrity`, handled here, NOT a fallthrough to 404 — corrupt ≠ missing). Mid-stream failure → the connection is cut (`panic(http.ErrAbortHandler)` via `abortResponse`, counted in `vaultaire_chunked_get_truncated_total{reason}`), never a clean end; a chunk backend that cannot be asked (unregistered, breaker open) is 503 before any header, whichever chunk it holds (Stage 1a Part A). HEAD needs no chunk-aware logic — `object_head_cache` already holds plaintext size/ETag.

**Constraints**: chunking is mutually exclusive with SSE-C (customer keys) — enforced at the gate since review-D (#343): an SSE-C body that entered the chunked path was stored as chunked ciphertext with AES256-CE stamped over the SSE-C marker, so a keyless GET served raw ciphertext with 200. Versioned buckets are mutually exclusive with chunking (review-A, #341) until manifests are version-aware. SSE-S3 objects >256 MiB route through per-chunk convergent encryption (Phase 10) when `chunkEncSvc` is available. Cross-tenant dedup of encrypted chunks is not supported — same-tenant dedup works via convergent determinism.

**Deterministic chunking (WP-7)**: `NewRabinChunker` uses a single fixed polynomial, `DefaultChunkerPolynomial` (`0x2ADD89E3B790BB`). This value is **PERMANENT** — changing it re-defines every chunk boundary, so nothing would dedup against existing chunks and re-chunking to locate data would fail (every stored chunk orphaned). Pinned by `TestRabinChunker_PermanentPolynomial`, and since WP-R8-4 by the golden boundaries. Before WP-7 each chunker drew a fresh `RandomPolynomial`, so identical content never produced matching chunk hashes and dedup could never hit.

**Tenant-scoped encrypted dedup (WP-7)**: the GCI is partitioned by a `dedup_scope`. Unencrypted chunks use `crypto.GlobalDedupScope` (`"_global"`) — shared across tenants. Encrypted chunks use the **tenant ID** as the scope, and are stored under `_chunks/{tenantID}/{hash}` (at the same one address, `t-_global/_global/_chunks/{tenantID}/{hash}` — the scope partitions the index, not the prefix; an erased tenant's scoped chunks are released on the date and collected by GC like the shared ones); their `tenant_chunk_refs.dedup_scope` records this so GET/DELETE/GC resolve the right row. This is why deterministic chunking is safe: identical plaintext from two tenants yields identical plaintext hashes but distinct scoped GCI rows, each encrypted with that tenant's convergent key — so tenant B never receives tenant A's undecryptable ciphertext. `LookupChunk`/`IncrementRef`/`DecrementRef`/`LookupChunks` all take a scope argument; `GCIEntry`/`TenantChunkRef` carry `DedupScope`.

**Ciphertext hash lives on the GCI row**: `global_content_index.ciphertext_hash` (nullable, set for encrypted chunks) is the SHA-256 of the blob actually stored, recorded once at first store. Dedup hits COPY it from the row into the new `tenant_chunk_refs` entry — never recompute it. Recomputing depended on the current request's Content-Type matching the first uploader's (`ShouldCompress` consults Content-Type, so the compression decision could differ) and on zstd output being byte-stable across library versions; either mismatch produced a hash of a blob that was never stored, and the object then failed its integrity precheck on every GET. On read, the GCI row's hash is authoritative; the per-ref copy is a fallback for older rows.

**SSE-S3 ↔ chunk-encryption mutual exclusion (WP-7)**: whole-object SSE-S3 (`sseService`) is skipped when an object will take the chunked per-chunk-encryption path (`chunkEncSvc` set, size > chunk threshold, non-versioned bucket). Otherwise the object would be encrypted twice (SSE-S3 whole-object, then per-chunk) and GET — which only peels the per-chunk layer — would return SSE ciphertext. SSE-S3 is also non-deterministic (random ML-KEM ciphertext + nonce), which would defeat chunk-dedup determinism. Guarded by `TestChunkedEncryption_SkipsWholeObjectSSE`.

**Tables**: `global_content_index`, `tenant_chunk_refs`, `object_metadata` — created by migration **016** (051's CREATEs were no-ops; 016 is the source of truth per review-B #340), TEXT tenant_id at source + migration 058 converts pre-2026-07-18 DBs in place (WP-C). Scope partitioning + `ciphertext_hash` via 054. `object_head_cache.is_chunked` flag.

## SSE-C Architecture (Phase 5.14.8)

**Stateless** customer-provided key encryption. No DB, no key management — the customer sends a raw 256-bit AES key with each PUT/GET/HEAD request.

- **Encrypted blob format** (since WP-R8-5 Part B, row `AES256-SSE-C-v3`; first byte 0x04 since WP-R8-3 A.2 — the object's identity in each segment's AAD, as SSE-S3; 0x03 still opens): `[0x04][0x02][salt 16][segment_size 4][nonce_prefix 7]` then 1 MiB segments with their tags (`stream.go`); the old format `[nonce (12B)][AES-GCM ciphertext+tag]` (row `AES256-SSE-C`) still opens. The row decides the format, never the first byte (a nonce byte is 0x03 one time in 256)
- **Size overhead**: 29 + 16 × segments (`SSECSealedLength`); 28 bytes for the old format
- **No size limit**: one segment in memory per stream
- **ETag**: computed on plaintext (before encryption)
- **Key never stored**: only the algorithm indicator `AES256-SSE-C` in `object_head_cache.encryption_algorithm`
- **Mutually exclusive** with SSE-S3 per object
- **S3 headers**: `x-amz-server-side-encryption-customer-algorithm: AES256`, `x-amz-server-side-encryption-customer-key: <base64>`, `x-amz-server-side-encryption-customer-key-MD5: <base64>`
- **GET/HEAD without key**: returns 403 AccessDenied
- **Multipart uploads**: parts sealed at UploadPart under the key in the request (each its own 0x04 stream bound to the part number), Complete writes the 0x05 container without a key (`ssec_multipart.go`, WP-SSEC-1)
- **CopyObject**: the source opened under its key (`x-amz-copy-source-server-side-encryption-customer-*`), the destination sealed under the request's key (WP-SSEC-1 B.4)
